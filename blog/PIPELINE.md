# eddmpython 블로그 파이프라인

이 문서는 블로그 제작과 발행의 정본이다. DartLab의 작가 파이프라인에서 독자 질문, 핵심 답,
검증과 편집의 분리, 발행 게이트를 가져왔다. 점수표와 역할 수는 복제하지 않고 이 저장소의
글 수와 운영 규모에 맞게 줄였다.

# 작가 파이프라인

**이 절이 다른 모든 규칙보다 먼저다.** 아래 항목이 안 되면 뒤의 형식 계약을 다 지켜도 실패다.

## 순서: 절 뼈대가 먼저다

**글자를 쓰기 전에 절 제목부터 세운다.** 문장부터 쓰고 나중에 목차를 정리하면 이음이 죽는다.

1. 이 글이 답할 질문 하나를 적는다
2. **절 제목만 나열한다.** 본문을 쓰지 않는다
3. 절마다 `이 절이 남기는 모르는 것`을 한 줄 적는다
4. 인접한 두 절의 자리를 바꿔 보고 글이 깨지는지 본다. 안 깨지면 뼈대가 틀린 것이다
5. 그 뼈대를 카테고리 폴더의 `원장.md` 에 올린다
6. **뼈대가 통과한 뒤에 본문을 쓴다**
7. 다 쓰고 `python blog/scripts/outline.py` 로 원장과 본문을 대조한다

절 제목만 읽어도 글이 무슨 이야기인지 보여야 한다. 안 보이면 본문을 아무리 잘 써도 안 읽힌다.

## 게이트는 절이지 글자 수가 아니다

**분량으로 막지 않는다.** 하한에 미달할 때 가장 싼 해는 새 사실이 아니라 같은 사실의
재진술이다. 2026-08-17 에 발행 40편을 실측해 확인했다. 막는 것은 절 사슬이다.

## 아홉 가지 관문

운영자가 정한 것이다. 하나라도 아니면 발행하지 않는다.

1. **무조건 쉽게.** 읽는 사람은 코드를 한 줄도 써 본 적이 없다
2. **추상적 문장 금지.** 파일, 화면, 명령, 값, 오류 중 하나가 그 문장 안에 있어야 한다
3. **운영자 문체를 따른다.** 작법은 `memory/writingVoice.md` 다
4. **내용이 자연스럽게 이어진다.** 절과 절 사이가 예고가 아니라 사슬이어야 한다
5. **기승전결이 있다.** 절 순서를 바꾸면 글이 깨져야 한다
6. **절을 뼈대로 먼저 세우고 그것이 학습에 도움이 되는지 본다**
7. **볼거리가 풍부하다.** 영상과 이미지와 실행 칸이 절마다 있는지 본다
8. **퀄리티가 좋다.** 허접해 보이는 자리가 없어야 한다
9. **진짜 공부에 도움이 된다.** 읽고 나서 실제로 할 수 있는 것이 늘어야 한다

## 일곱 가지 함정

위 아홉을 지키려다 빠지는 자리다. 전부 이 저장소에서 실제로 겪었다.

10. **확인한 것만 쓴다.** 돌려 보지 않은 출력과 실측하지 않은 수치를 쓰지 않는다.
    2026-08-19 에 001 을 고치며 절을 이으려고 사실 아닌 인과를 여섯 군데 지어냈다
11. **없는 인과를 지어내지 않는다.** 예고는 지루할 뿐이지만 틀린 인과는 거짓이다.
    이을 말이 없으면 절을 합치거나 순서를 바꾼다
12. **개수를 미리 읊지 않는다.** `이유 세 가지입니다` 를 먼저 말하고 세 절이 차례로 다루면
    그 세 절은 사슬이 아니라 목록이 된다. 자리를 바꿔도 글이 성립한다
13. **자기 판정을 믿지 않는다.** 자기 글의 이음은 언제나 이어져 보인다.
    다른 눈이 인접 절의 자리를 바꿔 보는 검사를 거친다
14. **실패를 하나 보여준다.** 정답만 보여주면 독자는 자기가 막혔을 때 무너진다
15. **검색으로 바로 들어와도 닫힌다.** 앞 글을 먼저 읽으라고 요구하지 않는다.
    필요한 개념은 그 글에서 짧게 정의한다
16. **예제는 독자의 일이어야 한다.** 회사 엑셀과 전표에서 가져온다.
    문법을 설명하려고 만든 가짜 예제를 쓰지 않는다

## 좋은 글이 갖춰야 할 것

한 편은 다음 여덟 가지를 만족해야 한다.

1. 누가 읽는 글인지 한 사람을 정한다.
2. 그 사람이 아직 모르는 말을 먼저 적는다.
3. 처음부터 끝까지 질문 하나에 답한다.
4. 실제 화면, 코드, 파일, 숫자로 설명한다.
5. 저장소에서 확인한 사실과 글쓴이의 생각을 구분한다.
6. 왜 그렇게 동작하는지 원인과 관계를 설명한다.
7. 실패 사례, 반례, 한계 중 하나 이상을 다룬다.
8. 글을 읽은 사람이 바로 해 볼 행동과 확인 방법으로 끝낸다.

분량만 늘리는 것은 목표가 아니다. 그러나 짧다는 이유로 정의, 원리, 예제, 실패, 검증을 생략해서도
안 된다. 처음 온 독자가 다른 글이나 강의 자료를 먼저 읽지 않고도 질문의 답을 이해하고 직접 확인할
수 있는지를 본다. 어려워 보이게 만드는 문장, 제품을 좋아 보이게만 만드는 문장, 앞 문장을 되풀이하는
문장은 삭제한다.

### 한 편은 주제 하나다

한 편이 답하는 주제는 하나다. 그 주제에 기승전결이 있어야 한다.

2026-08-18 에 006 번을 고치면서 이 원칙을 어겼다. 검증, 입력 계약, 경계값, 재실행, 다섯 칸을 한 글에
넣었는데 그 넷은 이미 각각 024, 018, 015, 016 번 글이었다. 다른 글 네 편을 한 글 안에 다시 넣어 놓고
구조가 난잡하다고 문장을 고치고 있었다. 절이 여럿인 것은 문제가 아니다. 주제가 여럿인 것이 문제다.

절은 몇 개여도 된다. 다만 절 사이가 이어져야 한다. 각 절의 마지막 문장이 다음 절의 질문을 만들고,
H2 순서를 바꾸면 글이 깨져야 한다. 순서를 바꿔도 성립하면 그것은 나열이지 기승전결이 아니다.

### 절의 구조

절 하나는 언제나 이 순서다.

```markdown
## 독자의 질문이나 장면이 보이는 제목

### 이 절에서 무엇을 볼지 알려 주는 한 줄 부제

![본문과 직접 관련된 대체 텍스트](이미지 또는 영상 주소 "이 장면을 어떻게 읽을지 말하는 캡션")

이미지 다음에는 코드나 목록보다 서술형 설명을 먼저 둔다. 한 문단은 소스에서도 한 줄이다.

#### 예시 코드: 역할과 개념이 함께 보이는 제목
```

보조자료는 없어도 된다. 넣는다면 실행 가능한 코드, 입력과 결과가 있는 실제 예, 순서를 풀어 쓴 목록이나
표만 쓴다. 캡션은 그 절의 결론을 미리 말하지 않는다. 결론을 캡션에 넣으면 독자가 본문을 읽을 이유가
사라진다.

### 서술 문단은 줄을 바꾸지 않는다

한 문단은 소스에서도 한 줄이다. 하드 줄바꿈은 문장을 임의의 자리에서 끊어 보이게 하고, 고칠 때 문단
단위로 다시 읽기 어렵게 만든다. `check:post` 가 막는다.

### 추상적인 문장을 쓰지 않는다

`환경`, `구조`, `흐름`, `경계`, `맥락`, `관점`, `과정`, `방식`, `역할`, `가치`, `기반`, `가능성`,
`본질`, `체계`, `전략`, `경험`, `판단`, `규칙` 을 쓴 문장에는 그 문장 안에 파일, 화면, 명령, 값, 오류
가운데 하나가 있어야 한다. 이웃 문장에 있는 것으로는 인정하지 않는다. 문단 단위로 재던 예전 검사는
추상 문장 하나가 구체적인 이웃 문장에 묻어가는 것을 막지 못했다.

### 글자 수 하한을 쓰지 않는다

예전 계약은 깊이를 서술 3,000자와 4,000자로 쟀다. 2026-08-17 에 발행 40편을 실측한 결과 이 하한이
정확히 반대로 작동하고 있었다. 하한에 미달할 때 가장 싼 해가 새 사실이 아니라 같은 사실의 재진술이기
때문이다. 006 번은 하한에 딱 맞춘 3,719자였고 장문 21편 가운데 문단 길이 편차가 가장 작았다.

같은 이유로 절마다 고유 이미지를 요구하던 규칙도 없앴다. 그 규칙이 40편 전부에서 H2 수와 이미지 수를
1 대 1 로 묶었고, 이미지 제작 비용이 절 개수의 상한까지 정하고 있었다. 이미지는 문장으로 따라가기
어려운 장면에만 넣는다.

분량은 목표가 아니다. 주제 하나를 끝까지 답했으면 짧아도 된다.


### 카테고리는 강의 한 묶음이다

`blog/order.json` 의 `categories` 가 카테고리 정본이다. 카테고리 하나가 강의 한 묶음이며 글은
`posts[].category` 로 그 묶음에 속한다. 글 파일은 `blog/<category-slug>/NNN-kebab.md` 에 둔다.
폴더 이름과 category slug 는 같다. 그 폴더의 `원장.md` 가 글 제목 사슬의 정본이다.

```json
{
  "version": 3,
  "categories": [
    { "slug": "work-automation", "title": "업무자동화", "order": 1, "summary": "..." }
  ],
  "posts": [{ "order": 1, "slug": "what-is-python", "category": "work-automation" }]
}
```

**공개 URL 은 카테고리를 넣지 않는다.** `/blog/{slug}` 한 형태를 유지한다. 이미 발행한 slug 를
바꾸면 검색 색인과 외부 링크가 끊어진다. 카테고리는 `/blog` 목록에서 묶어 보여 주는 데만 쓴다.

`check:blog` 가 카테고리 slug 형식과 중복, order 연속성, summary 길이, 그리고 모든 글의
`category` 가 실제로 존재하는 카테고리인지 검사한다.

카테고리와 frontmatter 의 `section` 은 층이 다르다. 카테고리는 강의 묶음이고 `section` 은 글
하나의 소주제다. 한 카테고리 안에 여러 `section` 이 들어간다.

### 아카이브

`order.json` 의 `archived` 에 넣은 글은 `/blog` 목록에서만 빠진다. 글 파일과 공개 URL 과 sitemap 은
그대로 둔다. 검색에 색인된 글을 실제로 내리면 유입이 죽고 되돌릴 수 없기 때문이다.

```json
{ "archived": [{ "slug": "no-install", "note": "목록에서 뺀 이유" }] }
```

모든 글 파일은 `posts` 또는 `archived` 중 정확히 한 곳에 있어야 한다. `check:blog` 가 양쪽에
동시에 있거나 어느 쪽에도 없는 경우를 막고, `note` 가 비면 실패시킨다. 왜 뺐는지 적지 않으면
나중에 되돌릴 근거가 사라진다.

커리큘럼을 다시 짤 때는 글을 지우지 않고 아카이브로 내린 뒤 새 순서로 다시 쓴 것부터 한 편씩
`posts` 에 올린다.

### 블로그 순서와 강의 참조 계약

`blog/order.json`은 `/blog`의 공개 읽기 순서만 관리한다. `/blog`에는 날짜나 별도 커리큘럼 소개를
표시하지 않고 `posts[].order` 순서로 글만 나열한다. 이 파일에는 강의 시간, 차시, 선수 단계, 학습
성과를 넣지 않는다. 공개 읽기 순서는 처음 방문한 사람이 목록을 훑기 좋은 편집 순서일 뿐 강의
시간표도 아니고 글의 선수 관계도 아니다.

검색으로 들어온 독자에게 앞 글을 먼저 읽으라고 요구하지 않는다. 필요한 개념은 현재 글에서 짧게
정의하고, 더 깊은 다른 글은 선택 참고 링크로만 둔다. 새 글을 발행하면 `order.json`에 slug를 정확히
한 번 넣고 1부터 빈 번호 없이 순서를 정한다. 파일 순번과 공개 읽기 순서는 서로 독립적이다.

강의 구성, 수업 시간, 슬라이드 순서, 실습 결과, 완료 기준은 비공개 `course/`에서 관리한다. 강의는
stage id가 아니라 안정적인 공개 slug `/blog/{slug}`를 참조한다. 강의 슬라이드 여러 장이 같은 블로그
URL을 참조할 수 있고, 슬라이드 한 장도 필요하면 여러 블로그 URL을 참조할 수 있다.

관계의 방향은 항상 `독립 블로그 원문 -> 강의 슬라이드의 요약과 참조 링크`다. 슬라이드는 수업 시간에
필요한 행동과 핵심 그림만 압축하고, 정의의 전체 설명, 원리, 전체 코드, 실패 사례, 추가 근거는 블로그
링크에서 읽게 한다. 교안이 짧아졌다고 블로그를 줄이지 않으며, 강의 순서가 바뀌었다고 블로그 제목과
본문 순서를 억지로 바꾸지 않는다.

새 글을 만들기 전에는 독자가 목록에서 발견하기 좋은 위치를 고른다. 중간에 새 주제가 필요하면
`order.json`의 order만 다시 정렬한다. 이미 발행한 파일 순번과 slug는 바꾸지 않는다.

글 본문에는 `지난편`, `다음편`, `이전 글`, `다음 글` 안내를 넣지 않는다. 각 글은 검색으로 바로
들어와도 자체 질문, 설명, 예제, 실패와 확인을 모두 끝낸다. 추가로 읽을 글은 본문을 이해하기 위한
필수 숙제가 아니라 선택 참고 자료로만 연결한다.

비공개 강의 교안은 Git에 넣지 않는다. 강의 슬라이드는 공개 blog slug를 참조 링크로 기록하고 링크가
실제 운영 URL에서 열리는지 확인한다. 교안 변경은 참조 링크와 슬라이드 요약의 정확성을 확인하는
작업이며, 독립 블로그 원문을 강의 분량에 맞춰 다시 자르는 작업이 아니다.

현장 강의의 분 단위 진행, 강사의 연결 질문, 개입 기준, 설치 실패 대체안, 수행평가 배점은 비공개
교안에 둔다. 공개 블로그에는 강의용 stage id를 만들지 않는다. 강의가 참조 대상을 찾는 키는 공개
slug다.

## 발행 파일 계약

발행 글은 `blog/<category-slug>/NNN-kebab.md` 한 파일이다. `NNN`은 저장소 전체에서 `001`부터 빈 번호 없이 증가하는 발행 순번이다.
한 번 발행한 순번은 공개 읽기 순서가 바뀌어도 고치지 않는다. 파일 stem 전체는 미디어 키용
**post id**다. 새 글은 현재 가장 큰 순번에 1을 더해 만든다. 공개 URL은 frontmatter `slug`만 쓴다
(`/blog/{slug}`). 날짜는 저장하거나 정렬에 사용하지 않는다.

순서는 두 가지뿐이다.

- 파일 순번: 저장소와 미디어에서 글을 구분하는 고정 번호
- `order.json`의 `order`: `/blog`에서 사용하는 공개 읽기 순서

새 글은 다음 파일 순번을 받고, 독자가 보는 위치는 `order.json`의 `order`로 정한다. 발행일과
수정일은 frontmatter, 구조화 데이터, sitemap, RSS에 넣지 않는다.
대문자 영문 운영 문서와 `product-marketing.md`는 사이트 글 목록에서 제외한다.

```yaml
---
title: 독자가 읽을 제목
slug: 공개-경로-kebab
author: 화면과 구조화 데이터에 함께 표시할 작성자
section: 글을 분류하는 한 개의 상위 주제
summary: 목록과 검색 결과에서 글을 열 이유를 설명하는 문장
readerQuestion: 이 글이 끝까지 답할 질문은 무엇인가?
readerTakeaway: 독자가 글을 덮고 기억할 한 문장
readerLevel: beginner, working, advanced 중 하나
readerStartingPoint: 독자가 이미 아는 것과 아직 모르는 것
primaryKeyword: 제목과 summary와 도입에 함께 쓸 두 단어 이상의 검색어
searchIntent: explanation, how-to, troubleshooting, comparison 중 하나
ogImage: 선택. 발행 전에는 media://asset-key, 발행 뒤에는 HF 객체 URL
ogImageAlt: ogImage가 있으면 필수. plan의 alt와 같은 설명
ogImageWidth: ogImage가 있으면 필수. 원본 픽셀 너비
ogImageHeight: ogImage가 있으면 필수. 원본 픽셀 높이
ogImageType: ogImage가 있으면 필수. image/png 같은 MIME
---
```

### 공개 slug 규칙

공개 URL은 `/blog/{slug}` 한 형태다. 업계 기본과 같다. 날짜를 경로에 넣지 않고, 여러 단어는
하이픈으로만 나눈다.

| 규칙 | 내용 |
|---|---|
| 문자 | 소문자 영문, 숫자, 하이픈만. 날짜로 시작 금지 |
| 길이 | 4자 이상 40자 이하. 보통 2~4 단어 |
| 뜻 | 제목 전체를 옮기지 말고, 독자가 주제를 바로 읽게 짧게 |
| 제품명 | 인지도가 약한 제품명을 slug 앞에 두지 않는다 |
| 고정 | 한 번 공개한 slug는 바꾸지 않는다. 바꾸면 Worker `LEGACY_BLOG`에 301을 남긴다 |

좋은 예: `no-install`, `ai-environment`.  
나쁜 예: `2026-08-09-codaro-guide`(날짜), `run-python-without-install`(제목 나열로 김),
`codaro_guide`(밑줄).

미디어 plan/catalog 키의 `post` 필드는 파일 stem(post id)을 유지한다. 공개 slug와 달라도 된다.

별도 지시가 없으면 `readerLevel`은 `beginner`로 잡는다. `readerStartingPoint`에는
`초보자`라고만 쓰지 않는다. `Python을 설치해 본 적이 없고 셀과 .py의 뜻을 모른다`처럼
독자가 모르는 말을 적는다. 글을 다 쓴 뒤에는 이 출발점을 넘어서는 설명이 빠지지 않았는지 확인한다.

`readerQuestion`과 `readerTakeaway`는 본문이 옆길로 새는지 확인할 때 쓴다. 답이 바뀌면
frontmatter와 본문을 함께 고친다.

## 1. 읽는 사람을 먼저 정한다

글을 쓰기 전에 아래 네 줄을 먼저 적는다.

- 독자는 지금 무엇을 하려는가
- 첫 화면에서 무엇을 모르는가
- 글을 읽고 처음으로 무엇을 누르거나 입력할 것인가
- 성공하면 화면에 무엇이 보여야 하는가

`Python 초보자`처럼 넓게 잡지 않는다. `Python을 설치하지 않았고 실행 버튼을 한 번도 눌러 보지
않은 사람`처럼 시작 위치가 보여야 한다. 글을 쓰는 동안 독자에게 그보다 많은 지식을 기대하면
설명을 추가하거나 내용을 뺀다.

## 1.5 유입 패키징 게이트

제목과 summary를 쓰기 전에 아래 세 문항을 모두 통과해야 한다. 하나라도 실패하면 제목을 고친다.
제품 이름보다 독자의 문제나 결과가 먼저 나와야 한다. 자세한 판단은
`skills/specs/operation/blogCopy.md`와 `blog/product-marketing.md`를 본다.

1. **브랜드 지움 테스트**: 제목에서 Codaro, xlpod, DartLab, pyproc, eddmpython 이름을 지워도
   검색 의이 남는가. 남는 것이 없으면 브랜드 사용법 제목이다.
2. **인지도 테스트**: `readerStartingPoint`에 그 제품 이름을 처음 본다고 적혀 있으면, 제목과
   summary가 제품 사용법을 전제하지 않아야 한다. 먼저 무엇을 할 수 있는지가 나와야 한다.
3. **결과 선행 테스트**: summary 첫 절이 제품명으로 시작하지 않고, 독자가 얻는 결과나 피하려는
   문제로 시작하는가.

통과한 뒤에만 `title`, `summary`, `readerQuestion`을 확정한다. 본문 초입에서 제품 이름은
문제를 말한 뒤 한두 문장으로 소개한다. `Codaro 사용법`처럼 인지도 없는 브랜드를 제목 앞에 두지
않는다.

## 2. 확인한 재료만 모은다

이 저장소에서 실제로 바뀐 코드, 실패한 검사, 되돌린 결정, 지금 보이는 제품 화면을 먼저 읽는다.
제품 기능과 숫자는 코드, 제품 저장소 또는 직접 실행한 결과에서 확인한다.

자료마다 글에 쓸 문장을 먼저 만들지 말고 아래 세 줄만 적는다.

- 독자가 보게 될 화면이나 파일
- 독자가 누르거나 바꿀 것
- 성공했을 때 나오는 결과

셋 중 하나를 확인하지 못한 기능은 단정해서 쓰지 않는다. 꼭 필요하면 출처를 링크하고, 확인할 수
없으면 본문에서 뺀다.

## 3. 독자가 움직이는 순서로 목차를 만든다

목차보다 먼저 깊이 설계표를 만든다. 독자의 질문, 직접 답, 반드시 풀 용어, 작동 이유, 완성 예제의
입력과 출력, 실패 사례, 반례나 한계, 검증 방법을 한 줄씩 적는다. 빈 줄이 있으면 H2를 만들지 말고
자료를 더 확인한다. 강의 차시 제목과 시간표를 깊이 설계표 대신 복사하지 않는다.

사용법 글은 제품 내부 구조가 아니라 독자의 손이 움직이는 순서로 쓴다.

1. 어디를 여는가
2. 무엇을 누르는가
3. 무엇을 입력하거나 바꾸는가
4. 성공하면 무엇이 보이는가
5. 실패하면 어디를 확인하는가
6. 다음 기능은 언제 필요한가

개념 글은 `겪는 문제 -> 왜 생기는가 -> 실제 예 -> 맞지 않는 경우 -> 지금 할 일` 순서로 쓴다.
H2만 읽어도 이 순서가 보여야 한다. `핵심 구조`, `실행 환경`, `확장 가능한 흐름`처럼
내용을 열어 봐야 뜻을 알 수 있는 H2는 쓰지 않는다.

H2는 같은 크기의 카드 여러 장이 아니다. 질문을 여는 짧은 절, 원리를 깊게 파는 중심 절, 실제 입력과
출력을 끝까지 따라가는 실습 절, 실패와 한계를 다루는 절의 길이가 서로 달라도 된다. 중심 주장은 여러
문단과 코드 및 표를 사용해 충분히 설명한다. 한 절을 이미지 뒤 첫 문단 두세 문장만 쓰고 끝내지 않는다.
절 마지막에는 지금 확인한 결과 때문에 다음 질문이 왜 생기는지 한 문장으로 잇는다. 이 연결 문장은
다른 블로그 글을 먼저 읽으라는 안내가 아니라 현재 글 안의 다음 H2로 사고를 이어 주는 문장이다.

### 예고는 이음이 아니다

연결 문장을 붙였다고 절이 이어진 것이 아니다. 2026-08-19 에 발행 001 번을 실측하고 이 항목을
추가했다. 그 글은 절마다 마지막 문장이 있었고 전부 다음 절을 가리키고 있었는데도 읽히지 않았다.
앞 여섯 절의 마지막 문장이 이랬다.

```text
브라우저 안의 칸도 같은 식으로 채워집니다.
바깥에서 숫자를 받아 오는 일도 됩니다.
이미 내 컴퓨터에 있는 표 파일도 같은 식으로 넘길 수 있습니다.
아직 없는 숫자를 이어서 그려 보기도 합니다.
지금 열 수 있는 제품 화면에도 이런 일이 있습니다.
화면이 여러 가지인 만큼, 그 화면을 만드는 도구도 여러 가지입니다.
```

여섯 문장이 전부 `다음에 이런 것도 나온다`고 알려 주기만 한다. 여섯 절의 자리를 어떻게 바꿔도
글이 성립했다. 이것은 이음이 아니라 목차다. 그 여섯 절이 글의 앞 46퍼센트였고 독자는 글의 절반을
예고만 읽었다.

이음인지 보는 방법은 하나다. **인접한 두 절의 자리를 바꿔 보고 글이 깨지는지 본다.** 깨지지 않으면
가짜다. 진짜 이음은 이 절에서 나온 결과 때문에 앞에 없던 모르는 것이 생기는 것이다.

절이 여러 장면이나 사례를 보여 주는 자리라면 특히 조심한다. **장면 수와 절 수는 다른 값이다.**
장면 다섯을 절 다섯으로 세우면 다섯 번 예고하게 된다. 장면을 종류로 묶어 절을 줄이고, 종류가
서로 다르다는 사실이 다음 절의 질문을 만들게 한다. 001 번은 다섯 장면을 화면 누르기, 있는 값
옮기기, 없는 값 만들기 셋으로 묶어 절 열셋을 열로 줄였고 예고 여섯이 0이 되었다.

### 절 사슬은 원장에 적고 글 파일에는 넣지 않는다

절 설계는 카테고리 폴더의 `원장.md` 에 표로 적는다. 판정 칸에는 `이어짐`, `예고`, `나열`, `끊김`
넷만 쓴다. 한 글에서 `예고` 와 `나열` 을 합쳐 셋을 넘으면 그 글은 카탈로그이므로 절을 접는다.

설계 메모를 글 파일 안에 두지 않는다. `site/src/posts.ts` 가
`import.meta.glob("../../blog/*/???-*.md", { query: "?raw" })` 로 글 파일 **원문 전체**를 공개 JS
번들에 문자열로 굽기 때문이다. frontmatter 도 본문도 예외가 아니다. `react-markdown` 은 `skipHtml`
기본값이 `false` 라 `<!-- 주석 -->` 을 지우지 않고 화면에 글자 그대로 찍는다. frontmatter 에 넣는
것도 막힌다. `check-blog.mjs` 의 파서가 `^([A-Za-z][A-Za-z0-9]*):\s*(.*)$` 한 줄 정규식이라 여러
줄 배열을 만나면 그 줄에서 실패한다.

원장과 본문이 어긋나는 것은 아래 명령이 잡는다. 게이트가 아니라 글을 고치는 동안 쓰는 도구다.

```text
python blog/scripts/outline.py                 원장과 본문 H2 를 대조한다
python blog/scripts/outline.py --chain          절 사슬을 한 화면에 편다
```

v1 계약 글의 각 H2는 `제목 -> 한 줄 부제 -> 이미지와 캡션 -> 쉬운 서술형 설명 -> 선택 보조자료`
순서를 지킨다. v2 계약 글은 부제와 이미지를 절마다 강제하지 않는다. 부제는 그 절이 H2만으로 부족할
때만 붙이고, 이미지는 문장으로 따라가기 어려운 장면에만 붙인다. 붙였다면 부제는 15자 이상 80자 이하로
적고 이미지에는 캡션을 단다. 어느 계약이든 절의 첫 블록은 코드나 목록이 아닌 60자 이상의 서술 문단이고
절 전체 설명은 120자를 넘는다. 보조자료는 없어도 되며, 넣는다면 실행 코드, 입력과 결과가 있는
예시, 설명용 목록이나 표만 쓴다. 다른 H2와 같은 이미지를 다시 쓰지 않는다. 앞 절에서 열지 않은
기능이나 용어를 다음 절이 당연히 아는 것처럼 시작하면 순서를 바꾼다.

코드 블록은 설명을 대신하지 않는다. 모든 코드 블록은 `#### 예시 코드: 금액 문자열을 숫자로 바꾸기`,
`#### 실행 명령: 프로젝트 전체 검사하기`, `#### 실패 예시: 없는 파일을 열었을 때`처럼 역할과 개념이
함께 보이는 H4 아래에 둔다. `#### 코드`, `#### 예시`처럼 무엇을 배우는지 알 수 없는 제목은 깊이
계약 글에서 금지한다.

v1 계약은 H4 역할어를 정해진 열한 개 어휘로 제한했다. 그 결과 발행 40편의 H4 590개가 예외 없이 그
어휘 안에서만 나왔다. v2 계약은 `역할: 설명` 형태만 요구하고 역할어는 글쓴이가 고른다. 다만 `코드`,
`예시`, `참고`, `내용`, `정리`, `설명`, `기타`, `자료`처럼 그 자체로 아무것도 알려 주지 않는 역할어는
계속 막고, 코드 블록이 붙은 H4 의 역할어에는 자료의 성격이 드러나야 한다.

**실패 예시는 실제로 발생시킨 출력만 쓴다.** 교정 전 006 번은 실패 사례를 전부 `~하면 ~됩니다` 가정법
으로 적었고 코드 블록 두 개 모두 본문이 직접 실행용이 아니라고 밝혔다. 그 글에서 실제로 돌린 코드는
0줄이었다. 기계는 라벨과 글자 수만 세므로 이 항목은 사람이 지킨다. 같은 H4 범위에 코드의 입력, 핵심 줄이 바꾸는 값, 실행 뒤 예상 결과를 합쳐
80자 이상 서술한다.

## 4. 쉬운 말로 쓰고 여덟 번 검토한다

첫 두 문단에는 독자가 겪는 문제와 이 글에서 처음 할 일을 쓴다. 제품 역사와 기능 목록은 뒤로
보낸다. 첫 문단에서 `가상환경`, `런타임`, `의존성` 같은 말을 여러 개 던지지 않는다.

설명은 이름, 동작, 보이는 결과 순서로 쓴다. 예를 들어 `격리된 런타임을 제공합니다`라고 끝내지
않는다. `다른 프로젝트와 섞이지 않는 Python 실행 공간을 만듭니다. 이 공간을 가상환경이라고
부릅니다`처럼 독자가 아는 말로 동작을 먼저 보여 준다.

문장은 다음 기준으로 고친다.

- 한 문장에는 한 가지 사실만 둔다
- 문단 길이를 고르게 맞추지 않는다. 한 문장짜리 문단과 여러 문장짜리 문단을 섞는다
- 어려운 말은 처음 나오는 자리에서 뜻을 바로 쓴다
- `셀은 코드를 입력하고 실행하는 칸입니다`처럼 먼저 쉬운 말을 쓰고 이름을 붙인다
- `기능을 확장합니다` 대신 `CSV를 읽고 새 파일로 저장합니다`처럼 실제 행동을 쓴다
- `효율적으로 검증합니다` 대신 어떤 값을 넣고 어떤 결과를 확인하는지 쓴다
- 링크를 누르면 어느 화면이 열리는지 링크 앞에서 알려 준다
- 절 마지막에는 다음 절이 왜 필요한지 한 문장으로 연결한다

### 추상어를 실제 예로 바꾼다

`환경`, `구조`, `흐름`, `경계`, `맥락`, `과정`, `방식`, `역할`, `가치`, `기반`, `가능성`, `판단`은
그 자체로 설명이 아니다. 같은 문단에 파일, 화면, 버튼, 명령, 값, 오류 중 하나를 넣고 무엇이 실제로
달라지는지 쓴다. 넣을 수 없다면 문장을 지운다.

비유는 사실을 설명한 뒤 기억을 돕는 한 문장만 허용한다. `작업장`, `갈림길`, `여정` 같은 비유를
이어 붙여 기능이나 절차를 설명하지 않는다. `이를 통해`, `이러한 방식`, `단순히 무엇을 넘어`,
`혁신적인 흐름`처럼 내용 없이 문장을 크게 만드는 표현도 쓰지 않는다.

초안을 고칠 때 각 문장을 확인한 사실, 독자가 할 행동, 독자가 볼 결과, 꼭 필요한 연결 설명 중 하나로
분류한다. 어느 쪽도 아니면 삭제한다. 구체적인 교정 예와 실행 순서는 저장소 스킬
`.agents/skills/blog-writing/SKILL.md`에 있다.

`beginner` 글은 기계 검사도 통과해야 한다. H2는 32자를 넘기지 않고, 일반 문단은 220자,
한 문장은 160자를 넘기지 않는다. 이 숫자를 맞췄다고 글이 쉬워지는 것은 아니지만 긴 문장이
그대로 발행되는 일은 막을 수 있다.

초안은 아래 순서로 여덟 번 읽는다. 한 사람이 한 번에 모두 통과시켰다고 처리하지 않고, 각 관점의
실패 이유를 따로 적은 뒤 고친다.

1. 사실 확인: 기능과 숫자가 코드나 실행 결과와 맞는지 본다.
2. 독립성 확인: 다른 글이나 강의 슬라이드를 보지 않아도 질문과 용어를 이해할 수 있는지 본다.
3. 깊이 확인: 정의, 원리, 완성 예제, 실패, 반례나 한계, 검증이 실제 문장으로 있는지 본다.
4. 초보자 확인: 처음 보는 말을 표시하고 그 자리에서 풀었는지 본다.
5. 연결 확인: 각 절의 마지막 결과가 다음 절의 질문을 자연스럽게 만드는지 본다.
6. 소리 내어 읽기: 숨이 차는 문장, 같은 뜻을 반복하는 문장, 홍보 문장을 지운다.
7. 유입 패키징 확인: 1.5절 세 문항을 제목, summary, 첫 두 문단에 다시 적용한다.
8. 구체성 확인: 각 H2에 파일, 화면, 버튼, 명령, 값, 오류 중 하나가 실제 예로 있는지 본다.

깊이 확인은 H2 개수와 글자 수만 세고 끝내지 않는다. 독자가 완성 예제의 입력을 바꾸었을 때 출력이
왜 달라지는지 설명할 수 있는지, 실패 예제를 정상 상태로 되돌릴 수 있는지, 결과가 맞다는 증거를 직접
찾을 수 있는지를 평가한다. 셋 중 하나라도 할 수 없으면 본문을 보강한다.

제품을 직접 실행해야 이해되는 글은 정적 코드 블록에서 멈추지 않는다. Codaro 입문 예제는
`blog/embeds/codaro-cells.json`에 제목, 설명, 실행 코드, 전체 Web Run URL을 등록하고 본문에 아래
주소를 다른 내용 없는 한 줄로 둔다.

```text
https://eddmpython.com/codaro/run/?example=<example-id>
```

사이트는 이 줄을 브라우저에서 실행할 수 있는 코드 입력칸으로 바꾼다. 블로그 안에서는 코드를
바꾸고 결과를 보는 기능만 제공한다. 답 검사, 학습 기록 저장, 다음 레슨 이동은 셀 아래의 전체
Web Run 링크에서 사용할 수 있다고 정확히 쓴다.

마지막 H2에는 독자가 지금 열 링크, 누를 버튼 또는 실행할 명령을 적는다. `이제 시작해 보세요`처럼
행동이 보이지 않는 문장으로 끝내지 않는다.

섹션 이미지는 설명을 대신하지 않는다. 이미지 뒤에는 120자 이상의 실질적인 설명을 두고, 장면이
무엇을 뜻하는지 실제 파일, 코드, 숫자, 실패 사례 중 하나와 연결한다. 캡션은 보이는 물체를 되풀이하지
않고 그 장면을 본문에서 어떻게 읽어야 하는지 한 문장으로 말한다.

## 5. 이미지를 기획한다

이미지는 글을 꾸미기 위해 넣지 않는다. 설명만으로 공간, 장면, 물성, 전후 차이를 따라가기 어려울 때
사용한다. 각 이미지는 어느 문단 뒤에서 무엇을 이해시키는지 먼저 정한다.

이미지 의미의 정본은 `blog/media/plan.json`이다. plan은 `version: 2`,
`promptContract: section-grounded-v2`를 쓴다. 키는 `<post id>/<assetKey>`이고 아래 필드를 가진다.
post id는 파일 stem이며 공개 URL slug와 다를 수 있다.

```json
{
  "20260808-example/hero": {
    "post": "20260808-example",
    "assetKey": "hero",
    "role": "section",
    "sectionHeading": "이 이미지가 바로 뒤따르는 H2 원문",
    "sectionSubtitle": "본문 H3와 같은 한 줄 부제",
    "contentAnchor": "이미지가 설명할 본문의 실제 문장",
    "visualSubject": "화면, 파일, 코드, 명령, 결과처럼 눈으로 확인할 대상",
    "visualRelationship": "대상의 전후, 원인과 결과, 순서",
    "visualProfile": "eddmpython-dark-v2",
    "palettePolicy": "eddmpython-carbon-ivory-sand-v1",
    "alt": "이미지를 보지 못해도 내용을 이해할 수 있는 설명",
    "placement": "H3 부제 바로 뒤",
    "narrativeUse": "독자가 글의 문제 장면을 한눈에 이해한다",
    "sourcePolicy": "auto",
    "sourceKind": "imagegen",
    "prompt": "구도, 재질, 조명처럼 의미를 바꾸지 않는 장면 지시"
  }
}
```

`role`은 공유 대표 이미지 `hero`, 각 H2의 첫 이미지 `section`, 추가 설명 이미지 `support` 중
하나다. v1 계약 글은 모든 H2에 고유한 `section` 이미지가 하나 필요하다. v2 계약 글은 본문 이미지가
3장 이하이며 이미지 없는 절을 허용한다. H2 마다 이미지를 요구하던 규칙이 절 개수의 상한까지 정하고
있었기 때문이다. 서로 다른 H2가 같은 이미지를 다시 쓰는 것은 어느 계약에서도 막는다.
`sectionHeading`은 본문 H2 원문과 정확히 같아야 하고, 부제를 쓴 절이라면 `sectionSubtitle`도
H3 원문과 같아야 한다. 부제가 없는 절에서는 `sectionSubtitle`을 적지 않고 `placement`에
`H2 제목 바로 뒤`를 적는다. `contentAnchor`도 해당 절의 설명에
실제로 있는 문장이어야 한다. 대표 이미지가 특정 H2의 의미 장면과 맞으면 `section` 이미지 하나를
OG에도 함께 써도 된다.

### eddmpython 생성 이미지 색상 계약

DartLab 카드뉴스에서 가져오는 핵심은 이미지에 문장을 구워 넣는 형식이 아니다. 큰 문장은 HTML과
마크다운이 맡고, 이미지는 그 문장이 말하는 의미 장면만 맡는다. 새로 만들거나 교체하는 생성 이미지는
`visualProfile: eddmpython-dark-v2`와 `palettePolicy: eddmpython-carbon-ivory-sand-v1`을 쓴다.
`dark-editorial-v1`은 기존 자산을 찾기 위한 이전 값이며 새 작업에 선택하지 않는다.

- 본문 폭에 맞는 3:2 가로형을 기본으로 하고 ImageGen은 1536 x 1024를 우선한다
- 배경과 가장 큰 면은 carbon `#101514`를 쓴다
- 주요 피사체와 밝은 면은 ivory `#f5f3ee`를 쓴다
- 강조색은 sand `#d8be91` 하나만 작은 면적에 쓴다
- 나머지는 검정, 흑연, 웜그레이처럼 채도가 거의 없는 중성색만 쓴다
- 파랑, 청록, 초록, 보라, 분홍, 빨강, 금색, 네온색은 성공과 실패 표시에도 쓰지 않는다
- 성공, 실패, 선택, 경로는 색을 늘리지 않고 모양, 선 굵기, 명암, 위치 차이로 구분한다
- 글자, 숫자, 코드, 로고, 가짜 제품 화면을 이미지 바이트에 넣지 않는다
- 평면 인포그래픽과 장식 배경 대신 공간, 물성, 전후 차이, 작동 경로가 보이는 한 장면을 만든다
- 같은 구도와 소품을 반복하지 않고 해당 H2의 주장 하나만 시각화한다
- 프롬프트의 자유 장면 지시가 색상 계약과 충돌하면 색상 계약이 이긴다

텍스트를 이미지 밖에 두면 모바일에서도 선명하고, 오탈자를 이미지 전체 재생성 없이 고칠 수 있으며,
검색과 접근성 도구도 제목과 캡션을 읽을 수 있다. 이것이 카드뉴스의 읽힘을 블로그에 맞게 옮기는
부분이다.

실제 제품 화면은 `sourceKind: screenshot`, `visualProfile: product-screen-v1`으로 두고 원본
`sourceUrl`과 재현할 `captureState`를 적는다. 실제 화면은 기능을 사실대로 보여 주기 위해 원래 색을
보존하며 생성 이미지 팔레트로 강제로 다시 칠하지 않는다.
화면이 움직이는 녹화는 `sourceKind: recording`, `visualProfile: source-original-v1`으로 두고
`captureState`와 `credit`을 적는다. 작업본은 저장소 밖 staging의 `.mp4`이며 Git에 넣지 않는다.
본문에는 이미지와 같은 `![대체 텍스트](media://asset-key "캡션")` 자리를 쓰고, 사이트는 이 주소를
재생 컨트롤이 있는 영상으로 렌더한다. 로그인, 비밀번호, 신청자 이름, 주민번호가 보이는 녹화는
올리지 않는다. 영상은 ogImage로 쓰지 않는다.
인물, 행사, 장소처럼 모양이 사실과 맞아야 하는 이미지는 공식 자료나 사용 가능한 라이선스 이미지를
쓴다. 이때 `sourceKind`는 `official` 또는 `licensed`, `visualProfile`은 `source-original-v1`이고
`sourceUrl`, `credit`, `licensed` 이미지에는 `license`를 함께 기록한다.

개념 장면, 전후 차이, 아직 사진으로 존재하지 않는 설명용 장면은 Codex의 기본 `image_gen` 도구로
만들 수 있다. 제품 화면, 코드 내용, 실제 문서 모양이 중요하면 생성 이미지로 흉내 내지 않고 확인된
화면이나 공식 자료를 쓴다. 생성 전 해당 절의 서술 문단을 먼저 쓴 뒤 plan에 `contentAnchor`,
`visualSubject`, `visualRelationship`을 적는다. `generate_flux.py`는 이 값을 자유 장면 프롬프트보다
높은 우선순위로 붙인다.

생성본은 실제 픽셀을 눈으로 확인한다. `visualSubject`가 보이는지, `visualRelationship`을 캡션 없이도
읽을 수 있는지, 다른 H2 이미지와 바꿨을 때 바로 어색한지 본다. 공방, 길, 문, 기계 같은 범용 비유가
본문의 실제 파일, 화면, 결과를 밀어내면 다시 만든다. 통과한 파일만 `--reviewed`로 발행한다.

ImageGen 결과는 기본 생성 경로에만 남겨 두지 않는다. 최종 선택본을 다음 저장소 밖 경로로 옮긴다.

```text
../eddmpython.out/blog-media/<post id>/<assetKey>.webp
```

PNG, JPG, GIF도 지원하지만 새 래스터는 용량과 품질을 확인한 WebP를 우선한다. Git 저장소의
`blog/` 아래에는 SVG를 포함한 이미지 파일을 두지 않는다.

## 6. Hugging Face에 발행한다

이미지 바이트의 정본은 공개 Hugging Face 데이터셋 `eddmpython/eddmpython-media`다. Git에는
의미 계약인 `blog/media/plan.json`과 저장 계약인 `blog/media/catalog.json`만 남긴다.

본문에는 먼저 자리표시자를 둔다.

```markdown
![대체 텍스트](media://hero "독자에게 보이는 선택 캡션")
```

같은 이미지를 공유 카드에도 쓰려면 frontmatter에 `ogImage: media://hero`를 추가한다. 업로더가
plan의 대체 텍스트와 실제 이미지의 너비, 높이, MIME을 frontmatter에 함께 기록한다. 발행 전 준비는
한 번만 한다.

```bash
python -m pip install -r blog/requirements.txt
```

HF 데이터셋을 처음 만들 때만 `--create-repo`를 붙인다.

```bash
python -X utf8 blog/scripts/publish_media.py --asset 20260808-example/hero --create-repo --reviewed
```

이후에는 `--create-repo` 없이 같은 명령을 쓴다. 스크립트는 다음 순서를 바꾸지 않는다.

1. plan과 저장소 밖 작업본을 검증한다.
2. 파일 바이트의 SHA-256을 계산한다.
3. `objects/sha256/<앞 두 글자>/<전체 해시>.<확장자>`에 올린다.
4. 원격 객체가 실제로 존재하는지 다시 확인한다.
5. catalog에 바이트 수, MIME, 너비, 높이를 기록하고 본문의 `media://`를 HF URL로 바꾼다.
6. 교체 뒤 어떤 asset도 가리키지 않는 예전 객체 레코드를 catalog에서 정리한다.
7. 성공한 로컬 작업본과 빈 staging 폴더를 삭제한다.

업로드나 원격 확인이 실패하면 본문과 catalog를 바꾸지 않는다. 발행 스크립트는 이미 설정된 셸
환경변수를 먼저 쓰고, 없으면 eddmpython 루트 `.env`, 형제 DartLab `.env` 순서로 필요한 값을 읽는다.
`HF_TOKEN`은 이 로컬 저장소에만 두고 Git, 문서, 로그에 값을 남기지 않는다.

## 7. 발행한다

사이트 디렉터리에서 다음 순서로 확인한다.

```bash
npm run check:post -- 001-what-is-python.md
npm run check:blog
npm run verify:media
npm test
npm run build
npm run verify:visual
npm run approve:visual -- --run=<run-id>
npm run deploy
```

### 게이트를 두 개로 나눈 이유

예전에는 한 편을 고칠 때마다 `check:blog` 가 40편을 전부 다시 쟀다. 그래서 규칙 하나를 넣으려면 기존
40편이 모두 통과해야 했고, 통과시키려고 `v1` 과 `v2` 같은 계약 버전을 만들어 붙였다. 그 복잡함은 전부
게이트가 전역이라서 생긴 것이었다. 지금은 두 개로 나눈다.

**`npm run check:post -- <파일명>`** 은 그 한 편만 본다. 글을 쓰는 동안 도는 게이트다. 문장 단위 추상
검사, 서술 문단 줄바꿈, 절의 제목과 부제와 이미지 순서, H4 보조자료 라벨, 코드 앞뒤 설명 길이,
`sectionHeading` 과 `contentAnchor` 가 본문과 같은지를 검사한다.

**`npm run check:blog`** 는 여러 글 사이의 관계만 본다. 파일 순번, slug 중복, `order.json` 정합,
미디어 catalog 의 참조 무결성, SHA-256 경로, `blog/` 아래 로컬 이미지 차단, em dash, 명령형 뒤 마침표를
검사한다. 한 편의 문장 품질은 여기서 재지 않는다.

핵심어는 제목과 summary 와 H2 하나에만 요구한다. 도입 두 문단에도 핵심어 전체를 넣게 하던 규칙은
뺐다. 그 규칙이 발행 40편 중 29편의 첫 문장을 `핵심어 + 을 또는 를` 로 시작하게 만들었다.

기계 검사는 글맛과 주제와 기승전결을 판정하지 못한다. 세기 시작하면 세기 좋은 글이 나온다. 게이트는
깨지면 비용이 드는 것만 막고, 글이 좋은지는 사람이나 새 컨텍스트의 독자가 읽어서 정한다.

`verify:visual`은 sitemap의 모든 페이지를 데스크톱과 모바일
폭으로 렌더하고 가로 넘침, 깨진 이미지, 브라우저 오류, H2와 이미지 수를 검사한다. 저장소 밖에 생성된
두 화면 폭의 전체 스크린샷을 직접 읽고 제목 줄바꿈, 본문 폭, 이미지 크기와 캡션, 표와 코드의 가로
넘침을 확인한 뒤 해당 run id를 승인한다. 승인 뒤 빌드가 바뀌면 `deploy`는 중단된다.

배포 뒤에는 캐시버스터를 붙인 실제 글 URL을 다시 읽는다. 모든 H2의 고유한 이미지가 렌더됐는지,
`og:image`와 `twitter:image`가 plan과 catalog에서 정한 Hugging Face 객체인지 확인한다. `/blog`,
`rss.xml`, `sitemap.xml`의 반영과 홈, favicon, 404, `xlpod.eddmpython.com`의 상태도 확인한다. Git push,
HF 업로드, 빌드 통과는 각각 중간 단계이며 이 실사이트 확인 전에는 발행이 끝난 것이 아니다.

발행 후에는 다음 글을 늘이기보다 이 글의 질문과 답이 실제 화면에서도 선명한지 먼저 본다.
