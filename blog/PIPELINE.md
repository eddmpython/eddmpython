# eddmpython 블로그 파이프라인

이 문서는 블로그 제작과 발행의 정본이다. DartLab의 작가 파이프라인에서 독자 질문, 핵심 답,
검증과 편집의 분리, 발행 게이트를 가져왔다. 점수표와 역할 수는 복제하지 않고 이 저장소의
글 수와 운영 규모에 맞게 줄였다.

## 글의 계약

한 편은 다음 다섯 가지를 만족해야 한다.

1. 처음부터 끝까지 독자 질문 하나에 답한다.
2. 글을 덮은 뒤 되뇔 수 있는 답 한 문장을 남긴다.
3. 저장소에서 확인한 사실과 필자의 해석을 구분한다.
4. 처음 온 독자가 용어보다 장면과 예시를 먼저 만난다.
5. 다음 작업에서 다시 써먹을 판단 기준으로 끝난다.

분량은 목표가 아니다. 질문에 답하는 데 필요한 장면, 원인, 반례가 빠지지 않았는지를 본다.
목차를 채우기 위한 문단과 이미 아는 말을 늘인 문단은 길어도 삭제한다.

## 발행 파일 계약

발행 글은 `blog/YYYY-MM-DD-slug.md` 한 파일이다. 대문자 영문 운영 문서는 사이트 글 목록에서
제외한다. frontmatter에는 다섯 필드를 둔다.

```yaml
---
title: 독자가 읽을 제목
date: YYYY-MM-DD
summary: 목록과 검색 결과에서 글을 열 이유를 설명하는 문장
readerQuestion: 이 글이 끝까지 답할 질문은 무엇인가?
readerTakeaway: 독자가 글을 덮고 기억할 한 문장
---
```

`readerQuestion`과 `readerTakeaway`는 제작 메모가 아니라 글의 공개 계약이다. 본문이 다른
질문으로 새거나 답이 바뀌면 frontmatter와 본문을 함께 고친다.

## 1. 재료를 찾는다

유행하는 주제부터 고르지 않는다. 이 저장소에서 실제로 바뀐 코드, 실패한 검증, 되돌린 결정,
새로 세운 경계를 먼저 읽는다. 자료를 모을 때 아래 세 줄을 적을 수 있어야 한다.

- 독자가 겪는 구체적인 장면
- 상식과 다르거나 쉽게 놓치는 지점
- 저장소 파일이나 실행 결과로 확인할 수 있는 근거

셋 중 하나가 비면 집필하지 않는다. 특히 제품 기능과 숫자는 코드, 제품 저장소, 실행 결과에서
확인한다. 확인하지 않은 외부 사실은 링크로 출처를 분리하거나 본문에서 뺀다.

## 2. 관통선을 정한다

초안을 쓰기 전에 독자 질문과 답을 한 문장씩 정한다. 좋은 질문은 제목 없이 보여 줘도 읽고
싶고, 좋은 답은 일반론을 반복하지 않으며 다른 저장소에서도 판단 기준으로 쓸 수 있다.

그다음 H2만 먼저 배열한다. 각 H2는 다음 네 역할 중 하나를 맡는다.

- 궁금증을 더 구체적으로 만든다.
- 원인이 작동하는 장면을 보여 준다.
- 그 설명이 틀릴 수 있는 조건을 드러낸다.
- 독자가 바로 적용할 기준으로 닫는다.

어느 역할도 하지 않는 H2는 합치거나 지운다. 표와 목록은 비교가 쉬워질 때만 쓰고, 본문의
척추는 문장으로 이어 간다.

## 3. 네 번에 나눠 쓴다

한 번에 완성하려 하지 않고 같은 초안을 네 관점으로 순서대로 읽는다.

1. 사실 검토자는 강한 주장마다 읽은 파일과 실행 결과가 있는지 확인한다.
2. 회의론자는 그럴듯한 AI 일반론, 과장된 인과, 제품 홍보 문장을 공격한다.
3. 독자 대리인은 첫 두 문단에서 읽을 이유가 생기는지, 용어를 몰라도 따라가는지 본다.
4. 편집자는 장면, 설명, 반전, 판단의 순서와 문단 사이의 다리를 다듬는다.

이것은 반드시 네 명의 작업자를 뜻하지 않는다. 한 사람이 써도 검토 관점을 섞지 않고 순차로
통과시킨다. 사실을 고치는 일과 문장을 매끄럽게 하는 일을 동시에 하면 틀린 문장이 더 그럴듯해진다.

## 4. 읽히는 글로 고친다

첫 두 문단은 배경 설명이 아니라 독자가 겪는 장면과 질문으로 시작한다. 어려운 용어는 처음
나오는 문장에서 일상어로 풀고, 바로 코드, 파일, 명령, 화면 중 하나를 붙인다.

각 H2를 따로 읽었을 때도 앞 절의 결과를 이어받아야 한다. 절 끝에는 다음 절이 필요한 이유를
한 문장으로 놓는다. `핵심`, `구조`, `맥락`, `효율적` 같은 추상어만 남은 문장은 누가 무엇을
보고 어떻게 판단하는지까지 다시 쓴다.

마지막 H2는 요약 목록으로 끝내지 않는다. 조건이 달라질 때 무엇을 확인하고 기존 판단을 언제
버려야 하는지 2개 이상 보여 준다.

## 5. 발행한다

사이트 디렉터리에서 다음 순서로 확인한다.

```bash
npm run check:blog
npm test
npm run build
```

`check:blog`는 파일명, frontmatter, 날짜, 질문과 답, 최소 본문 구조, 미완성 표식, 금지 문자를
검사한다. 기계 검사는 글맛을 판정하지 않는다. 통과 뒤 `/blog`와 글 상세 화면을 데스크톱과
모바일 폭에서 직접 읽고, 제목 줄바꿈, 본문 폭, 표와 코드의 가로 넘침을 확인한다.

발행 후에는 다음 글을 늘이기보다 이 글의 질문과 답이 실제 화면에서도 선명한지 먼저 본다.
