Claude Code에 작은 수정을 부탁했는데 예상보다 많은 파일이 바뀔 때가 있습니다. 서브에이전트가
여러 개 생기고, 확인 보고는 길어졌는데 정작 필요한 기능은 어긋나기도 합니다. 이런 일을 한 번
겪으면 새 모델이 나빠졌다고 생각하기 쉽습니다. 그러나 결과만 보고 모델을 원인으로 지목하면
설정과 작업 방식에서 생긴 문제를 놓치게 됩니다.

이 글은 Claude Code 에이전트가 일을 지나치게 벌이는 상황을 재현 가능한 문제로 바꾸는 방법을
다룹니다. 먼저 무엇이 달라졌는지 기록하고, 모델과 설정을 분리해 비교합니다.

그다음 메인 세션, 서브에이전트, 에이전트 팀, 작업 트리를 언제 써야 하는지 고릅니다. 마지막에는
작은 설정 파일과 검증 프롬프트를 직접 적용합니다. 특정 모델을 칭찬하거나 비난하는 글이 아니라,
모델이 바뀌어도 계속 쓸 수 있는 문제 해결 절차입니다.

## Claude Code 에이전트 문제를 기록합니다

### 요청, 변경 범위, 실행 시간, 검증 결과를 한 줄에 놓으면 무엇이 이상한지 보입니다

![한 장의 작업 요청 옆에 변경 파일과 실행 시간과 테스트 결과가 나란히 기록된 점검대](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/62/62488340e5e810505fece29f7132248140d532aba3d498f37c6c212a1afd5a57.png "에이전트의 말보다 요청과 변경 파일과 테스트 결과를 함께 놓은 기록이 원인을 찾는 출발점입니다")

"에이전트가 삽질한다"는 말에는 서로 다른 문제가 섞여 있습니다. 파일을 너무 많이 바꾸는 것은
범위 문제이고, 실행 시간이 길어진 것은 비용과 작업 분해 문제입니다. 보고가 긴 것은 출력 형식
문제이며, 테스트가 실패한 것은 정확성 문제입니다. 네 가지를 한 문장으로 묶으면 무엇을 고쳐야
할지 알 수 없습니다.

예를 들어 `invoice.py`의 날짜 형식 하나를 고치는 작업을 맡겼다고 가정해 보겠습니다. 결과가
마음에 들지 않았다면 아래 항목을 따로 기록합니다.

| 확인할 것 | 기록할 내용 | 알 수 있는 문제 |
|---|---|---|
| 요청 | 바꾸라고 한 파일과 완료 조건 | 처음부터 범위가 모호했는지 |
| 변경 | 실제로 수정된 파일과 줄 수 | 요청 밖으로 작업이 번졌는지 |
| 과정 | 사용한 턴, 시간, 서브에이전트 수 | 병렬화가 도움이 됐는지 |
| 검증 | 실행한 명령과 종료 코드 | 완료라는 보고가 사실인지 |
| 결과 | 사용자가 직접 확인한 동작 | 테스트가 놓친 문제가 있는지 |

핵심은 관찰과 해석을 분리하는 것입니다. "모델이 과도하게 자율적이다"는 해석입니다. "요청은
한 파일이었는데 네 파일이 수정됐다"는 관찰입니다. 관찰부터 쌓아야 모델, 프로젝트 규칙, 사용자
설정 가운데 무엇이 원인인지 비교할 수 있습니다.

#### 예시 코드: 작업 기록을 비교 가능한 양식으로 남기기

아래 양식은 특별한 도구가 없어도 쓸 수 있습니다. `git diff --stat`은 바뀐 파일과 줄 수를
보여 주고, 테스트 명령의 종료 코드는 성공이면 보통 `0`, 실패면 그 밖의 숫자를 반환합니다.
에이전트의 설명을 복사하는 대신 사용자가 확인한 값을 적는 것이 중요합니다.

```text
요청: invoice.py의 날짜를 YYYY-MM-DD 형식으로 저장
완료 조건: 기존 테스트와 date_format 테스트 통과
변경 파일: invoice.py, tests/test_invoice.py
요청 밖 변경: 없음
서브에이전트: 0개
검증 명령: uv run pytest tests/test_invoice.py
종료 코드: 0
직접 확인: sample.xlsx의 날짜 열이 2026-08-15로 저장됨
```

이 기록이 두세 개만 있어도 막연한 불만이 패턴으로 바뀝니다. 같은 설정에서 작은 작업만 계속
번진다면 지시 범위를 먼저 봐야 합니다. 서브에이전트를 켠 작업만 느리다면 병렬 구조를 확인해야
합니다. 모델을 바꾼 직후에만 결과가 달라졌다면 그때 모델 변경을 원인 후보로 올릴 수 있습니다.

## 모델과 설정을 한 번에 하나씩 나눠 비교합니다

### 같은 요청과 같은 저장소에서 한 조건만 바꿔야 원인을 구분할 수 있습니다

![같은 작업 카드에서 모델과 설정 스위치를 하나씩 바꾸며 결과를 비교하는 실험대](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/a7/a71bf2cf89fe14614d4d1cba9f1d1a2c1dd073e461994a714cfb6c8ad46d530d.png "모델과 설정을 동시에 바꾸지 않고 스위치 하나씩 시험해야 결과 차이의 원인을 구분할 수 있습니다")

모델을 바꾸면서 프롬프트와 에이전트 설정까지 함께 고치면 결과가 좋아져도 이유를 알 수 없습니다.
문제 해결에서는 조건을 고정한 작은 비교가 필요합니다. 복잡한 제품 기능 전체를 시험 대상으로
잡을 필요도 없습니다. 실패가 잘 드러나는 10분짜리 작업 하나면 충분합니다.

먼저 기준 실행을 만듭니다. 같은 커밋에서 시작하고, 같은 요청을 사용하며, 같은 테스트 명령으로
판정합니다. 그런 다음 한 번은 모델만 바꾸고, 다음에는 모델을 원래대로 둔 채 에이전트 설정만
바꿉니다. 실행마다 새 대화를 사용해야 앞선 대화의 지시와 파일 읽기 기록이 섞이지 않습니다.

| 비교 | 고정하는 것 | 바꾸는 것 | 확인할 질문 |
|---|---|---|---|
| A와 B | 저장소, 요청, 설정, 테스트 | 모델 | 모델에 따라 변경 범위가 달라지는가 |
| A와 C | 저장소, 요청, 모델, 테스트 | 에이전트 설정 | 서브에이전트 수가 원인인가 |
| A와 D | 저장소, 모델, 설정, 테스트 | 요청 문장 | 완료 조건이 모호했던 것인가 |

비교 결과는 좋다와 나쁘다가 아니라 숫자와 사실로 남깁니다. 수정 파일 수, 테스트 성공 여부,
걸린 시간, 사용자가 되돌린 줄 수 정도면 충분합니다. 토큰 사용량을 볼 수 있다면 함께 기록하되,
토큰이 많다는 이유만으로 실패라고 판단하지는 않습니다. 어려운 조사에는 많은 토큰이 필요할 수
있기 때문입니다.

#### 예시 코드: 실험 조건을 YAML로 고정하기

실험 기록은 저장소 밖 메모에 두어도 됩니다. 팀이 같은 문제를 반복해서 확인한다면 아래처럼
작은 YAML 파일로 남기면 누가 실행해도 조건이 달라지지 않습니다. 여기서 `expected_files`는
허용 목록이지 에이전트에게 반드시 두 파일을 고치라는 뜻이 아닙니다.

```yaml
task: invoice-date-format
start_commit: 2d6f9ac
prompt_file: experiments/invoice-date-prompt.txt
expected_files:
  - invoice.py
  - tests/test_invoice.py
test_command: uv run pytest tests/test_invoice.py
record:
  changed_files: []
  elapsed_minutes: 0
  test_exit_code: null
  reverted_lines: 0
```

이렇게 해 두면 "지난번보다 별로다"가 아니라 "같은 요청에서 수정 파일이 2개에서 7개로
늘었다"고 말할 수 있습니다. 원인을 고칠 수 있는 문장은 두 번째 문장입니다.

## Opus 5와 Fable 5의 차이를 정확히 읽습니다

### 이름의 서열보다 작업 성격, 비용, 보존 정책, 생각 설정을 함께 봐야 합니다

![서로 다른 규격표가 붙은 두 작업 기계 앞에서 작업 카드를 맞는 투입구에 놓는 장면](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/2f/2f55c0f761b8e573e94f0a197cbbe8afad5ff4bf918a29825470d704b0a7608a.png "가장 비싼 기계 하나로 모든 일을 처리하지 않고 작업 성격과 운영 조건을 보고 모델을 고릅니다")

Anthropic의 [모델 개요](https://platform.claude.com/docs/en/about-claude/models/overview)는
Opus 5를 복잡한 에이전트 코딩과 기업 작업에 권장하고, Fable 5를 가장 높은 능력이 필요한 작업의
선택지로 설명합니다.

이것은 Fable 5가 모든 작업에서 자동으로 더 낫다는 뜻이 아닙니다. 작은 파일 수정은 비용이 낮고
반응이 빠른 선택이 더 실용적일 수 있습니다.

Fable 5의 중요한 차이는 [공식 소개](https://platform.claude.com/docs/en/about-claude/models/introducing-claude-fable-5-and-claude-mythos-5)와
[마이그레이션 가이드](https://platform.claude.com/docs/en/about-claude/models/migration-guide)에
정리되어 있습니다. 컨텍스트 창은 100만 토큰이고 최대 출력은 12만 8천 토큰입니다.

입력 100만 토큰당 10달러, 출력 100만 토큰당 50달러이며 30일 보존이 필요합니다. 조직이 제로
데이터 보존을 요구한다면 성능과 상관없이 선택할 수 없는 모델입니다.

또한 Fable 5는 적응형 생각이 항상 켜져 있습니다. 원문 사고 과정은 반환하지 않지만, 이것을
사용자가 생각 깊이를 전혀 조절할 수 없다는 뜻으로 해석하면 안 됩니다.

API의 `effort` 값으로 계산 강도를 조절할 수 있고, 기본적으로 높은 수준에서 시작하며 가장 어려운
작업에는 `xhigh`를 검토할 수 있습니다. 원문 생각을 볼 수 없다는 사실과 생각에 쓰는 자원을
조절할 수 있다는 사실은 동시에 성립합니다.

모델 변경 뒤 행동이 달라졌다면 해당 모델의 마이그레이션 가이드를 먼저 읽습니다. 단, 다른 모델
절에 적힌 변화까지 가져와 설명하면 안 됩니다. 예를 들어 특정 세대가 더 긴 답을 내거나 더 적은
도구 호출을 한다는 설명이 있더라도, 그 문장이 지금 쓰는 모델 절에 없다면 관찰 결과와 공식 사양을
구분해 적어야 합니다.

| 선택 질문 | Opus 5를 먼저 볼 상황 | Fable 5를 검토할 상황 |
|---|---|---|
| 작업 난도 | 복잡한 코딩과 장기 에이전트 작업 | 최고 수준의 판단이 필요한 어려운 작업 |
| 운영 제약 | 현재 요금과 계정 정책 안에서 운용 가능 | 높은 비용과 30일 보존을 수용 가능 |
| 생각 조절 | 사용 환경이 제공하는 설정을 확인 | 적응형 생각과 `effort`를 함께 설계 |
| 도입 방법 | 작은 기준 작업으로 먼저 시험 | 가장 어려운 기준 작업에서 이득을 측정 |

모델 선택의 결론은 이름이 아니라 측정값이어야 합니다. 같은 완료 조건에서 성공률이 높아졌는지,
사람이 되돌리는 수정이 줄었는지, 추가 비용이 그 차이를 감당할 만한지를 함께 봅니다.

## 작업 모양에 맞는 병렬 방식을 고릅니다

### 메인 세션, 서브에이전트, 에이전트 팀, 작업 트리는 해결하는 문제가 서로 다릅니다

![한 작업대에서 네 갈래 작업 방식이 읽기와 구현과 독립 모듈과 격리 공간으로 나뉘는 안내판](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/fe/fe772ab3ab8fe75513272a46591222e7d2078730aadb2f012d99db9d2c92dab4.png "병렬 기능의 이름이 아니라 작업 사이의 의존성과 파일 충돌 가능성을 보고 방식을 선택합니다")

Claude Code에는 병렬처럼 보이는 기능이 여러 개 있습니다. 기능 이름만 보면 강할수록 좋은 단계처럼
보이지만, 실제로는 서로 다른 문제를 해결합니다.

메인 세션은 지금까지 나눈 대화와 읽은 파일을 이어서 사용합니다. 요구를 해석하면서 같은 파일을
여러 번 고쳐야 하는 작업에 맞습니다. 서브에이전트는 별도의 새 컨텍스트에서 한 가지 임무를 받고
요약을 돌려줍니다.

넓은 코드 검색, 서로 독립적인 조사, 도구 권한을 제한한 검사에 유리합니다.
[서브에이전트 문서](https://code.claude.com/docs/en/sub-agents)에 따르면 Claude Code에는
Explore, Plan, General purpose 같은 기본 에이전트가 있고, 직접 만든 에이전트는 프로젝트의
`.claude/agents/` 또는 사용자 홈의 `~/.claude/agents/`에 둘 수 있습니다.

에이전트 팀은 여러 작업자가 서로 메시지를 주고받는 실험적 기능입니다. 조사와 리뷰, 독립 모듈,
서로 다른 디버깅 가설처럼 작업 사이 결합이 낮을 때 효과가 있습니다.

반대로 순서대로 해야 하는 작업, 같은 파일을 계속 고치는 작업, 앞선 판단을 다음 단계가 알아야
하는 작업에는 조정 비용이 더 큽니다. [에이전트 팀 문서](https://code.claude.com/docs/en/agent-teams)도
팀 사용이 토큰을 더 많이 쓰며 파일 소유권을 나눠야 한다고 설명합니다.

작업 트리는 에이전트가 아니라 Git의 격리 공간입니다. 여러 작업이 코드를 동시에 써야 한다면
각자 다른 작업 트리에서 수정하게 해 파일 충돌을 줄입니다. [Claude Code 에이전트 비교 문서](https://code.claude.com/docs/en/agents)는
같은 파일을 건드릴 수 있는 병렬 작업을 작업 트리로 분리할 수 있다고 안내합니다.

| 작업 모양 | 먼저 선택할 방식 | 이유 |
|---|---|---|
| 요구를 묻고 답하며 한 기능 수정 | 메인 세션 | 대화와 판단의 흐름이 이어져야 함 |
| 저장소 전체에서 관련 코드 찾기 | 서브에이전트 | 읽기 범위를 분리하고 요약만 받을 수 있음 |
| 서로 다른 세 가지 원인 조사 | 서브에이전트 또는 에이전트 팀 | 가설 사이 의존성이 낮음 |
| 백엔드와 문서를 각각 독립 수정 | 작업 트리와 파일 소유권 | 동시에 써도 대상이 겹치지 않음 |
| 한 파일을 여러 작업자가 수정 | 병렬화하지 않음 | 병합보다 순차 수정이 단순하고 안전함 |

병렬화할 수 있는가보다 병렬 결과를 안전하게 합칠 수 있는가를 먼저 물어야 합니다. 결과를 합칠 때
메인 에이전트가 모든 판단을 다시 해야 한다면 병렬화로 아낀 시간보다 통합 비용이 커질 수 있습니다.

## 같은 파일을 쓰는 작업은 한 손에 모읍니다

### 읽기는 나눌 수 있지만 겹치는 수정에는 한 명의 소유자나 별도 작업 트리가 필요합니다

![여러 조사 카드가 하나의 수정 작업대로 모이고 격리된 두 작업대는 서로 다른 파일 상자를 다루는 장면](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/bd/bd1d023793222e742f3deed27ed46ff9b553aee5514807e5dcdce26bfd5e81cf.png "여러 에이전트가 읽은 결과는 모을 수 있지만 같은 파일을 쓰는 책임은 한곳에 둡니다")

여러 에이전트가 같은 파일을 고치면 Git 충돌만 생기는 것이 아닙니다. 한쪽은 함수 이름을 바꾸고
다른 쪽은 예전 이름으로 테스트를 추가할 수 있습니다. 두 수정이 문법상 합쳐져도 설계 판단이
충돌합니다. 에이전트 팀은 이 문제를 자동으로 없애지 않으므로 작업을 나눌 때 파일 소유권을 직접
정해야 합니다.

가장 안전한 기본값은 한 명의 작성자입니다. 다른 에이전트는 관련 파일 위치, 기존 규칙, 실패한
테스트를 읽고 요약만 반환합니다. 메인 세션은 그 증거를 모아 실제 수정과 통합을 담당합니다. 이
방식은 느려 보이지만 같은 판단을 여러 곳에서 다시 맞추는 시간을 줄입니다.

동시에 써야 할 이유가 분명하다면 작업 트리를 나눕니다. 예를 들어 한 작업자는 `api/`만, 다른
작업자는 `docs/`만 소유하고 각각 독립 테스트를 실행합니다. 완료 뒤에는 메인 세션이 diff를 읽고
공통 테스트를 실행한 다음 순서대로 통합합니다. 두 작업이 같은 설정 파일을 건드려야 한다면 그
설정 파일은 별도의 통합 작업으로 빼는 편이 안전합니다.

#### 예시 코드: 파일 소유권과 완료 조건을 함께 적기

아래처럼 "백엔드를 맡아라"보다 읽기 범위, 쓰기 범위, 완료 조건을 함께 적습니다. 읽기 범위는
넓어도 되지만 쓰기 범위는 겹치지 않게 좁힙니다. 공통 설정은 누구도 고치지 않고 발견 사항만
보고하게 했습니다.

```text
작업 A
- 읽기: api/, tests/, pyproject.toml
- 쓰기: api/, tests/api/
- 금지: docs/, pyproject.toml 수정
- 완료: uv run pytest tests/api 통과

작업 B
- 읽기: docs/, api/public.py
- 쓰기: docs/
- 금지: api/, pyproject.toml 수정
- 완료: 문서 빌드와 링크 검사 통과

공통 규칙
- 범위 밖 변경이 필요하면 수정하지 말고 파일과 이유만 보고
- 두 결과는 메인 세션이 diff 확인 후 순서대로 통합
```

이 규칙은 모든 코딩을 혼자 하라는 뜻이 아닙니다. 병렬 읽기와 독립 수정은 적극적으로 활용하되,
누가 최종 판단을 하고 어떤 파일을 소유하는지가 보이게 만들라는 뜻입니다.

## director 설정은 프로젝트 하나에서 작게 시험합니다

### 전역 기본값으로 고정하기 전에 명령 한 번으로 실행하고 결과를 비교합니다

![프로젝트 하나가 놓인 작은 시험대에서 에이전트 설정 스위치와 동시 작업 수 조절기를 확인하는 장면](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/bd/bdea0c86f940c0da9bcd8b211e89c142585c77d68df6ee4854e3258a548f6454.png "에이전트 설정을 모든 저장소에 퍼뜨리기 전에 프로젝트 하나와 기준 작업 하나에서 작게 시험합니다")

Claude Code의 사용자 설정은 Windows에서 `%USERPROFILE%\.claude\settings.json`, macOS와
Linux에서 `~/.claude/settings.json`에 있습니다. 프로젝트 설정은 저장소 안의
`.claude/settings.json`에 둡니다.

[설정 문서](https://code.claude.com/docs/en/settings)에 따르면 프로젝트 설정은 팀과 공유할
수 있고 사용자 설정은 개인에게만 적용됩니다.

처음부터 사용자 설정에 복잡한 감독 에이전트를 연결하면 모든 저장소의 행동이 한꺼번에 바뀝니다.
먼저 프로젝트의 `.claude/agents/director.md`를 만들고 `claude --agent director`로 한 번만
실행합니다. 기준 작업에서 변경 범위와 테스트 결과가 나아진 것을 확인한 뒤 프로젝트 설정의
`agent` 항목에 연결합니다.

#### 예시 코드: 프로젝트의 동시 실행 수를 작게 제한하기

아래 설정은 `.claude/settings.json`에 둡니다. `agent`는 메인 세션을 `director` 정의로
실행합니다. `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`를 `1`로 두면 서브에이전트가 다시 다른
서브에이전트를 만드는 중첩을 막습니다. 동시 실행 수 `4`는 정답이 아니라 관찰하기 쉬운 시작값입니다.

현재 문서의 기본 동시 실행 한도는 20개이고 기본 중첩 깊이는 메인 아래 3단계이므로, 큰 작업을
병렬화하기 전에는 의도적으로 작은 값에서 출발하는 편이 원인 분석에 쉽습니다. 동시 실행 환경
변수는 Claude Code 2.1.217 이상에서 지원됩니다.

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "agent": "director",
  "env": {
    "CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH": "1",
    "CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS": "4"
  }
}
```

설정 파일은 행동의 상한을 정할 뿐 어떤 일을 위임할지는 알려 주지 않습니다. 그 기준은 에이전트
정의에 짧게 적습니다. 너무 긴 규칙은 실제 작업 요청보다 앞에 놓여 매번 컨텍스트를 차지하므로,
처음에는 관찰 가능한 원칙만 넣습니다.

#### 예시 코드: 읽기와 독립 검증만 위임하는 에이전트 정의

아래 파일을 `.claude/agents/director.md`로 저장합니다. `model: inherit`는 메인 세션이 선택한
모델을 그대로 사용한다는 뜻입니다. 직접 만든 에이전트의 시스템 프롬프트는 기본 Claude Code
시스템 프롬프트를 대체하지만 프로젝트의 `CLAUDE.md`는 계속 읽힙니다.

따라서 저장소 규칙의 정본은 `CLAUDE.md`에 두고, 에이전트 파일에는 역할에만 필요한 차이를 적는
편이 좋습니다.

```markdown
---
name: director
description: 구현을 통합하고 독립적인 읽기와 검증만 우선 위임한다.
model: inherit
---

작업의 최종 책임자는 당신이다.

다음 작업은 직접 수행한다.
- 요구 해석과 완료 조건 확정
- 서로 의존하는 파일의 구현
- 서브에이전트 결과 통합과 최종 판정

다음 작업은 서로 독립적일 때만 위임할 수 있다.
- 넓은 저장소 검색과 문서 조사
- 쓰기 범위가 겹치지 않는 수정
- 구현 과정을 모르는 새 컨텍스트의 검증

위임할 때는 읽기 범위, 쓰기 범위, 완료 조건, 검증 명령을 적는다.
범위 밖 수정이 필요하면 직접 고치지 말고 이유와 위치만 보고하게 한다.
에이전트의 완료 보고를 증거로 삼지 말고 지정된 테스트를 직접 확인한다.
```

이 설정이 모든 프로젝트의 정답은 아닙니다. 파일 한두 개를 고치는 짧은 작업은 메인 세션 하나가
더 빠릅니다. 여러 저장소에 공통 적용하고 싶더라도 먼저 한 프로젝트에서 같은 기준 작업을 설정
전후로 비교해야 합니다.

## 완료는 새 컨텍스트와 실제 테스트로 확인합니다

### 검토 에이전트는 놓친 조건을 찾고 테스트는 결과가 실제로 작동하는지 증명합니다

![새 검토 창이 변경 내역을 읽고 옆의 실제 테스트 장치가 결과물을 작동시키는 이중 검증대](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/db/db09a4aa1753cf6577e84aff28e08e885bd7bed60230cc7a2d76cff155108b8c.png "새 컨텍스트의 검토와 실행 가능한 테스트는 역할이 다르며 두 결과가 함께 있어야 완료를 판단할 수 있습니다")

서브에이전트는 별도 컨텍스트에서 시작하므로 구현자가 당연하다고 여긴 가정을 다시 물을 수
있습니다. 그러나 새 컨텍스트라고 해서 검토 결과가 자동으로 맞는 것은 아닙니다. 검토 에이전트도
코드를 잘못 읽거나 테스트하지 않은 추측을 확신할 수 있습니다. 새 컨텍스트는 독립적인 관점을
만들고, 테스트는 실행 결과라는 증거를 만듭니다.

검토자에게는 구현자의 긴 설명보다 원래 요청, 완료 조건, diff, 관련 테스트 명령을 줍니다. "잘
했는지 확인해 줘"라고 묻지 말고 어떤 조건이 깨졌는지, 범위 밖 수정이 있는지, 테스트가 실제
실패를 잡는지를 찾게 합니다. 검토 결과에 문제가 적혀 있으면 파일과 테스트로 재현한 뒤 반영합니다.

#### 예시 코드: 구현 설명 없이 결과만 검사하는 검증 프롬프트

이 프롬프트는 검토자를 반대편 토론자로 만드는 것이 아니라 증거 수집자로 만듭니다. 지적마다
파일과 근거를 요구하고, 재현하지 못한 의심은 사실과 분리하게 합니다. 저장소가 정한 테스트가
있다면 아래의 `<검증 명령>` 자리에 정확히 넣습니다.

```text
원래 요청, 완료 조건, 현재 diff만 보고 결과를 독립적으로 검토한다.

확인할 것
1. 완료 조건을 빠뜨린 부분
2. 요청 범위를 벗어난 변경
3. 기존 동작을 깨뜨릴 수 있는 구체적인 경로
4. 테스트가 실패 사례를 실제로 잡는지

각 지적에는 파일 위치와 재현 근거를 붙인다.
근거가 없는 가능성은 확정 오류와 구분한다.
마지막에 <검증 명령>을 실행하고 종료 코드와 핵심 결과를 보고한다.
코드는 수정하지 않는다.
```

완료 순서는 간단합니다. 먼저 저장소가 요구하는 테스트를 실행하고, 다음으로 새 컨텍스트 검토를
받고, 지적을 실제로 재현합니다. 수정이 생기면 테스트를 다시 실행합니다. 마지막에는 사용자가
보는 화면, 생성된 파일, API 응답처럼 작업의 실물을 확인합니다. 웹 화면이라면 DOM에 요소가
있다는 사실만 보지 말고 실제 화면 크기에서 스크린샷을 확인해야 합니다.

Claude Code 에이전트가 일을 벌일 때 가장 먼저 할 일은 더 강한 모델로 바꾸거나 더 긴 규칙을
쓰는 것이 아닙니다. 요청과 결과를 기록하고, 한 조건씩 비교하고, 작업의 모양에 맞는 실행 방식을
고르는 것입니다. 같은 파일을 쓰는 책임을 분명히 하고 실제 테스트로 끝을 판정하면, 다음 모델이
나와도 같은 절차로 원인을 찾을 수 있습니다.
