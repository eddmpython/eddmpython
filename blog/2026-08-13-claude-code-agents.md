비싼 최신 모델로 바꿨는데 에이전트가 더 서툴러진 경험이 있으신가요. 시키지 않은 일을 벌이고,
확인을 반복하느라 시간을 태우고, 보고서는 길어지는데 정작 코드는 어긋납니다. 저도 자동투자
프로그램을 만드는 저장소에서 몇 주 동안 같은 일을 겪었고, 처음에는 모델을 욕했습니다.

이 글은 그 원인을 둘로 가릅니다. 절반은 모델의 행동이 실제로 바뀌었고 그 변화가 공식 문서에
이미 적혀 있었다는 것, 나머지 절반은 제 에이전트 구조가 그 변화를 증폭했다는 것입니다. 끝에는
제가 실제로 쓰고 있는 Claude Code 설정 파일을 그대로 복사해 쓸 수 있게 담았습니다.

## 최신 모델로 바꿨는데 결과물이 나빠졌다

![작은 설계 도면 하나가 과잉 생산된 똑같은 부품 더미에 묻혀 있는 작업대](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/c5/c512dad5e83c99f310e9a837d80e5b751922f6f6d96f17fd7db307b09bd621b2.webp "요청은 도면 한 장인데 산출물이 작업대를 덮으면, 문제는 성실함이 아니라 방향입니다")

이 장면이 제가 겪은 상황과 정확히 같습니다. 요청한 작업은 작고 분명했는데, 돌아온 결과물은
요청을 덮을 만큼 많았습니다. 더 많이 일했는데 더 틀린 상태입니다. 증상을 구체적으로 적으면
네 가지였습니다.

- 고쳐 달라고 한 함수 옆의 코드까지 스스로 판단해서 바꿉니다.
- 시키지 않은 검증을 반복하며 턴을 태웁니다. 확인했다는 보고가 코드보다 깁니다.
- 응답과 산출 문서가 이전 모델보다 눈에 띄게 길어집니다.
- 서브에이전트를 띄울 수 있는 환경이면 작은 일에도 위임을 남발합니다.

여기까지는 제 저장소에서 직접 관측한 경험입니다. 이 증상만 보면 "Opus 5는 이상한 모델"이라는
결론이 자연스럽습니다. 그런데 원인을 찾으러 가 보니 절반은 이미 인쇄되어 있었습니다.

## Opus 5의 이상함은 공식 문서에 이미 적혀 있다

![제도용 책상 위에 펼쳐진 두꺼운 기술 설명서와 그 위에 놓인 돋보기](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/61/617abe2b2581ab754a2a98be4f6115f2ef018c621aab090f625574df9721fea6.webp "당황스러운 행동의 목록은 비밀이 아니었습니다. 마이그레이션 가이드에 교정 문구까지 함께 있습니다")

Anthropic이 공개한 [모델 마이그레이션 가이드](https://platform.claude.com/docs/en/about-claude/models/migration-guide)를
열면 Opus 5 절에 위 증상이 거의 그대로 나옵니다. 문서가 밝힌 변화는 이렇습니다. 응답과 파일
산출물이 이전 모델보다 길어지는 경향이 있고, 시키지 않아도 자기 작업을 스스로 검증하며, 작업
범위를 넓히는 일이 있고, 서브에이전트 위임을 이전 세대인 Opus 4.8보다 훨씬 적극적으로 합니다.

중요한 건 다음 문장입니다. 문서는 "검증하라"는 프롬프트 지시를 지우라고 권합니다. 스스로
검증하는 모델에게 검증 지시까지 겹치면 과잉 검증이 된다는 뜻입니다. 위임도 같습니다. Opus 4.8은
위임을 잘 안 해서 "위임을 늘려라"라는 문구를 넣던 시절이 있었는데, 그 문구가 남아 있으면 Opus
5에서는 위임 남발이 됩니다. 즉 구모델에 맞춰 조율한 프롬프트가 신모델에서는 역효과를 냅니다.

그래서 Opus 5를 서브에이전트로 쓸 때는 저는 프롬프트에 아래 세 줄을 고정으로 넣습니다. 문서의
권고를 제 작업에 맞게 줄인 것입니다.

```text
요청한 범위만 수행한다. 요청 밖 코드는 발견만 보고하고 고치지 않는다.
시키지 않은 검증을 반복하지 않는다. 검증은 지정된 명령 1회로 끝낸다.
결과 보고는 결론부터 다섯 문장 이내로 한다.
```

모델이 이상해진 게 아니라 모델이 바뀌었는데 지시문이 그대로였던 것입니다. 그런데 문서를 다
반영해도 남는 문제가 있었습니다. 그 얘기 전에 Fable 5부터 정리합니다.

## Fable 5가 반쪽으로 느껴지는 이유

![불투명 유리 뒤에서 실루엣으로만 보이는 기계와 유리 앞 선반에 놓인 완성된 부품](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/07/071089ce2fe07e4d1b6f83f9fc42f62290f5364be9f3b1d3a06c42de4af3268c.webp "결과물 선반은 앞에 있는데 작동은 유리 뒤에 있습니다. 반쪽이라는 체감의 실체는 이 유리벽입니다")

Fable 5는 Anthropic의 최상위 모델입니다. 그런데 써 보면 "반쪽짜리"라는 말이 나오는 지점들이
있고, 이것들은 감상이 아니라 [공식 문서](https://platform.claude.com/docs/en/about-claude/models/introducing-claude-fable-5)에
있는 사양입니다.

- 추론이 항상 켜져 있는데 원문 사고 과정은 절대 돌려주지 않습니다. 요약만 받을 수 있습니다.
- 안전 분류기가 요청을 거절할 수 있습니다. 보안 도구나 생명과학 인접 작업은 정상 요청도 가끔
  걸립니다.
- 제로 데이터 보존을 지원하지 않습니다. 30일 보존이 필수라서 조직 정책에 따라 아예 못 씁니다.
- 응답 앞부분을 미리 채워 주는 prefill 기법이 금지됩니다.
- 가격이 Opus 5의 두 배입니다. 백만 토큰당 입력 10달러, 출력 50달러입니다.

제 생각을 구분해서 적으면, 이건 반쪽이라기보다 유리벽입니다. 결과물 품질은 실제로 가장 좋은데
과정을 보여 주지 않고, 쓸 수 있는 조건이 까다롭습니다. 어려운 설계 판단과 긴 자율 작업의 감독
자리에는 값을 하고, 짧고 기계적인 작업에 쓰면 돈과 시간에서 손해를 봅니다. 어디에 앉히느냐의
문제였고, 그 "자리 배치"가 바로 다음 절의 주제입니다.

## 진짜 범인은 모델이 아니라 에이전트 구조였다

![조각 작업대는 하나뿐이고 양쪽 선반에서 재료 수레들이 그 작업대로 모여드는 공방](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/4b/4be7741c7a7728a278411ba98d67b471992b40ab160b1fa519ec72a062980505.webp "재료를 나르는 수레는 여러 대여도 조각칼은 한 자리에만 있습니다. 코드를 쓰는 손이 이래야 합니다")

문서 교정을 다 반영해도 삽질이 남았던 이유는 제 에이전트 배치에 있었습니다. 저는 이렇게 쓰고
있었습니다. 감독은 Fable 5, 핵심 구현은 Opus 5 서브에이전트, 그 결과의 검증은 또 다른 Opus 5
서브에이전트. 강한 모델이 관리하고 싼 모델이 일하는, 그럴듯해 보이는 구조입니다.

이 구조는 두 군데가 틀렸습니다. 첫째, 판단이 필요한 구현을 위임했습니다. Anthropic의
[에이전트 팀 문서](https://code.claude.com/docs/en/agent-teams)는 병렬 에이전트가 리서치와
리뷰에 맞고, 순차 작업이나 같은 파일을 고치는 작업은 단일 세션이 낫다고 명시합니다. Anthropic이
[에이전트들로 C 컴파일러를 만든 실험](https://www.anthropic.com/engineering/building-c-compiler)에서도
성공 조건은 협업이 아니라 각 에이전트가 파일을 거의 독점하는 배치였습니다. 멀티에이전트에
회의적인 [Cognition의 글](https://cognition.com/blog/dont-build-multi-agents)과 그 후속작도
결론은 같습니다. 지능은 여럿이 보태도 쓰기는 단일 스레드여야 합니다.

둘째, 같은 모델이 쓰고 같은 모델이 검증했습니다. 2025년 ICML에 발표된
[LLM 오류 상관 연구](https://arxiv.org/abs/2506.07962)는 350개 넘는 모델을 비교해서, 모델들이
우연보다 훨씬 자주 같은 오답에 동의하고 같은 계열일수록 그 상관이 크다는 것을 보였습니다. Opus가
저지르는 유형의 실수는 Opus 검증자도 잘 못 봅니다. 검증에서 실제로 값진 것은 다른 모델이 아니라
구현 과정을 전혀 모르는 새 컨텍스트입니다. Claude Code의
[서브에이전트 문서](https://code.claude.com/docs/en/sub-agents)도 서브에이전트 모델의 기본값을
메인과 같은 모델, 즉 상속으로 둡니다.

그래서 원칙을 이렇게 다시 세웠습니다. 쓰기는 단일 스레드, 읽기는 병렬, 검증은 새 컨텍스트.
핵심 구현은 메인 루프가 직접 하고, 서브에이전트는 넓은 탐색과 대량 읽기, 그리고 구현 과정을
모르는 검증에만 씁니다. 이 원칙을 파일로 박은 것이 다음 절입니다.

## 바로 복사해 쓰는 에이전트 설정

![빈틈없이 정리되어 들고 갈 준비가 된 공구함 하나가 어두운 작업대 위에 놓인 장면](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/ad/add93db32ea5eecdc197a5956e6f8a3fc0097286679c670152ca4df561eecba1.webp "짜인 공구함을 통째로 들고 가면 됩니다. 이 절이 그 공구함입니다")

Claude Code 기준으로 파일 두 개면 됩니다. 하나는 전역 설정이고 하나는 메인 에이전트의 행동
규칙입니다. 두 파일 모두 홈 디렉터리의 `.claude` 폴더에 두면 모든 프로젝트에 적용됩니다.

먼저 `~/.claude/settings.json`입니다. 서브에이전트 폭주를 막는 한도 두 개와, 아래에서 만들
에이전트 정의를 메인 루프에 연결하는 줄이 핵심입니다.

```json
{
  "model": "claude-opus-5",
  "agent": "director",
  "env": {
    "CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH": "2",
    "CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS": "4"
  }
}
```

`model`은 구독에 맞게 고르면 됩니다. 저는 감독 품질 때문에 Fable 5를 쓰지만 Opus 5로도 같은
구조가 성립합니다. 다음은 `~/.claude/agents/director.md`입니다. 이 파일이 이 글의 결론
전체입니다.

```markdown
---
name: director
description: 기본 메인 루프 에이전트. 핵심 구현과 판단은 직접 하고, 읽기 작업과 fresh-context 검증만 위임한다.
model: inherit
---

당신은 이 저장소의 테크리드 겸 최종 책임자다. 관리자가 아니다.

## 제1원칙: 쓰기는 단일 스레드, 읽기는 병렬

코드를 쓰는 손은 하나여야 한다. 병렬 쓰기는 충돌과 암묵적 결정 불일치를 만들고,
판단이 필요한 구현을 하급 모델에 위임하면 품질이 무너진다.
위임이 확실히 이기는 곳은 읽기 작업과 fresh-context 검증뿐이다.

## 직접 하는 일 (위임 금지)

- 핵심 구현. 설계 판단이 섞인 코드는 전부 직접 쓴다.
- 설계, 문제 분해, 어려운 디버깅, 모호한 요구의 해석.
- 최종 통합과 판정. 서브에이전트 결과물을 붙이고 수용 여부를 정하는 일.
- 판단이 산출물인 작업은 위임하지 않는다. 판단인지 애매하면 판단이다.

## 위임하는 일

| 무엇 | 누구에게 | 규약 |
|---|---|---|
| 넓은 탐색, 대량 읽기, 병렬 리서치 | sonnet (단순 조회는 haiku) | 읽기 전용. 요약만 반환받는다 |
| 명세가 완결된 기계적 구현 | sonnet | 반환된 diff는 검토 후에만 수용 |
| 독립 검증 (fresh context) | model 미지정 (부모 상속) | 검증자에게 diff와 완료 조건만 주고 구현 reasoning은 주지 않는다 |

기본은 model 미지정(부모 상속)이다. 하급 모델 지정은 판단이 얕은 작업일 때만 한다.
opus를 쓸 때는 프롬프트에 명시한다: 요청 범위만 수행, 시키지 않은 검증 반복 금지,
결과는 간결하게 보고.

## 위임 전 3확인

1. 완료 조건이 무엇인가 (검증 가능한 형태로)
2. 이 작업이 무엇을 몰라도 되는가 (컨텍스트 경계)
3. 결과를 어떻게 판정할 것인가

셋 중 하나라도 못 적으면 위임하지 않고 직접 한다.

## 위임 실패 규약

서브에이전트가 실패하거나 결과가 비면, 같은 프롬프트를 다시 던지지 않고
```

## 오늘 내 세팅에서 확인할 것

![어두운 작업대 위에 나란히 선 검사 게이지 세 개와 첫 게이지에 물린 부품](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/24/24797d52ca5755b466fecfaf06639bbcecf78b48cb29ba3aa405448d777eec52.webp "게이지 세 개를 차례로 물려 보는 것으로 충분합니다. 통과 못 한 것 하나만 오늘 고칩니다")

글을 덮기 전에 자기 세팅을 세 가지만 확인하면 됩니다.

1. 코드를 쓰는 손이 몇 개인가. 구현이 서브에이전트로 나가고 있다면 그 작업에 판단이 섞여
   있는지 봅니다. 섞여 있으면 메인 루프로 가져옵니다.
2. 검증자가 구현자와 같은 모델, 같은 컨텍스트인가. 같다면 검증이 아니라 동의입니다. 새
   컨텍스트의 검증자로 바꾸고 diff와 완료 조건만 넘깁니다.
3. 프롬프트에 구모델용 문구가 남아 있는가. "반드시 검증하라", "적극적으로 위임하라" 같은
   문구는 Opus 5에서 역효과입니다. 지우고 모델의 기본 행동을 관찰한 뒤에 필요한 것만 다시
   넣습니다.

시작은 터미널에서 파일 하나를 만드는 것입니다. 아래 명령을 실행하면 빈 에이전트 정의가 열리고,
위 절의 `director.md` 내용을 붙여 넣으면 다음 세션부터 적용됩니다.

```bash
mkdir -p ~/.claude/agents && $EDITOR ~/.claude/agents/director.md
```

모델은 계속 바뀝니다. 다음 모델이 나와도 순서는 같습니다. 마이그레이션 문서를 먼저 읽고, 구조를
점검하고, 프롬프트에서 지난 모델의 흔적을 지우는 것. 모델을 욕하는 건 그 다음에 해도 늦지
않습니다.
