`Python 자동화 30일 실행 계획`은 한 달 안에 큰 시스템을 새로 만드는 일정이 아닙니다. 수업에서 만든
작은 자동화를 반복 실행하고, 직접 한 번 고치고, AI로 한 번 확장하고, 동료에게 넘기는 4주 계획입니다.

시작 전에 실제 업무 후보를 하나만 고릅니다. 주 1회 이상 반복되고 입력과 결과가 분명하며, 합성 데이터로
먼저 시험할 수 있는 일이 좋습니다. 각 주에는 날짜, 결과물, 검증, 도움 요청 기준을 반드시 적습니다.

## 1주차에는 같은 자동화를 세 번 재실행합니다

### 월요일과 수요일 및 금요일에 합성 입력을 처리하고 결과 숫자를 기준선으로 남깁니다

![Python 자동화 30일 실행 계획의 1주차에 재실행 세 번과 기준선 기록이 배치된 달력](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/ed/edf68eba6adf2e16fda996a4b3c99f1e638f7e44e2638dec6b0f516153aeffba.png "세 번의 실행 결과가 같은 기준선 카드로 모여 재현성을 확인합니다")

첫 주에는 기능을 추가하지 않습니다. 새 폴더에서 설치하고 같은 합성 입력을 월요일, 수요일, 금요일에
각각 실행합니다. 매번 명령, 실행 시간, 결과 파일, 테스트 결과를 짧게 기록합니다.

세 결과가 다르면 확장보다 재현 문제를 먼저 고칩니다. 30분 안에 원인을 찾지 못하면 오류보고 6항목을
작성해 도움을 요청합니다.

#### 예시

| 날짜 | 결과물 | 검증 | 도움 요청 기준 |
|---|---|---|---|
| 1일 | 첫 재실행 결과 | 정상 4행, 합계 249998 | 설치가 30분 넘게 막힘 |
| 3일 | 두 번째 결과 | 첫 결과와 숫자 차이 0 | 결과 차이 원인을 30분 안에 못 찾음 |
| 5일 | 세 번째 결과 | 전체 테스트 PASS | 같은 오류가 두 번 반복됨 |

## 2주차에는 작은 규칙 하나를 직접 수정합니다

### AI 없이 경계값 하나를 바꾸고 테스트 실패와 통과를 모두 기록합니다

![2주차에 사람이 조건 코드와 테스트를 직접 바꾸고 빨간 실패에서 녹색 통과로 이동하는 모습](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/03/03bb89bcddfc43c4e9034e4e86c36867b768af409302e7ac88701227e3fb21d7.png "직접 수정한 한 규칙이 테스트 증거와 diff 검토를 거쳐 승인됩니다")

둘째 주에는 코드 구조를 이해했는지 확인합니다. 예를 들어 고액거래 기준을 합성 실험에서만 `100000`원에서
`120000`원으로 바꾸고, 경계 테스트도 `119999`원과 `120000`원으로 수정합니다.

먼저 기존 테스트가 실패하는 장면을 확인하고 코드와 테스트를 맞춘 뒤 전체 테스트를 통과시킵니다. 실무
규칙을 실제로 변경할 때는 담당자 승인 없이 숫자를 바꾸지 않습니다.

#### 확인 목록

- 실행 날짜와 바꿀 규칙 한 가지를 적었습니다.
- 변경 전 테스트 실패를 확인했습니다.
- 코드와 경계 테스트를 함께 수정했습니다.
- 전체 테스트가 PASS했습니다.
- `git diff`에 설명할 수 있는 파일과 줄만 남았습니다.
- 45분 안에 끝나지 않으면 기준선으로 돌아가 도움을 요청합니다.

## 3주차에는 작업지시서로 AI 확장을 맡깁니다

### 새 변형 열 하나를 추가하고 계획과 구현 및 테스트와 diff를 차례로 승인합니다

![3주차 작업지시서가 AI 계획과 변형 열 구현 및 테스트와 diff 승인으로 이어지는 모습](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/0b/0bb44573f391507bbf2851ea4068aaaaf6e65af1eabd6087a1e2bc3bce49d43d.png "AI는 정해진 한 기능만 바꾸고 사람은 각 증거 관문에서 범위를 확인합니다")

셋째 주에는 `팀명`을 `부서`로 바꾸는 새 열 별칭처럼 범위가 작은 기능을 고릅니다. 목적부터 완료조건까지
8항목 작업지시서를 쓰고, AI에게 수정 전 계획을 먼저 받습니다.

구현 뒤에는 변형 파일 테스트와 전체 테스트 및 diff를 확인합니다. 계획과 다른 파일이 바뀌거나 테스트가
두 번 연속 실패하면 더 큰 수정을 계속하지 않고 재현 가능한 오류보고로 전환합니다.

#### 예시

| 항목 | 3주차 기록 |
|---|---|
| 실행 날짜 | 17일 |
| 결과물 | `팀명` 별칭과 변형 파일 테스트 |
| 검증 | 기존 숫자 차이 0, 전체 테스트 PASS |
| 변경 통제 | 승인한 코드와 테스트 파일만 남음 |
| 도움 요청 | 계획 밖 파일 변경 또는 같은 테스트 두 번 실패 |

## 4주차에는 동료 재실행과 다음 30일을 결정합니다

### 인수인계서만 전달해 동료가 성공하면 유지와 개선 및 중단 가운데 다음 행동을 고릅니다

![4주차에 동료가 인수인계서로 재실행하고 유지와 개선 및 중단 세 선택지로 마무리하는 모습](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/4a/4a9aae7bd42bdb2a57af63e7175517c6eb51933664b7875689be4b407bd37723.png "동료 실행 증거가 다음 달의 실제 운영 결정을 위한 세 갈래로 연결됩니다")

마지막 주에는 작성자가 설명하지 않고 동료 한 명에게 저장소와 인수인계서만 전달합니다. 동료가 합성 입력의
결과와 전체 테스트 PASS를 만들면 교육용 프로젝트가 전달 가능한 작업 도구가 됩니다.

그 결과를 보고 다음 30일을 정합니다. 시간이 줄고 오류가 줄었다면 실제 업무 적용 승인을 준비하고,
가치는 있지만 불안정하면 합성 데이터로 개선을 계속합니다. 효과가 작거나 위험이 크면 중단 기록을 남깁니다.

#### 확인 목록

- 동료 실행 날짜와 담당자를 적었습니다.
- 작성자 도움 없이 결과 파일과 PASS 검증표를 만들었습니다.
- 막힌 지점을 인수인계서에 반영하고 다시 실행했습니다.
- 절약 시간과 오류 수 및 수동 확인 시간을 기록했습니다.
- 유지, 개선, 중단 가운데 다음 행동 하나를 정했습니다.
- 실제 회사 자료 사용 전 담당자와 보안 및 운영 승인을 확인합니다.

30일의 성공 기준은 많은 코드를 만든 것이 아닙니다. 같은 결과를 반복해서 만들고, 변경을 증명하고,
다른 사람이 이어서 실행할 수 있는 상태를 만든 것입니다.
