새 AI 대화를 열면 모델은 코드를 읽을 수 있지만 이 저장소의 규칙은 아직 모릅니다. 어느 명령으로
테스트하는지, 지금 브랜치가 배포용인지, 옆 폴더의 변경을 지워도 되는지 알 수 없습니다. 그런데 첫
요청에는 대개 "이 버그를 고쳐 줘"만 적습니다.

같은 모델이 저장소마다 다른 결과를 내는 이유는 반복 규칙을 읽을 수 있느냐에 있습니다. 이 저장소는
`AGENTS.md`에서 시작해 `CLAUDE.md`를 읽도록 연결합니다. 실제 테스트 명령, 수정 범위, 배포 조건은
`CLAUDE.md` 한곳에 적습니다.

## 반복 규칙은 프롬프트가 아니라 파일에 적습니다

![한 번 쓰고 사라지는 요청 메모와 반복 작업을 지탱하는 고정 작업 환경의 대비](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/71/710fb217b5ff64f54d8932e7111cd5669319d6393295c96dc7b46c4f77775761.webp "프롬프트에는 이번 요청을 쓰고 저장소 문서에는 반복해서 지킬 규칙을 남깁니다")

프롬프트에는 지금 할 일을 적습니다. 여러 세션이 반복해서 지켜야 할 테스트 명령과 수정 금지 경로는
저장소의 규칙 파일에 적습니다. 둘은 쓰이는 기간이 다릅니다.

예를 들어 "README를 고쳐 줘"라는 요청에는 중요한 정보가 빠져 있습니다. README에 적힌 제품 수치는
어디서 확인해야 하는지, 형제 저장소의 기능을 이 저장소가 가진 것처럼 써도 되는지, 문서를 고친 뒤
사이트도 빌드해야 하는지 알 수 없습니다. 요청을 길게 써서 이번 한 번은 설명할 수 있습니다. 다음
대화에서는 다시 써야 합니다.

반면 `CLAUDE.md`에 "제품 수치는 제품 저장소나 실제 화면에서 확인한 것만 쓴다"고 적어 두면 다음
요청에서는 다시 설명하지 않아도 됩니다. AI는 숫자를 바로 복사하지 않고 제품 저장소나 공개 화면을
먼저 확인합니다.

이번 요청만 필요한 내용은 프롬프트에 쓰고, 다음 요청에도 필요한 내용은 규칙 파일에 한 번만 씁니다.

## 저장소에 다섯 가지 답을 적습니다

![하나의 저장소 작업대를 둘러싼 다섯 개의 서로 다른 확인 지점](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/c6/c6c68286dca4b9ce7ce538938c782bb5b8670c032a4b946e0e0ddf978733463f.webp "제품 범위, 읽을 곳, 실행 명령, 완료 증거, 수정 권한을 저장소가 답해야 합니다")

Python 버전과 운영체제만 적어서는 부족합니다. AI가 파일을 열고 변경을 끝내려면 다음 다섯 가지를
알아야 합니다.

| 질문 | 저장소가 알려 줄 것 |
|---|---|
| 여기는 무엇을 만드는 곳인가 | 제품 경계와 소유하지 않는 영역 |
| 어디서부터 읽어야 하나 | 코드 지도와 문서의 정본 |
| 무엇을 실행해야 하나 | 설치, 테스트, 빌드, 배포 명령과 실행 환경 |
| 됐다는 말은 무엇으로 증명하나 | 실데이터 호출, 코드 확인, 테스트, 화면 검수 순서 |
| 어디까지 바꿔도 되나 | 기존 변경 보존, 비밀정보, 커밋, 배포 권한 |

이 다섯 답이 없으면 AI는 다른 프로젝트에서 쓰던 방법을 가져옵니다. `test`라는 폴더가 보이면 전체
테스트를 돌리고, `dist`가 Git에서 무시되면 그 안에 임시 산출물을 만들어도 된다고 생각합니다.

우연히 맞으면 빠진 규칙이 더 오래 남습니다. 다음 세션도 같은 선택을 다시 추측하기 때문입니다. 규칙
파일 앞부분에는 이 저장소가 소유하지 않는 경로, 완료 전에 실행할 검사, 별도 승인이 필요한 배포 작업을
적습니다.

## AGENTS.md는 CLAUDE.md 한곳을 가리킵니다

![서로 다른 두 진입 경로가 하나의 정돈된 작업 환경으로 합쳐지는 모습](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/11/118381f89feb8d2c84d2fd6f4d6e7da52bf0c1bbb63e3f29f695dbcdb7daaf73.webp "AGENTS.md는 CLAUDE.md를 읽게 하고 실제 규칙은 CLAUDE.md 한곳에 둡니다")

왜 파일이 두 개나 필요할까요. 배경은 하나의 표준 파일 이름이 없다는 데 있습니다. Claude는
`CLAUDE.md`를 읽고, Codex를 비롯한 여러 에이전트는 `AGENTS.md`를 먼저 읽습니다. Claude와 일하며
`CLAUDE.md`에 규칙을 쌓아 온 프로젝트에 다른 에이전트가 들어오면, 그 규칙을 보지 못한 채 작업을
시작할 수 있습니다. 반대 방향도 같습니다.

규칙을 두 파일에 똑같이 복사하면 한쪽의 테스트 명령만 바뀌는 날 내용이 어긋납니다. Claude는 예전
명령을 따르고 다른 에이전트는 새 명령을 따를 수 있습니다. 그래서 한 파일에만 규칙을 쓰고 다른 파일은
그 파일을 읽으라는 안내만 둡니다.

이 저장소의 [에이전트 템플릿](https://github.com/eddmpython/eddmpython/tree/main/agent-template)은
역할을 나눕니다. `AGENTS.md`는 `CLAUDE.md`를 끝까지 읽으라는 안내만 제공합니다. 제품 범위, 검증
명령, 임시 산출물, 버전 관리 규칙은 `CLAUDE.md` 한곳에만 둡니다.

다만 이것은 현재 템플릿의 배치일 뿐, 파일 사이의 서열이 아닙니다. 새 프로젝트가 여러 범용 에이전트를
중심으로 시작한다면 `AGENTS.md`에 규칙 본문을 두는 편이 더 자연스럽습니다. 그때는 `CLAUDE.md`를
짧은 입구로 만들고 `AGENTS.md`를 읽으라고 적으면 됩니다. Claude 중심으로 이미 자란 프로젝트라면
지금처럼 반대로 둬도 됩니다. 중요한 것은 어느 이름이 정본인가가 아니라 정본이 하나인가입니다.

정본이 하나라는 말은 모든 설명을 한 파일에 밀어 넣는다는 뜻도 아닙니다. 강행규칙에는 어기면 실제
사고가 나는 것만 둡니다. 지금 작동하는 상세 계약은 제품 문서로 보내고, 아직 만들지 않은 계획은
이슈나 계획 문서로 보냅니다. AI가 항상 읽어야 할 내용과 필요할 때 찾아갈 내용을 나누지 않으면,
중요한 규칙도 긴 배경 설명 사이에 묻힙니다.

두 문서의 내용이 다르면 루트 규칙에 적힌 정본만 고칩니다. 어느 파일이 맞는지 다시 추측하지 않아도
됩니다.

## 실패한 지점을 다음 규칙으로 바꿉니다

![깨진 작업 경로에서 확인 지점과 안전 난간이 만들어지는 모습](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/0d/0d17c5f74d34115c4fc9dd372b260b896faaeee1cafde0810c648b1d4cc94465.webp "실패한 검사 위치와 다시 확인할 순서를 다음 작업의 규칙으로 남깁니다")

처음부터 완벽한 규칙집을 만들 수는 없습니다. 일반적인 모범 사례를 모아 붙이면 문서는 금방
길어지지만, 정작 이 저장소에서 일어나는 사고는 막지 못합니다. 지금의 템플릿에는 실제 작업에서
되풀이된 실패가 남아 있습니다.

한 번은 검사가 끝나기 전에 결과를 읽고 제품이 실패했다고 판단했습니다. 여기서 나온 규칙은 단순히
"테스트를 잘하라"가 아닙니다. 실패하면 대상보다 검사 코드, 종료 시점, 경로를 먼저 확인하라는
순서입니다. 거짓 실패도 거짓 성공만큼 위험하기 때문입니다.

또 다른 때에는 지킬 코드가 충분하지 않은데 검사부터 늘어났습니다. 게이트 수는 많아졌지만 제품은
달라지지 않았습니다. 그래서 템플릿은 결함을 실제로 보기 전에 게이트를 만들지 말고, 지킬 코드가
생길 때 그 코드와 함께 만들라고 적습니다. 테스트 통과 개수를 성과처럼 말하지 않는 이유도 같습니다.

참조 프로젝트처럼 만들어 달라는 요청을 받고 원문을 읽지 않은 채 분위기만 흉내 낸 실패도 있었습니다.
여기서 나온 규칙은 분명합니다. 읽을 수 있는 참조가 지목되면 먼저 열고, 실제로 확인한 부분만
반영했다고 말합니다. 이 글을 쓰기 전에 DartLab의 블로그 파이프라인과 마스터라이터 문서를 직접
읽은 것도 같은 규칙의 적용입니다.

실패에서 출발한 규칙은 구체적입니다. 언제 멈추고, 무엇을 보고, 어떤 순서로 다시 시도할지가 보입니다.
반대로 "최선을 다한다", "안전하게 작업한다" 같은 문장은 옳지만 행동을 바꾸지 못합니다.

## 템플릿 규칙 세 곳을 고쳤습니다

![헐거운 작업 틀이 세 개의 정밀한 보강 부품으로 단단해지는 과정](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/8d/8d7e756072345c3fde690e01bf3573c8cd1a59b99f88d991be2817837845b8d5.webp "템플릿에서 기존 변경, 권한, 실행 환경 규칙을 세 곳 고쳤습니다")

환경에 관한 글을 쓰면서 [공개용 `CLAUDE.md`](https://github.com/eddmpython/eddmpython/blob/main/agent-template/CLAUDE.md)를
다시 읽어 보니 세 곳이 말과 맞지 않았습니다.

첫째, 기존 템플릿은 작업 트리가 더러우면 남의 미완성 위에 쌓지 말라고만 했습니다. 안전한 문장이지만
행동은 모호했습니다. 이제는 변경 경로를 먼저 읽고, 관련 없는 변경은 보존한 채 진행하며, 같은 파일과
같은 부분이 겹칠 때 보고하도록 바꿨습니다. 무조건 멈추는 것도 협업이 아니고, 모른 척 덮어쓰는 것도
협업이 아닙니다.

둘째, 요청의 동사가 권한의 경계라는 점을 명시했습니다. 설명과 진단 요청은 파일을 고치라는 허가가
아닙니다. 반대로 구현 요청은 관련 수정만 하고 끝나는 게 아니라 그 수정에 필요한 검증까지 포함합니다.
배포, DNS, 결제처럼 외부 상태를 바꾸는 일은 별도 승인을 받습니다. AI가 적극적이어야 할 범위와
조심해야 할 범위를 같은 문단에서 분리했습니다.

셋째, 프로젝트별 칸에 실행 환경을 추가했습니다. 운영체제, 셸, 런타임, 패키지 관리자, 빌드 산출물
위치를 한 줄로 퉁치지 않고 실제 값으로 채우게 했습니다. Windows에서 Unix 명령을 가정하거나,
저장소 안에 빌드 폴더를 남기거나, 서로 다른 패키지 관리자를 섞는 일은 모델의 지능보다 빈 환경 칸에서
시작하는 경우가 많습니다.

마지막으로 완료의 뜻을 보강했습니다. 코드를 바꿨다는 사실과 요청한 동작이 이어진다는 사실은 다릅니다.
위험에 맞는 테스트, 공개 화면의 직접 확인, 확인하지 못한 항목의 분리까지 끝나야 완료라고 말하게
했습니다. 이렇게 문서와 실제 작업의 거리가 발견되면 글만 고치는 대신 템플릿도 같은 자리에서 고쳐야
합니다.

## 작은 저장소는 네 줄부터 적습니다

![네 개의 기본 도구만 갖춘 작고 단단한 저장소 작업대](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/2f/2fbb1e26b069ae904ed8e058a3071a37e7c3dc9440b87bc7445b060bc11e1217.webp "작은 저장소는 소유 범위, 명령, 진입 파일, 실제 실패 하나부터 적습니다")

환경을 만든다고 100줄짜리 규칙부터 쓸 필요는 없습니다. 오히려 처음에는 아래 네 가지면 충분합니다.

1. 이 저장소가 소유하는 것과 소유하지 않는 것을 한 문단으로 씁니다.
2. 설치, 테스트, 빌드 명령을 복사해서 실행할 수 있게 둡니다.
3. 진입 파일 세 곳과 절대 깨면 안 되는 경계 하나를 적습니다.
4. 최근 실제로 겪은 실패 하나를 행동 규칙으로 바꿉니다.

그다음 README 문장 하나처럼 작은 작업을 맡깁니다. AI가 같은 질문을 되풀이하거나 잘못된 명령을
고른다면 그 지점에 필요한 규칙 한 줄을 추가합니다.

여기에도 함정은 있습니다. 현재 코드와 문서에서 다시 알 수 있는 사실을 모두 강행규칙에 복사하면
파일은 빠르게 낡습니다. "컴포넌트는 37개"보다 "컴포넌트 진입점은 이 파일"이 오래 갑니다. 계획을
현재 계약처럼 쓰는 것도 피해야 합니다. AI는 문서에 적힌 미래형 설계를 이미 존재하는 구조로 믿고
없는 코드를 찾기 시작합니다.

규칙 파일은 길 필요가 없습니다. AI가 추측한 자리에 확인한 파일이나 명령 한 줄을 추가하면 됩니다.

## 문서와 실제 명령이 다르면 문서를 고칩니다

![안전한 기본 경로 옆에서 새로운 증거에 따라 다시 열리는 판단의 갈림길](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/74/742afbe9dcc6fa1b3572d7c705e355ce3c64e25d877bd728a81f120318b1fbb0.webp "문서의 명령이 실패하면 패키지 설정, 프로세스 종료, 산출물 경로를 다시 확인합니다")

규칙 파일도 코드가 바뀌면 낡을 수 있습니다. 문서와 실제 실행 결과가 다르면 다음 순서로 확인합니다.

만약 테스트 명령이 문서에는 맞지만 실제로 실패한다면, 제품 결함이라고 바로 결론 내리지 않습니다.
명령이 현재 패키지 설정과 이어지는지, 프로세스가 끝났는지, 산출물 경로가 바뀌지 않았는지를 먼저
봅니다. 문서가 낡았다는 증거가 나오면 코드에 맞춰 같은 작업에서 고칩니다.

만약 기존 변경과 내 작업이 겹친다면, 깨끗한 작업 트리를 만들겠다는 이유로 남의 변경을 지우지
않습니다. 겹치는 파일과 부분을 확인하고, 보존한 채 합칠 수 없을 때만 사람의 결정을 요청합니다.
여기서 확인할 것은 `git status`가 깨끗한지가 아니라 서로의 의도가 보존됐는지입니다.

같은 실수가 다시 나오면 `CLAUDE.md`를 열어 해당 규칙의 위치와 문장을 확인합니다. AI가 규칙을 읽지
못했다면 파일 앞쪽으로 옮기고, `안전하게 검증한다`처럼 행동이 없는 문장은 실제 명령으로 바꿉니다.
예를 들어 테스트 실수가 반복되면 `테스트한다` 대신 `cd site && npm test`라고 적습니다.

프롬프트에는 이번 작업을 적습니다. 제품 범위, 먼저 읽을 파일, 확인 순서, 테스트 명령은
`CLAUDE.md`에 적습니다. AI 모델을 바꾸기 전에 새 세션이 이 파일을 읽는지부터 확인합니다.
