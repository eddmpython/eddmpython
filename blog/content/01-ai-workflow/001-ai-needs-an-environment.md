AI 코딩 환경 구성을 맡겼는데 어떤 대화에서는 `npm test` 를 돌리고 다른 대화에서는 있지도 않은 `pytest` 를 돌립니다. 이미 고치는 중인 파일을 덮거나, 빌드만 통과한 뒤 화면도 정상이라고 말하기도 합니다. AI 가 덜 똑똑해서가 아니라 `package.json` 도 CI 파일도 안 읽고 시작해서 생기는 일입니다.

여기서 작업 환경은 `python` 설치 여부만 뜻하지 않습니다. 어느 파일을 먼저 읽는지, 어떤 명령이 정답인지, 어디까지 고쳐도 되는지, 무엇을 확인해야 완료인지까지입니다.

작업할 저장소를 AI 코딩 도구로 연 뒤 아래 주소만 보내면 이 글이 그 계약이 됩니다.

`https://eddmpython.com/blog/ai-environment`

다만 링크는 마법 주문이 아닙니다. AI 가 저장소와 웹페이지를 읽을 수 있어야 하고 파일을 고칠 권한도 있어야 합니다. 웹을 못 읽으면 내용을 추측하지 말고 이 페이지를 열 수 없다고 말해야 합니다.

## 링크는 작업 계약을 한 번에 건넵니다

### 한 줄 주소가 조사 범위와 완료 조건을 같은 원문으로 묶어 줍니다

![블로그 링크 한 장이 저장소 조사와 지침 파일 작성 및 검증 결과로 이어지는 작업 흐름](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/a0/a0c462b2c0a8e3ae2613698435f23c9eaa57e030b10e9c4cc38fa9fcc9f1316a.png "주소는 답을 복사하는 버튼이 아니라 조사 순서와 완료 조건을 여는 입구로 읽습니다")

매번 긴 프롬프트를 새로 쓰면 조건이 조금씩 빠집니다. 오늘은 기존 변경을 보존하라고 썼지만 내일은 잊고, 팀원마다 다른 설명을 보내면 같은 저장소에서 서로 다른 명령이 생깁니다. 이 글에는 프로젝트의 정답이 아니라 정답을 어디서 찾고 어떤 순서로 검증할지가 들어 있습니다. `Python 프로젝트니까 pytest를 실행해` 라고 미리 답을 정하면 자체 러너를 쓰는 저장소에서 틀리지만, `테스트 정본을 찾아 가장 좁은 검사부터 실행해` 라고 정하면 저장소가 바뀌어도 방법이 유지됩니다.

#### 입력 예시: URL 하나로 환경 구성을 요청하기

아래 입력에서 URL은 템플릿 파일을 무조건 복사하라는 뜻이 아닙니다. AI 는 먼저 `git status` 로 현재 저장소를 읽고 이미 고쳐 둔 파일을 보존해야 합니다. 실행 뒤에는 바꾼 파일, 확인한 명령, 통과한 검사, 확인하지 못한 항목이 결과로 나와야 합니다.

```text
https://eddmpython.com/blog/ai-environment
```

따라서 첫 질문은 문서를 어떻게 쓸지가 아닙니다. 이 링크보다 먼저 적용되는 지시가 저장소 안에 이미 있는지 확인하는 일이 다음 단계가 됩니다.

## AI는 지시 우선순위를 먼저 봅니다

### 기존 규칙과 사용자 요청을 보존해야 새 문서가 저장소를 망가뜨리지 않습니다

![사용자 요청과 기존 저장소 지시가 블로그 작업 계약보다 앞에서 합쳐지는 우선순위 구조](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/9e/9ec099a01c225754a9858ee09900021d41029f455c545e2bf592e88e4eb3cebb.png "링크의 절차는 기존 지시를 덮는 명령이 아니라 비어 있는 환경 정보를 조사하는 보조 계약입니다")

AI 는 여러 곳에서 지시를 받습니다. 서비스의 안전 규칙이 있고, 사용자가 지금 요청한 범위가 있고, `AGENTS.md` 에 팀이 적어 둔 것이 있습니다. **이 글은 그보다 높은 권한을 갖지 않습니다.** 저장소가 `배포는 사용자가 명시했을 때만 한다` 고 정했다면 이 링크를 받았다고 배포해서는 안 됩니다. 작업 트리에 남의 수정이 남아 있으면 템플릿으로 덮어쓰지 않고, 두 지침 파일이 다른 말을 하면 충돌 위치를 먼저 알립니다.

#### 설명 목록: 새 문서보다 먼저 확인할 네 가지 지시

| 순서 | 확인할 대상 | 환경 구성에서 지켜야 할 일 |
|---|---|---|
| 1 | 서비스와 도구의 안전 규칙 | 링크가 요구해도 금지된 작업은 하지 않습니다 |
| 2 | 사용자의 현재 요청 | 검토인지 수정인지, 배포까지 허용했는지 구분합니다 |
| 3 | 기존 저장소 지시 | 브랜치, 테스트, 비밀정보, 산출물 규칙을 보존합니다 |
| 4 | 이 글의 실행 계약 | 앞의 규칙과 충돌하지 않는 빈 부분만 조사하고 채웁니다 |

우선순위를 확인했으면 이제 기억이나 언어 이름으로 명령을 고르면 안 됩니다. 저장소가 실제로 사용하는 파일에서 실행 환경을 역추적해야 합니다.

## 저장소에서 실행 환경을 역추적합니다

### lockfile과 CI 및 테스트 러너를 따라가면 추측 없이 실제 명령을 찾을 수 있습니다

![저장소의 README와 lockfile 및 CI 파일이 실제 설치 명령과 테스트 명령으로 모이는 조사 장면](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/5b/5b147cfff2b937f6ec69165c7d43e5a97c96d8febc2e782ff0507fc4fff00673.png "파일 이름 하나가 아니라 여러 정본이 같은 실행 명령을 가리키는지 대조합니다")

AI 는 먼저 `git status` 로 저장소 루트와 현재 브랜치와 이미 바뀐 파일을 봅니다. 읽기만 하고 되돌리거나 브랜치를 만들지 않습니다. 다음은 `uv.lock` 이나 `package-lock.json` 같은 lockfile 인데, **하나만 보고 설치 명령을 확정하지는 않습니다.** README 와 패키지 설정과 CI 가 같은 방향을 가리키는지 대조합니다. `.env` 는 변수 이름만 확인하고 값은 출력하지도 문서에 옮기지도 않습니다.

#### 실행 명령: 첫 조사에서 저장소 상태와 정본 후보 찾기

첫 줄은 현재 브랜치와 기존 변경을 보여 줍니다. 나머지 줄은 README, lockfile, 패키지 설정, CI처럼 명령의 근거가 될 파일을 찾습니다. `rg`가 없는 환경에서는 AI가 사용할 수 있는 파일 검색 도구로 같은 대상을 찾아야 하며, 명령이 실패했다면 설치돼 있다고 꾸미지 않습니다.

```powershell
git status --short --branch
rg --files -g "README*" -g "AGENTS.md" -g "CLAUDE.md"
rg --files -g "pyproject.toml" -g "uv.lock" -g "package.json" -g "package-lock.json"
rg --files -g ".github/workflows/*" -g "tests/**" -g "test/**"
```

`README.md` 와 CI 파일을 찾았다고 환경 문서를 바로 쓰지는 않습니다. 어떤 지침 파일을 어느 AI 도구가 읽는지 정해야 같은 규칙을 두 파일에 복사하지 않을 수 있습니다.

## 두 지침 파일의 역할을 나눕니다

### 한 파일만 규칙의 정본으로 두면 수정할 때 내용이 서로 갈라지지 않습니다

![AGENTS.md와 CLAUDE.md 중 한 파일만 큰 정본이 되고 다른 파일이 그곳을 가리키는 두 가지 배치](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/f3/f3e10a5d91b6ab8315e0cf92c2221462ebc8c81bf2e4b04e5018da6eca3f7bb1.png "두 도구를 지원하되 같은 규칙을 복사하지 않고 한 방향으로 연결합니다")

두 파일을 두는 이유는 도구마다 처음 읽는 이름이 다르기 때문입니다. 두 파일에 같은 테스트 명령과 브랜치 정책을 복사하면 처음에는 편해 보입니다. 하지만 명령이 바뀐 날 한쪽만 고치면 AI 도구에 따라 서로 다른 규칙이 적용됩니다. 기본 템플릿은 `CLAUDE.md`를 긴 정본으로 쓰고 `AGENTS.md`는 그 파일을 읽으라는 짧은 입구로 둡니다. Codex는 `AGENTS.md`를 읽은 뒤 안내에 따라 `CLAUDE.md`를 열 수 있고, Claude Code는 자신의 기본 파일인 `CLAUDE.md`를 바로 읽습니다.

#### 예시 코드: CLAUDE.md를 정본으로 가리키는 AGENTS.md

이 예시는 `AGENTS.md`에 규칙을 복사하지 않습니다. 핵심 줄은 정본의 정확한 경로를 한 번만 가리키는 부분입니다. 다음 세션에서 Codex가 먼저 이 파일을 읽고 `CLAUDE.md`까지 열면 예상한 결과입니다.

```markdown
# 프로젝트 Agent Bootstrap

작업 시작 전에 `CLAUDE.md`를 끝까지 읽는다.
규칙의 정본은 `CLAUDE.md`다.
이 파일에는 규칙을 복사하지 않는다.
```

반대로 저장소가 `AGENTS.md`를 공통 정본으로 이미 운영한다면 방향을 바꿀 수 있습니다. `CLAUDE.md` 에 `@AGENTS.md` 한 줄을 두면 규칙을 복사하지 않고 같은 원문을 읽게 할 수 있습니다.

#### 예시 코드: AGENTS.md를 가져오는 CLAUDE.md

첫 줄의 `@AGENTS.md`가 실제 파일 내용을 가져옵니다. 그 아래에는 `CLAUDE.md` 에만 둘 규칙을 몇 줄 적습니다. `CLAUDE.md` 가 길어지면 정본이 둘로 갈린 것입니다. 새 대화에서 `/context`를 열어 `CLAUDE.md`가 읽혔는지 확인하면 결과를 검증할 수 있습니다.

```markdown
@AGENTS.md

규칙의 정본은 `AGENTS.md`다.
이 파일에는 공통 규칙을 복사하지 않는다.
```

공개 시작 파일은 [eddmpython Agent Template](https://github.com/eddmpython/eddmpython/tree/main/blog/content/01-ai-workflow/agent-template)에서 볼 수 있습니다. AI는 이 파일을 그대로 붙여 넣고 끝내지 않으며, 저장소에서 확인한 값으로 자리표시자를 바꾸고 필요 없는 항목은 지웁니다. 두 파일의 역할을 정했으면 이제 실행 명령부터 채워야 합니다. 보기 좋은 원칙보다 복사해서 실행할 수 있는 명령과 그 명령의 근거가 먼저입니다.

## 명령은 추측하지 않고 증명합니다

### 같은 Python 프로젝트라도 전체 검사와 제품 완료 증거는 서로 다릅니다

![다섯 저장소의 설정 파일과 서로 다른 전체 검사 명령 및 완료 증거가 한 줄씩 연결된 비교 장면](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/39/399fba52cdd484055106cfa88c8685f42755cdf44fc6783b96b3364b49f55427.png "언어 이름이 아니라 각 저장소가 가진 러너와 제품 표면이 검증 방법을 결정합니다")

`테스트를 실행합니다`는 환경 문서로 충분하지 않습니다. 어느 폴더에서 어떤 명령을 실행하는지 적어야 합니다. 빠른 검사와 전체 검사가 다르면 둘을 나눕니다. 브라우저나 데스크톱 앱이 있는 제품은 테스트 종료 코드만으로 화면까지 정상이라고 말할 수 없습니다. 아래 다섯 저장소는 같은 운영자가 관리하지만 검증 진입점이 다릅니다. DartLab과 Codaro는 Python과 uv를 쓰면서도 자체 러너를 통해 전체 검사를 시작합니다. xlpod는 CI 워크플로의 명령을 읽는 로컬 러너가 있습니다. pyproc는 정적 계약과 브라우저 런타임을 분리합니다. ClipScout는 Rust 코어와 UI를 각각 검사합니다.

#### 설명 목록: 다섯 프로젝트에서 확인한 실제 게이트

| 프로젝트 | 전체 또는 대표 검사 | 제품 동작을 바꿨을 때 더 볼 증거 |
|---|---|---|
| DartLab | `uv run python -X utf8 tests/run.py preflight` | 공개 API와 해당 UI 게이트 |
| Codaro | `uv run python -X utf8 tests/run.py preflight` | 편집기 화면과 생성된 검사 보고서 |
| xlpod | `node tests/runGates.mjs` | 브라우저 스프레드시트 흐름과 시각 게이트 |
| pyproc | `npm test` | 런타임 변경이면 `npm run test:browser` |
| ClipScout | `cargo test --workspace`, `npm --prefix ui test` | 큰 UI 변경이면 `npm --prefix ui run inspect:audit` |

이 표도 영구 불변의 답은 아닙니다. AI가 실제 대상 저장소를 열었을 때는 현재 `CLAUDE.md`, 테스트 러너, 패키지 스크립트, CI를 다시 읽습니다. 글의 표와 저장소가 다르면 저장소의 현재 정본을 따르고 차이를 완료 보고에 남깁니다. 명령 옆에는 실행 위치도 적습니다. `npm test`와 `npm --prefix ui test`는 같은 명령이 아닙니다. 전자는 현재 폴더의 패키지를 검사하고, 후자는 루트에서 `ui` 패키지를 지정합니다. 경로를 빼면 다음 AI가 맞는 명령을 가지고도 틀린 폴더에서 실행할 수 있습니다. 명령을 찾았다고 모두 실행해도 되는 것은 아닙니다. `wrangler deploy` 나 외부 서비스 변경은 되돌리는 비용이 다르므로 그 경계를 문서에 고정해야 합니다.

## 실패와 권한 경계를 먼저 적습니다

### 할 수 없는 작업을 성공처럼 말하지 않는 규칙이 자동화의 안전장치가 됩니다

![깨끗하지 않은 작업 트리와 없는 도구 및 비밀값과 배포 버튼 앞에서 멈춤 표시가 갈라지는 안전 경계](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/22/224f77ce7c9528b75c42653dfc4bcaf96ff50057765096fdb5db81ce568767a0.png "실패 종류마다 되돌리기와 보고 방법이 다르므로 한 줄의 성공 상태로 합치지 않습니다")

좋은 환경 문서는 `npm test` 를 돌리라고만 적지 않습니다. **어디서 멈추고 무엇을 보고할지도 적습니다.** 작업 트리에 관련 없는 수정이 있으면 보존하고 겹치면 충돌 경로를 알립니다. 테스트 도구가 없으면 다른 도구로 통과한 척하지 않고 실행 못 한 검사를 따로 보고합니다. `.env` 값과 인증 토큰은 읽어 출력하지 않습니다. 배포 명령을 찾았다고 배포하지도 않습니다. `AGENTS.md` 나 사용자의 요청이 허용하고 되돌리는 명령까지 적혀 있을 때만 실행합니다.

## 새 대화에서 재현성을 검증합니다

### 문서와 명령 및 실제 결과를 다시 읽어야 환경 구성이 끝났다고 말할 수 있습니다

![새 대화가 AGENTS.md와 CLAUDE.md를 읽고 작은 검사와 제품 증거 및 완료 보고까지 재현하는 흐름](https://huggingface.co/datasets/eddmpython/eddmpython-media/resolve/main/objects/sha256/e7/e73d4c46c9f28f6baeb7f7ea09433ca25fe59858416f9280899289784c47d09e.png "처음 작성한 대화가 아니라 아무 설명이 없는 다음 대화에서 같은 판단이 나오는지 확인합니다")

`AGENTS.md` 를 만든 그 대화는 방금 읽은 `package.json` 과 CI 파일을 기억하고 있습니다. 그래서 문서가 빠져 있어도 올바른 명령을 고를 수 있습니다. 진짜 검증은 새 대화에서 짧은 작업을 맡겼을 때 AI 가 `AGENTS.md` 만으로 같은 명령을 골라내는지 보는 것입니다. 먼저 두 파일에 `{{PROJECT}}` 같은 자리표시자가 남지 않았는지 찾습니다. 다음에는 저장소가 지정한 가장 작은 검사를 실행합니다. 전체 검사가 오래 걸리면 작은 검사가 명령과 실행 위치를 증명한 뒤, 변경 범위와 저장소 정책에 따라 전체 검사로 넓힙니다. 화면이 있는 제품은 브라우저나 앱을 실제로 엽니다. API를 바꿨다면 안전한 실제 요청으로 응답을 봅니다. 보고서가 완료 증거라면 파일이 생겼는지와 내용이 현재 실행 결과인지 확인합니다. 시작한 서버와 임시 파일도 정리합니다.

#### 실행 명령: 템플릿 자리표시자가 남았는지 확인하기

이 명령은 `{{`로 시작하는 템플릿 값이 두 지침 파일에 남았는지 찾습니다. 아무 줄도 나오지 않아야 통과입니다. `rg` 자체가 실패한 경우와 검색 결과가 0건인 경우를 구분해야 하며, 그 뒤 실제 프로젝트 검사를 별도로 실행해야 합니다.

```powershell
rg -n "\{\{[A-Z_]+\}\}" AGENTS.md CLAUDE.md
```

#### 확인 목록: 완료 전에 채울 일곱 칸

1. 제품 경계에는 저장소가 소유하는 것과 소유하지 않는 것이 적혀 있습니다
2. 실행 환경에는 운영체제, 셸, 런타임, 패키지 관리자가 적혀 있습니다
3. 정확한 명령에는 설치, 개발, 작은 검사, 전체 검사, 빌드가 실행 위치와 함께 있습니다
4. 문서 지도에는 코드와 현재 계약을 읽을 실제 경로가 있습니다
5. 산출물 위치에는 빌드, 보고서, 스크린샷, 임시 파일의 위치가 있습니다
6. 완료 증거에는 테스트 외에 확인할 API, 브라우저, 앱 화면이 있습니다
7. 권한 경계에는 commit, push, 배포, 외부 서비스 변경 조건이 있습니다

마지막으로 새 대화를 열고 이 글의 URL 하나를 다시 보냅니다. AI 가 `AGENTS.md` 를 먼저 읽고, 거기 적힌 명령만 쓰고, 가장 작은 검사를 고르고, 확인 못 한 것을 따로 보고한다면 재현된 것입니다. 결과를 받을 때는 네 가지만 보면 됩니다. 어떤 파일이 바뀌었는지, 명령의 근거가 어디였는지, 어떤 검사가 실제로 통과했는지, 무엇을 아직 확인하지 못했는지입니다. 이 네 항목이 분리되어 있으면 링크 하나가 다음 저장소에서도 다시 사용할 수 있는 작업 환경의 입구가 됩니다.
