# Agent Template

AI 코딩 에이전트가 프로젝트를 처음 열어도 같은 경계 안에서 조사하고, 고치고, 검증하게 만드는
저장소용 작업 환경 템플릿입니다. 더 영리한 답을 끌어내는 프롬프트 모음이 아닙니다.

DartLab, Codaro, xlpod, pyproc을 만들면서 실제로 사고가 났던 지점을 역산해 남겼습니다. 종료를
기다리지 않은 검사를 제품 실패로 보고한 일, 지킬 코드가 없는데 게이트만 늘린 일, 참조 대상을
읽지 않고 "반영했다"고 말한 일 같은 것들입니다.

## 왜 파일이 두 개인가

AI 코딩 도구가 처음 찾는 파일 이름이 하나로 통일되어 있지 않기 때문입니다. Claude는
`CLAUDE.md`를 읽고, Codex를 비롯한 여러 에이전트는 `AGENTS.md`를 먼저 읽습니다. 한 파일만 두면
다른 이름을 찾는 도구는 프로젝트 규칙을 모르고 시작할 수 있습니다.

이 템플릿을 처음 공개할 때는 이미 `CLAUDE.md`에 규칙 본문이 자리 잡고 있었습니다. 그래서 기존
본문을 옮기지 않고 `AGENTS.md`를 짧은 연결 파일로 붙였습니다. 현재 기본 배치는 다음과 같습니다.

- `CLAUDE.md`는 제품 경계, 실행 환경, 검증, 버전 관리 규칙의 정본입니다.
- `AGENTS.md`는 짧은 진입점입니다. 규칙을 복제하지 않고 `CLAUDE.md`로 보냅니다.

이 배치는 도구의 우선순위를 뜻하지 않습니다. 새 프로젝트가 `AGENTS.md`를 주로 읽는 에이전트 중심이면
역할을 바꿔도 됩니다. 규칙 본문을 `AGENTS.md`에 두고, `CLAUDE.md`에는 `AGENTS.md`를 먼저 읽으라는
짧은 진입점만 둡니다.

지켜야 할 것은 파일 이름이 아니라 **정본이 하나라는 원칙**입니다. 두 파일에 같은 규칙을 복사하면
한쪽만 고친 날부터 작업 환경이 갈라집니다. 어느 쪽을 정본으로 골라도 다른 파일은 정확히 그 정본을
가리키고, 충돌하면 어느 쪽이 이기는지 적어야 합니다.

## 적용 순서

1. 두 파일을 프로젝트 루트에 복사합니다.
2. 아래 자리표시자를 실제 명령과 경계로 바꿉니다.
3. `{{`가 남았는지 검색합니다.
4. 새 대화에서 에이전트가 진입 파일과 정본을 읽는지 확인합니다.
5. 가장 작은 실제 변경 하나를 맡겨 검색, 수정, 검증, 보고 흐름을 점검합니다.

```bash
rg -n "\{\{[A-Z_]+\}\}" CLAUDE.md AGENTS.md
```

`AGENTS.md`를 정본으로 쓰려면 현재 두 파일의 역할을 맞바꿉니다. `AGENTS.md`에 규칙 본문을 두고,
`CLAUDE.md`의 진입 문장은 아래처럼 바꿉니다.

```markdown
# {{PROJECT}} Claude Bootstrap

작업 시작 전에 `AGENTS.md`를 끝까지 읽는다. 규칙의 정본은 그 파일이다.
이 파일은 규칙을 담지 않으며, 충돌하면 `AGENTS.md`가 이긴다.
```

| 자리표시자 | 예 |
|---|---|
| `{{PROJECT}}` | `dartlab` |
| `{{MAIN_BRANCH}}` | `main` |
| `{{INSTALL_CMD}}` | `npm install` |
| `{{DEV_CMD}}` | `npm run dev` |
| `{{TEST_CMD}}` | `npm test` |
| `{{BUILD_CMD}}` | `npm run build` |
| `{{DEPLOY_CMD}}` | `npm run deploy` |
| `{{BUILD_OUT_DIR}}` | `../project.out/dist` |
| `{{COMMIT_LANG}}` | `한국어` |
| `{{CHAT_LANG}}` | `한국어` |
| `{{SECRET_STORES}}` | `.env`, GitHub Secrets |
| `{{DOCS_DIR}}` | `docs/` |
| `{{TRACKER}}` | `plan/`, 이슈 트래커 |
| `{{BOUNDARY}}` | 이 저장소가 소유하는 것과 소유하지 않는 것 |
| `{{ENVIRONMENT}}` | 운영체제, 셸, 런타임, 패키지 관리자, 산출물 경로 |
| `{{INVARIANT}}` | 깨면 안 되는 계층 방향과 공개 API 표면 |
| `{{CODE_MAP}}` | 진입점 파일과 핵심 모듈 위치 |
| `{{PITFALL}}` | 메모리 제약, 플랫폼 고유 함정 |

마지막 다섯 개가 실제로 프로젝트를 구분하는 부분입니다. 저장소를 읽지 않고 다른 프로젝트의
값을 복사하지 않습니다.

## 무엇을 적어야 하나

좋은 환경 문서는 에이전트가 바로 행동을 고를 수 있게 합니다.

| 약한 문장 | 행동을 고를 수 있는 문장 |
|---|---|
| 테스트를 잘한다 | 변경 파일은 `npm test`, 공개 화면은 데스크톱과 모바일 렌더까지 확인한다 |
| 비밀을 조심한다 | 값은 `.env`와 GitHub Secrets에만 두고 로그와 예제 파일에는 변수 이름만 둔다 |
| 아키텍처를 지킨다 | UI는 `src/data/client.ts`만 호출하고 컴포넌트의 직접 `fetch`를 금지한다 |

명령은 복사해서 실행할 수 있어야 하고, 코드 지도는 실제 진입 파일을 가리켜야 합니다. 실행 환경에는
운영체제와 셸, 런타임 버전, 패키지 관리자, 빌드 산출물 위치를 적습니다. 에이전트가 추측해야 하는
칸이 남으면 그 추측이 세션마다 달라집니다.

## 유지 기준

**길어지면 앞부분만 지켜집니다.** 규칙을 추가하기 전에 두 가지를 확인합니다.

- 이 항목을 어겨서 실제로 사고가 났거나, 저장소 경계를 바꾸는가. 둘 다 아니면 넣지 않습니다.
  예방 차원의 일반론은 노이즈가 되고, 노이즈가 늘면 진짜 규칙의 밀도가 떨어집니다.
- 이 사실이 다른 문서에 이미 있는가. 있으면 포인터만 둡니다.

코드와 절차가 바뀌면 같은 작업에서 템플릿도 고칩니다. 반대로 아직 만들지 않은 계획을 현재 규칙처럼
쓰지 않습니다. 규칙은 희망 사항이 아니라 지금 작업자가 딛는 바닥이어야 합니다.
