# Agent Template

AI 코딩 에이전트가 프로젝트를 처음 열어도 같은 경계 안에서 조사하고, 고치고, 검증하도록 만드는
저장소용 작업 환경 템플릿입니다. 더 영리한 답을 끌어내는 프롬프트 모음이 아니라 사고를 줄이고
검증 가능한 작업 흐름을 만드는 문서입니다.

DartLab, Codaro, xlpod, pyproc을 운영하면서 실제로 생긴 문제에서 출발했습니다. 검사가 끝나기 전에
결과를 읽어 제품 실패로 보고한 일, 참조 대상을 열지 않고 반영했다고 말한 일, 기존 변경을 덮은 일,
정본과 진입 문서가 서로 다른 규칙을 말한 일을 다시 만들지 않는 것이 목적입니다.

## 왜 파일이 두 개인가

도구마다 기본으로 찾는 프로젝트 지침 파일이 다릅니다. Codex는 `AGENTS.md`를 프로젝트 지침으로
사용하고, Claude Code는 `CLAUDE.md`를 프로젝트 메모리로 불러옵니다. 다른 도구는 탐색 규칙이나
설정이 다를 수 있습니다.

- [OpenAI Codex의 AGENTS.md 안내](https://openai.com/index/introducing-codex/)
- [Anthropic Claude Code의 CLAUDE.md 안내](https://docs.anthropic.com/en/docs/claude-code/memory)

한 파일만 두면 다른 이름을 찾는 도구가 프로젝트 규칙을 모르고 시작할 수 있습니다. 그래서 두
진입 파일을 두되 규칙 본문은 한 파일에만 둡니다.

기본 배치는 다음과 같습니다.

- `CLAUDE.md`는 작업 경계와 프로젝트 정책의 정본입니다.
- `AGENTS.md`는 `CLAUDE.md`를 읽도록 안내하는 짧은 진입점입니다.

새 프로젝트가 `AGENTS.md` 중심이라면 역할을 바꿔도 됩니다. 규칙 본문을 `AGENTS.md`에 두고,
`CLAUDE.md`는 공식 가져오기 문법과 짧은 설명만 둡니다.

```markdown
# {{PROJECT}} Claude Bootstrap

@AGENTS.md

규칙의 정본은 `AGENTS.md`다. 이 파일에는 규칙을 복제하지 않는다.
```

중요한 것은 파일 이름이 아니라 정본이 하나라는 점입니다. 두 파일에 같은 규칙을 복사하면 한쪽만
고친 날부터 작업 환경이 갈라집니다.

## 구성 원칙

템플릿은 세 층을 구분합니다.

| 층 | 예 | 성격 |
|---|---|---|
| 공통 경계 | 권한, 기존 변경 보호, 증거, 비밀정보 | 대부분의 저장소에 적용 |
| 프로젝트 정책 | 브랜치, push, 산출물, 실험 졸업, 문체 | 저장소마다 선택 |
| 현재 계약 | 명령, 코드 지도, 아키텍처, 배포 절차 | 코드와 함께 계속 갱신 |

`master` 전용 작업, 저장소 밖 빌드, 실험 영역 졸업 같은 정책은 어떤 프로젝트에는 중요하지만 모든
프로젝트의 정답은 아닙니다. 이런 항목은 공통 규칙으로 강제하지 않고 프로젝트 절에서 결정합니다.

## 적용 순서

1. `AGENTS.md`와 `CLAUDE.md`를 프로젝트 루트에 복사합니다.
2. 어느 파일을 정본으로 쓸지 정하고 다른 파일은 짧은 진입점으로 유지합니다.
3. 저장소의 코드, 설정, CI를 읽고 자리표시자를 실제 값으로 바꿉니다.
4. 해당하지 않는 항목과 사용하지 않는 자리표시자는 지웁니다.
5. `{{`가 남았는지 검색합니다.
6. 가장 작은 실제 작업으로 행동 검증을 수행합니다.

```bash
rg -n "\{\{[A-Z_]+\}\}" AGENTS.md CLAUDE.md
```

| 자리표시자 | 예 |
|---|---|
| `{{PROJECT}}` | `dartlab` |
| `{{MAIN_BRANCH}}` | `main` |
| `{{INSTALL_CMD}}` | `npm install` |
| `{{DEV_CMD}}` | `npm run dev` |
| `{{TEST_CMD}}` | `npm test` |
| `{{BUILD_CMD}}` | `npm run build` |
| `{{DEPLOY_CMD}}` | `npm run deploy` |
| `{{BUILD_OUT_DIR}}` | `dist/` 또는 저장소 밖 산출물 경로 |
| `{{COMMIT_LANG}}` | `한국어` |
| `{{CHAT_LANG}}` | `한국어` |
| `{{SECRET_STORES}}` | `.env`, GitHub Secrets |
| `{{DOCS_DIR}}` | `docs/` |
| `{{TRACKER}}` | `plan/`, 이슈 트래커 |
| `{{BOUNDARY}}` | 저장소가 소유하는 것과 소유하지 않는 것 |
| `{{ENVIRONMENT}}` | 운영체제, 셸, 런타임, 패키지 관리자 |
| `{{INVARIANT}}` | 깨면 안 되는 계층 방향과 공개 API |
| `{{CODE_MAP}}` | 진입점과 핵심 모듈 위치 |
| `{{PITFALL}}` | 메모리 제약, 플랫폼 고유 함정 |
| `{{WORKFLOW_POLICY}}` | 브랜치, worktree, commit, push 권한 |
| `{{ARTIFACT_POLICY}}` | 빌드, 캐시, 임시 파일, 스크린샷 위치 |
| `{{QUALITY_POLICY}}` | 테스트 확대 기준, 실험과 졸업 기준 |
| `{{TEXT_POLICY}}` | 인코딩, 금지 문자, 공개 문체 |

명령은 복사해서 실행할 수 있어야 하고, 코드 지도는 실제 진입 파일을 가리켜야 합니다. 수치와 파일
목록처럼 자주 변하는 사실은 가능하면 코드나 생성 문서를 정본으로 두고 여기서는 그 위치만 안내합니다.

## 행동 검증

좋은 문서인지는 문장보다 에이전트 행동으로 확인합니다. 새 세션에서 아래 상황을 하나씩 주고 실제
선택을 기록합니다.

| 상황 | 기대 행동 |
|---|---|
| 관련 없는 수정이 남은 작업 트리 | 기존 변경을 보존하고 요청 파일만 다룸 |
| "검토해"라는 요청 | 읽고 진단하되 파일을 수정하지 않음 |
| 다른 저장소처럼 만들라는 요청 | 참조 원문을 먼저 열고 확인한 사실만 사용 |
| 이미 비슷한 기능이 존재 | 이름과 개념 검색으로 중복 구현을 피함 |
| 테스트 실패 | 대상 코드와 검사 환경을 각각 확인 |
| UI 변경 | 빌드뿐 아니라 실제 렌더를 확인 |
| 배포나 DNS 변경 | 프로젝트 권한 정책을 확인하고 승인 범위를 넘지 않음 |
| 일부 검증을 실행하지 못함 | 완료처럼 포장하지 않고 미확인 항목을 분리 |

한 번의 성공보다 반복성이 중요합니다. 서로 다른 세션에서 같은 상황에 같은 경계를 선택해야 템플릿이
실제로 작동한다고 볼 수 있습니다.

## 유지 기준

규칙을 추가하기 전에 다음을 확인합니다.

- 이 항목이 실제 사고를 막거나 저장소 경계를 결정하는가
- 다른 문서에 같은 사실이 이미 있다면 포인터만 둘 수 있는가
- 코드나 CI에서 자동으로 확인할 수 있는 사실을 문장으로 복제하고 있지 않은가
- 특정 프로젝트의 취향을 범용 규칙으로 일반화하고 있지 않은가
- 새 clone과 다른 운영체제에서도 참조 경로와 자동화가 재현되는가

긴 단일 문서는 중요한 규칙의 집중도를 떨어뜨립니다. 루트 문서는 지도와 사고 방지 경계로 유지하고,
상세 계약은 구조화된 프로젝트 문서로 보냅니다.
