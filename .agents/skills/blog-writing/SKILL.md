# 토탈 블로그 작가 파이프라인

제목, 검색 약속, 본문, 이미지가 질문 하나에 같은 답을 하게 만든다. 블로그는 강의 요약문이 아니라
검색과 공유 링크에서 한 편만 열어도 완결되는 독립 지식 원문이다. 강의 슬라이드는 완성된 블로그를
참조하며 강의 시간과 차시가 글의 깊이를 줄이지 못한다. 독자가 실제로 보는 화면, 누르는 버튼,
실행하는 명령, 확인하는 결과를 중심으로 쓴다. 개념어와 비유는 구체적인 설명을 대신할 수 없다.

## 1. 정본부터 읽기

작업 전에 다음 파일을 순서대로 읽는다.

- `CLAUDE.md`
- `blog/product-marketing.md`
- `blog/PIPELINE.md`의 1절부터 4절
- `skills/specs/operation/blogCopy.md`
- 고칠 글과 그 글이 설명하는 실제 코드, 문서, 화면

정확한 제품 동작을 확인할 수 없으면 단정하지 말고 뺀다. 저장소 안에 초안 메모나 임시 파일을 만들지
않는다.

## 2. 검색 약속과 독자를 함께 고정하기

초안보다 먼저 다음 네 답을 작업 메모에 적는다.

- 이 글을 여는 사람은 지금 무엇을 하려는가
- 그 사람은 어떤 말을 아직 모르는가
- 읽고 나서 처음 누르거나 실행할 것은 무엇인가
- 성공하면 화면이나 터미널에 무엇이 보이는가

네 답 중 하나라도 비어 있으면 자료를 더 확인한다.

이어서 다음 네 값을 정한다.

- `primaryKeyword`: 독자가 실제로 찾을 두 단어 이상의 검색어
- `searchIntent`: explanation, how-to, troubleshooting, comparison 중 하나
- `title`: 검색어와 문제, 질문, 결과 후크를 함께 담은 15자 이상 60자 이하 문장
- `summary`: 검색어, 읽어서 얻는 결과, 다룰 범위를 담은 한두 문장

제목에서 제품명을 지워도 독자의 문제가 남아야 한다. 제목, summary, 도입 두 문단에 핵심 검색어의
주요 단어가 모두 들어가야 한다. 제목만 크게 약속하고 본문에서 답하지 않는 후크는 쓰지 않는다.

## 3. 주제 하나를 정하고 기승전결을 잡는다

`order.json`은 공개 목록 순서만 제공한다. 강의 시간, 차시, 슬라이드 수를 글 분량과 목차의 상한으로
쓰지 않는다. 강의 운영표도 글쓰기 지시서가 아니다. 초안보다 먼저 다음 여덟 줄을 적는다.

- 질문에 대한 직접 답
- 반드시 풀어 쓸 용어와 정의
- 그렇게 동작하는 이유와 내부 관계
- 입력, 행동, 출력이 모두 있는 완성 예제
- 비슷한 선택지와 다른 점
- 실패 사례 또는 경계값과 복구
- 독자가 결과를 확인할 기준
- 적용 범위와 적용하면 안 되는 범위

빈 줄이 있으면 초안을 쓰지 않고 실제 코드, 화면, 공식 문서, 실행 결과를 더 확인한다. 분량은 목표가 아니다. 한 편은 주제 하나에 답하고, 그 주제를 끝까지 답했으면 짧아도 된다.
글자 수 하한은 쓰지 않는다. 하한에 미달할 때 가장 싼 해가 같은 사실의 재진술이라 반복을 직접 만든다.

## 4. 초안 전에 섹션 카드를 만든다

섹션 하나는 언제나 다음 순서로 구성한다.

```markdown
## 독자의 질문이나 행동이 보이는 제목

### 이 절에서 알게 될 결과를 쉬운 말로 적은 한 줄 부제

![본문과 직접 관련된 이미지 대체 텍스트](https://example.com/section-image.webp "이미지를 읽는 방법을 말하는 캡션")

이미지 다음에는 코드나 목록보다 서술형 설명을 먼저 둡니다. 낯선 말을 쉬운 말로 풀고, 독자가 할
행동과 화면이나 터미널에서 볼 결과를 첫 문단 두 문장부터 네 문장으로 설명합니다. 중심 절은 여기서
끝내지 않고 원리, 예제, 실패와 검증을 여러 문단으로 이어갑니다.
```

그 뒤 보조자료는 없어도 된다. 넣는다면 실행 가능한 코드, 입력과 결과가 있는 실제 예, 순서를 풀어 쓴
목록이나 표만 쓴다. 장식용 인용문, 링크 모음, 본문을 다시 줄인 요약은 보조자료가 아니다. 전체 양식은
[article-template.md](references/article-template.md)를 읽는다.

코드 블록에는 바로 위 범위에 H4 제목을 둔다. `코드`, `예시`처럼 역할만 적지 않고
`예시 코드: 금액 문자열을 숫자로 바꾸기`, `실행 명령: 전체 테스트 확인하기`,
`실패 예시: 없는 파일을 열었을 때`처럼 자료의 역할과 설명할 개념을 함께 쓴다. 코드 앞뒤의 서술에는
입력이 무엇인지, 핵심 줄이 무엇을 바꾸는지, 어떤 출력이 나와야 하는지를 합쳐 80자 이상 설명한다.
코드 줄 수와 코드 블록 수는 서술 본문 깊이로 계산하지 않는다.

H2를 같은 길이와 같은 문법의 카드로 맞추지 않는다. 짧은 문제 절, 긴 원리 절, 입력부터 출력까지
이어지는 실습 절, 실패와 한계를 다루는 절은 필요한 만큼 서로 다른 길이로 쓴다. 절 마지막에는 지금
확인한 결과가 현재 글 안의 다음 질문으로 왜 이어지는지 한 문장을 둔다.

## 5. 실제 동작부터 설명한다

도입 두 문단에 문제 장면과 이 글에서 얻는 결과를 바로 쓴다. 제품 역사, 업계 전망, 멋있어 보이는
비유로 시작하지 않는다.

각 설명은 가능한 한 다음 순서를 따른다.

1. 독자가 보는 이름을 쓴다
2. 독자가 하는 동작을 쓴다
3. 성공하거나 실패했을 때 보이는 결과를 쓴다

`환경`, `구조`, `흐름`, `경계`, `맥락`, `과정`, `방식`, `역할`, `가치`, `기반`, `가능성`, `판단`을
쓰려면 같은 문단에 파일, 화면, 버튼, 명령, 값, 오류 중 하나를 함께 적는다. 적을 수 없으면 그 문장을
지우거나 실제 예로 바꾼다.

비유는 먼저 있는 사실 설명을 짧게 기억시키는 용도로만 쓴다. 한 절에 한 문장을 넘기지 않는다.
`작업장`, `갈림길`, `여정` 같은 비유를 이어 붙여 제품 동작을 설명하지 않는다.

고치기 전과 후의 예는 [readability-cases.md](references/readability-cases.md)를 읽는다.

## 6. 이미지 브리프를 본문에서 뽑는다

본문을 쓰기 전에 이미지를 만들지 않는다. 각 H2의 첫 서술 문단까지 확정한 뒤 `blog/media/plan.json`에
다섯 값을 적는다.

- `sectionSubtitle`: 본문 H3와 똑같은 부제
- `contentAnchor`: 이미지가 설명할 본문 원문 한 문장
- `visualSubject`: 화면, 파일, 코드, 명령, 결과처럼 실제로 보여 줄 대상
- `visualRelationship`: 두 대상의 전후, 원인과 결과, 순서를 한 문장으로 설명
- `prompt`: 구도, 재질, 조명처럼 의미를 바꾸지 않는 장면 지시

제품 화면, 실제 코드, 공식 문서 모양이 중요하면 생성 이미지로 흉내 내지 말고 확인된 화면이나 공식
자료를 쓴다. 생성 이미지는 실제 화면이 존재하지 않는 개념, 전후 차이, 순서 설명에만 쓴다.
`generate_flux.py`는 자유 장면 지시 뒤에 제목, 부제, 본문 원문, 피사체, 관계를 강제로 붙인다.
자세한 선택 기준은 [image-brief.md](references/image-brief.md)를 읽는다.

새로 만들거나 교체하는 생성 이미지는 `visualProfile: eddmpython-dark-v2`와
`palettePolicy: eddmpython-carbon-ivory-sand-v1`을 쓴다. 배경은 `#101514`, 주요 밝은 면은
`#f5f3ee`, 유일한 작은 강조색은 `#d8be91`이다. 나머지는 저채도 흑연과 웜그레이만 허용한다. 파랑,
청록, 초록, 보라, 분홍, 빨강, 금색, 네온은 쓰지 않는다. 성공과 실패는 다른 색이 아니라 모양, 명암,
선 굵기와 위치로 구분한다. 실제 제품 스크린샷은 사실성을 위해 원래 색을 보존한다.

생성본은 대체 텍스트가 아니라 실제 픽셀을 직접 본다. `visualSubject`가 보이는지, 관계를 추측 없이 읽을
수 있는지, 글과 무관한 공방이나 길 같은 비유가 주인공이 되지 않았는지 확인한다. 통과한 파일만
`publish_media.py --reviewed`로 발행한다.

## 7. 네 평가자가 독립적으로 읽는다

초안을 다 쓴 뒤 문장마다 다음 중 하나를 표시한다.

- 확인한 사실
- 독자가 할 행동
- 화면이나 터미널에서 볼 결과
- 앞뒤 문장을 잇는 데 꼭 필요한 설명

어디에도 속하지 않으면 지운다. `이를 통해`, `이러한 방식`, `단순히 무엇을 넘어`, `혁신적인 흐름`처럼
내용 없이 문장을 크게 만드는 표현도 지운다.

다음 순서로 다시 읽는다.

1. 독립성 평가자: 다른 글과 강의 없이 질문, 용어, 예제를 이해할 수 있는지 확인한다
2. 깊이 평가자: 정의, 원리, 완성 예제, 실패, 반례나 한계, 검증이 빠지지 않았는지 확인한다
3. 연결 평가자: H2만 읽어도 질문이 이어지고 앞 절의 결과가 다음 절의 필요를 만드는지 확인한다
4. 실용성 평가자: 입력을 바꾸고, 실패를 복구하고, 결과가 맞는지 독자가 직접 확인할 수 있는지 본다

평가자는 각각 실패 이유와 고칠 위치를 남긴다. 단순히 `통과`만 적은 평가는 인정하지 않는다. 네
평가를 반영한 뒤 어려운 말이 처음 나온 자리에서 바로 풀렸는지, 같은 뜻을 되풀이한 문장과 비유가
없는지, 실제 말로 읽었을 때 어색하지 않은지 마지막으로 확인한다.

## 8. 검사하고 보고하기

사이트 디렉터리에서 다음 검사를 실행한다.

```powershell
npm run check:post -- <파일명>
```

`check:post` 는 그 한 편만 검사한다. 전체를 재는 `check:blog` 는 여러 글 사이의 관계만 본다.

검사가 통과해도 독립성, 깊이, 글맛, 이미지 의미가 자동으로 보장되지는 않는다. 마지막 보고에는 검색어와
제목 후크, 여덟 줄 깊이 설계 결과, 독자의 첫 행동, 각 절에 사용한 실제 예, 네 평가자의 실패와 수정
결과, 이미지 직접 검수 결과, 검사 결과를 한 줄씩 적는다. 강의와 연결할 때는 블로그가 참조 원문이고
슬라이드가 소비자라는 방향을 함께 확인한다.
