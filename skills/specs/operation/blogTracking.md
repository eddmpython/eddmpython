# 글 낡음 감시

글은 발행하는 순간부터 낡는다. 이 문서는 **밖에서만 확인되는 낡음**을 다룬다.

저장소 안에서 확인되는 낡음은 이미 게이트가 잡는다. 본문을 고치고 이미지 계획의
`contentAnchor` 를 안 고치면 `check:blog` 가 막는다. 2026-08-24 에 003 에서 그 사고가 났고
2026-08-26 에 004 에서 같은 사고를 그 검사가 다시 잡았다.

밖에서만 확인되는 낡음은 아무도 안 잡았다. 004 가 pandas 3.0.5 로 잰 4.1초와 560MB 를 표로
싣는데, pandas 가 메이저를 올려 기본 읽기 엔진이 바뀌면 그 표 전체가 근거 없는 주장이 된다.
방문자만 알고 글쓴이는 모른다.

## 기본은 알리는 데서 멈춘다

**아무것도 안 고르면 글쓴이에게 이슈 하나가 갈 뿐이다.** 본문도 사이트도 그대로다.
그 기본값이 이 도구의 경계이고 다른 모든 결정이 여기서 나온다.

이 사이트는 발행일과 수정일을 일부러 내보내지 않는다. `check:seo` 가
`article:published_time` 과 `article:modified_time` 을 막는다. 그래서 본문에 적힌
`이 글에서 쓴 버전은 pandas 3.0.5` 한 줄이 독자가 검증 시점을 아는 유일한 단서다.

기계가 그 줄만 최신으로 칠하면 뒤에 있는 숫자 스무 개는 그대로인 채 재현 조건만 새것인 글이
된다. 낡음의 흔적을 지우면서 낡음은 남기는 것이라 순 마이너스다. **그래서 본문 갱신은
기본값이 될 수 없다.** 다시 재고 다시 쓰는 것은 사람이 한다.

그런데 글마다 사정이 다르다. 004 처럼 표 스무 줄이 그 버전으로 잰 값이면 사람이 다시 재야
하고, 버전 한 줄만 적어 둔 글이면 그 줄을 갈아 끼우는 것으로 끝난다. **무엇이 맞는지는 글이
안다.** 그래서 고르는 자리를 글에 뒀다.

| 무엇 | 필드 | 안 고르면 |
|---|---|---|
| 어디로 알리나 | `notify` | `issue`. 글쓴이에게만 간다 |
| 본문을 고치나 | `update` | 안 고친다 |

두 필드는 아래 `알림 채널 고르기` 와 `본문 갱신 고르기` 에서 정한다. **`update` 를 달아도
기본 `mode` 는 `pr` 이라 사람이 diff 를 읽고 머지한다.** 기계가 바로 커밋하려면 그 글이
`commit` 을 명시해야 한다.

## 계획은 글 폴더가 소유한다

```text
blog/posts/004-dataframe-libraries/
  index.md      글
  media.json    이미지 계획
  cells.json    실습 칸
  track.json    감시 계획      <- 이 문서가 정하는 것
```

**파일이 있으면 추적하고 없으면 안 한다.** 002 처럼 밖에 매인 사실이 없는 글에 감시를 붙이면
알림이 소음이 된다. 지켜볼 것이 없으면 파일을 두지 않는다.

frontmatter 가 아니라 파일인 이유는 둘이다. 프론트매터 파서가 한 줄 정규식이라 배열을 못 받고
(`site/src/posts.ts`, `check-blog.mjs`, `check-seo.mjs` 세 곳을 고쳐야 한다), 발행할 때
추적을 정한다는 것이 파일을 만드는 행위로 그대로 표현된다.

```json
{
  "version": 1,
  "watch": {
    "polars": {
      "kind": "pypi",
      "package": "polars",
      "why": "지연 실행 판 두 행이 Polars 1.44.1 로 잰 값이다. 메이저가 바뀌면 scan_csv 와 collect 의 계약이 달라질 수 있다.",
      "anchor": "0.5초에 320MB입니다."
    }
  }
}
```

| 필드 | 필수 | 무엇 |
|---|---|---|
| `kind` | 예 | 감시 종류. 아래 표의 값만 쓴다 |
| `why` | 예 | **이 변화가 이 글의 무엇을 흔드는가** |
| `anchor` | 아니오 | 흔들리는 본문 문장. 적으면 본문에 살아 있는지 함께 검사한다 |
| `notify` | 아니오 | 알림 채널 목록. 안 적으면 `["issue"]` |
| `update` | 아니오 | 본문을 고칠 규칙. 안 적으면 안 고친다 |
| kind 별 필드 | kind 마다 | 아래 표 |

감시 id 는 소문자와 숫자와 하이픈만 쓴다. 글 안에서만 겹치지 않으면 된다. 상태 키가
`<글 폴더>/<감시 id>` 라서 글 사이에서는 겹쳐도 된다.

### why 가 필수인 이유

알림이 `polars 1.45.0 이 나왔다` 로 끝나면 읽는 사람이 매번 글을 다시 열어 무엇이 걸리는지
찾아야 한다. 그러면 몇 번 만에 안 읽게 되고, 안 읽는 알림은 없는 알림보다 나쁘다. 무엇이
흔들리는지를 계획에 미리 적어 두면 알림 한 줄로 판단할 수 있다.

`check:blog` 가 빈 `why` 를 막는다.

### anchor 는 언제 다는가

글이 확정된 뒤에 단다. 수치를 다시 재는 동안에는 비워 둔다. 본문이 흔들리는 중에 anchor 를
박으면 글을 고칠 때마다 게이트가 막아 글쓰기를 방해한다.

발행할 때 달아 두면 그 다음부터는 본문의 그 문장을 고칠 때 감시도 같이 보게 된다. 004 는
발행 전이라 비어 있고 003 은 발행됐으므로 달려 있다.

### 알림 채널 고르기

```json
"notify": ["issue", "comment"]
```

| 채널 | 누가 보나 | 무엇이 필요한가 |
|---|---|---|
| `issue` | 글쓴이 | 없음. 기본값이다 |
| `comment` | **독자와 글쓴이** | 없음. 그 글의 Discussions 스레드에 단다 |
| `mail` | 글쓴이 | 발송 시크릿 |

**`comment` 는 독자가 보는 표면에 봇이 글을 남기는 것이다.** 되돌리기 어려우므로 기본값이
아니다. 그 글이 명시적으로 고를 때만 달린다.

댓글은 giscus 가 그리고 giscus 는 `data-strict="1"` 로 돈다. strict 는 discussion 제목이
아니라 **본문에 박힌 SHA-1** 로 스레드를 찾으므로, 자동화가 스레드를 새로 만들 때 그 해시를
직접 넣어야 같은 스레드를 집는다. 해시는 글 폴더 이름의 SHA-1 이다. 저장소와 카테고리 id 는
`blog/discussions.json` 이 소유한다.

스레드를 미리 만들어 두는 것은 부작용이 아니라 이득이다. giscus 는 스레드가 없으면 첫 댓글을
쓰는 사람이 만들게 하는데, GitHub 검색 색인이 최종 일관성이라 만든 직후에는 검색이 못 찾아
같은 글에 스레드가 둘 생기는 창이 있다. 자동화가 방문자보다 먼저 만들면 그 창이 닫힌다.

### 본문 갱신 고르기

```json
"update": {
  "find": "Polars 1.44.1",
  "replace": "Polars {version}",
  "mode": "pr"
}
```

**정규식이 아니라 정확 문자열이다.** 정규식을 허용하면 글 한 편을 고치려다 다른 문장을 조용히
망가뜨릴 수 있고 그 사고는 발행된 뒤에야 보인다. `find` 가 본문에 정확히 없으면 아무것도
바꾸지 않고 실패로 보고한다. `replace` 에는 새 값이 들어갈 `{version}` 이 있어야 한다.

`mode` 는 `pr` 과 `commit` 둘이고 기본은 `pr` 이다. 숫자 한 줄만 바뀌는 글이면 `commit` 이
편하지만, 그 글의 다른 수치가 그 버전으로 잰 것이라면 사람이 다시 재야 하므로 `pr` 이 맞다.

고치면 같이 낡는 것이 둘 있다. 실행기가 그 둘을 함께 갱신한다.

1. `update.find` 자체. `Polars 1.44.1` 을 새 값으로 바꿔 놓고 `find` 를 그대로 두면 다음에는
   찾을 문자열이 본문에 없다
2. 같은 감시의 `anchor`. 본문 문장을 가리키는 포인터라 그 문장이 바뀌면 끊기고 `check:blog` 가
   그 다음 커밋을 막는다

**소식을 다루는 글에는 달지 않는다.** 005 가 `update` 를 안 쓰는 이유가 그것이다. 그 글은
`이 글을 쓴 시점의 최신은 3.14.7` 이라고 시점을 밝혀 적었고, 기계가 그 숫자만 갈아 끼우면
시점 서술이 거짓이 된다. 다음 판이 나오면 그 절 전체를 사람이 다시 쓴다.

## 감시 종류

| kind | 필수 필드 | 무엇을 보는가 | 출처 |
|---|---|---|---|
| `pypi` | `package` | 최신 정식 버전 | `pypi.org/pypi/<이름>/json` 의 `info.version` |
| `python` | 없음 (`series` 선택) | 계열의 최신 버전 | `endoflife.date/api/python.json` |
| `github-release` | `repo` (`owner/name`) | 최신 릴리스 태그 | `api.github.com/repos/<repo>/releases/latest` |
| `pep-status` | `status` (`type` 선택) | 그 상태인 PEP 번호 목록 | `peps.python.org/api/peps.json` |
| `feed` | `url` (`title`, `home` 선택) | 맨 위 글의 링크 | RSS 2.0 과 Atom 둘 다 |

종류의 정본은 `site/scripts/track.mjs` 의 `KINDS` 다. `check:blog` 가 그것을 import 해서
검사하므로 목록을 두 곳에 적지 않는다.

### python.org API 를 쓰지 않는 이유

`python.org/api/v2/downloads/release/` 는 쓰지 않는다. 2026-08-26 에 직접 찍어 보니
`ordering` 도 `is_latest` 필터도 **무시하고** 268 건을 통째로 준다. 그 안에 `is_latest` 가
참인 항목이 셋이고 (2.7.18, 3.14.7, 그리고 Python install manager 26.3) 파이썬이 아닌 설치
관리자까지 섞여 있다. 필터가 먹는 줄 알고 첫 항목을 집으면 Python 2.0.1 을 최신이라고 적게
된다.

endoflife.date 는 17 개 계열만 주고 계열마다 `latest` 와 `eol` 이 붙어 있다. 글이 특정 계열을
전제하면 `series` 로 그 계열만 본다.

### PyPI 에서 releases 키를 정렬하지 않는 이유

`info.version` 이 최신 정식 버전이다. `releases` 객체의 키를 정렬해 고르면 안 된다. 문자열
정렬이라 `1.9` 가 `1.44` 보다 뒤로 간다.

## 상태는 봇이 소유한다

```text
blog/track-state.json     마지막으로 본 값. 이 도구만 쓴다
```

계획은 사람이 쓰고 상태는 기계가 쓴다. 둘을 가른 이유는 봇 커밋이 글 폴더를 건드리지 않게
하기 위해서다. `git diff blog/track-state.json` 하나로 무엇이 실제로 움직였는지 다 보인다.

값이 바뀔 때만 `at` 을 갱신한다. 그래서 diff 에 실제 변화만 남는다.

**`actions/cache` 를 쓰지 않는다.** 7 일 안 쓰면 지워지고, 지워진 다음 실행이 모든 감시를 처음
보는 것으로 착각해 기준선을 다시 잡는다. 그러면 그 사이에 일어난 변화를 통째로 놓친다. 만료가
없는 곳은 저장소뿐이다.

처음 보는 감시는 지금 값을 기준선으로 잡고 알리지 않는다. 글 폴더를 지우면 그 감시는 상태
파일에서도 사라진다.

## 언제 도는가

`.github/workflows/track.yml` 이 하루 1 회 돈다. 손으로 돌리려면 Actions 탭의
`workflow_dispatch` 를 쓴다.

주 1 회로 시작했다가 2026-08-26 에 005 를 쓰면서 매일로 바꿨다. 005 가 보는 것은 버전만이
아니라 PEP 의 상태와 core 팀 블로그의 맨 위 글이고, 그것은 주 단위로 보면 이미 지난 소식이다.
버전 감시를 매일 찍어도 값이 그대로면 아무 일도 안 일어나므로 잃는 것이 없다.

**정시성을 약속하지 않는다.** GitHub 문서가 예약 실행의 지연과 드롭을 명시하고 실제로 몇
시간씩 밀린다. `매일 오전 9 시에 확인한다` 같은 서술을 글이나 문서에 쓰지 않는다.

예약 워크플로는 저장소가 60 일 동안 조용하면 자동으로 멈춘다. 그때는 `workflow_dispatch` 로
한 번 손으로 돌리면 다시 산다.

## 무엇을 알리는가

변화가 있거나 **확인에 실패하면** GitHub Issue 를 연다.

실패도 알리는 이유는 소스가 조용히 망가지기 때문이다. 패키지가 이름을 바꾸거나 API 가
개편되면 그때부터 그 감시는 영원히 아무것도 안 잡는다. 조용히 넘어가면 그 사실조차 모른다.

기본 채널인 이슈는 알림이 GitHub 계정 메일로 온다. 그래서 시크릿이 필요 없다. GitHub 기본 메일 알림
자체로는 `성공했지만 변화 감지` 를 표현할 수 없다. 켜면 변화 없는 날도 매일 오고 끄면 변화
있는 날에도 안 온다.

### 러너가 댓글을 달 수 있는가

**된다.** 워크플로의 `permissions` 에 `discussions: write` 를 주면 기본 `GITHUB_TOKEN` 으로
스레드를 만들고 댓글을 단다. 별도 PAT 나 App 이 필요 없다.

GitHub 문서는 `discussions: write` 로 무엇이 되는지 닫기와 삭제만 예로 들어서 댓글 추가가
되는지 확정할 수 없었다. 2026-08-26 에 실제로 태워서 확인했다. 러너가
`github-actions[bot]` 이름으로 003 의 스레드에 댓글을 달았고 그 댓글이 글 화면의 giscus
위젯에 그대로 떴다.

### 메일을 쓰려면

`mail` 채널은 시크릿 셋이 다 있어야 보낸다. 저장소 Settings > Secrets and variables >
Actions 에 넣는다.

| 시크릿 | 무엇 |
|---|---|
| `RESEND_API_KEY` | Resend API 키 |
| `TRACK_MAIL_FROM` | 보내는 주소. Resend 에서 인증한 도메인의 주소여야 한다 |
| `TRACK_MAIL_TO` | 받는 주소 |

하나라도 없으면 **보내지 않고 그 사실을 로그에 남긴다.** 조용히 넘어가면 메일이 오는 줄 알고
기다리게 된다. 시크릿이 없어도 다른 채널은 그대로 돌아간다.

## 손으로 돌리기

```powershell
cd site
npm run track                              # 확인만 한다. 변화가 있으면 종료 코드 1
node scripts/track.mjs --write             # 본 값을 상태 파일에 적는다
node scripts/track.mjs --report            # 이슈 본문 형식으로 낸다
node scripts/track.mjs --notify            # 고른 채널로 실제로 알린다
node scripts/track.mjs --apply-update      # update 를 단 감시의 본문을 고친다
node scripts/track.mjs --json              # 결과를 기계 판독 형식으로 낸다
```

`--notify` 는 `GITHUB_TOKEN` 이 필요하다. 손으로 돌릴 때는 `$env:GITHUB_TOKEN = gh auth token`
으로 넣는다. **실제로 이슈가 열리고 댓글이 달린다.** 배선을 시험할 때는 만든 것을 지운다.

`--apply-update` 는 파일을 실제로 고친다. 워크플로는 그 뒤에 `check:blog` 를 돌려 갱신한 글이
게이트를 통과하는지 보고, 통과해야 PR 이나 커밋으로 낸다.

종료 코드는 0 이 이상 없음, 1 이 변화나 확인 실패, 2 가 추적기 자체가 깨진 것이다.

`npm test` 에 넣지 않는다. 네트워크를 타므로 오프라인에서 커밋이 막히고, 커밋할 때마다 PyPI 를
찌를 이유가 없다. 계약 검사는 `check:blog` 가 하고 실제 관측은 워크플로가 한다.

## 새 감시 종류 추가하기

`site/scripts/track.mjs` 의 `KINDS` 에 한 항목을 더한다.

```js
myKind: {
  required: ["필수 필드 이름"],
  label: (w) => "알림에 보일 이름",
  source: (w) => "사람이 열어 볼 URL",
  async observe(w) {
    // 지금 값을 문자열 하나로 돌려준다. 실패하면 throw 한다.
  },
},
```

값을 문자열 하나로 좁힌 이유는 비교가 한 줄이어야 상태 파일의 diff 가 읽히기 때문이다.

`check:blog` 는 이 목록을 import 하므로 검사기를 따로 고치지 않는다.

**쓸 글이 생겼을 때 더한다.** `feed` 와 `pep-status` 도 005 를 쓰면서 더했다. 그전에는
그것을 쓰는 글이 없었다.

### 값을 고를 때 두 가지를 확인한다

**가장 큰 것을 고르지 않는다.** PEP 는 거버넌스 문서가 8000 번대를 쓴다. `Accepted` 중 번호가
가장 큰 것은 2018 년부터 `PEP 8016` 이라 그것을 집으면 감시가 영원히 같은 값을 돌려준다.
그래서 `pep-status` 는 번호 하나가 아니라 목록 전체를 값으로 삼는다.

**빈 값을 값으로 삼지 않는다.** 필드에 오타가 나면 조회는 성공하는데 결과가 비게 된다. 빈
문자열을 그대로 돌려주면 그 감시는 `변화 없음` 을 영원히 보고한다. `pep-status` 가 결과가
없을 때 throw 하는 이유다. 확인 실패는 알림으로 오지만 거짓 성공은 아무도 모른다.

## 되돌리기

| 무엇 | 어떻게 |
|---|---|
| 글 하나의 추적을 끈다 | 그 글의 `track.json` 을 지운다. 다음 실행이 상태에서도 지운다 |
| 감시 하나를 끈다 | `watch` 에서 그 항목을 지운다 |
| 전체를 멈춘다 | `.github/workflows/track.yml` 을 지우거나 Actions 탭에서 비활성화한다 |
| 기준선을 다시 잡는다 | `blog/track-state.json` 에서 해당 키를 지우고 다시 돌린다 |

워크플로가 바꾸는 파일은 `blog/track-state.json` 하나뿐이다. 본문과 사이트는 건드리지 않는다.
이 저장소는 `git push` 가 아니라 `npm run deploy` 로 배포되므로 봇 커밋이 공개 화면을 바꿀
경로 자체가 없다.
