# 블로그 이미지와 영상

## 섹션 구성과 렌더링

블로그의 섹션 기준은 운영자가 지정한 비공개 형제 저장소의
`curriculum/01-automation-start/04-run-python-online.md`다. **01~04 전체가 아니라 01단원의
04번 교안 하나**를 참고한다. 교안의 문장과 시각 자산은 복사하지 않고 구성과 렌더링 방식을 적용한다.

한 H2는 개념 하나만 맡는다. 섹션 수에 상한을 두지 않는다. 개념이 둘이면 섹션을 나누고 각 개념에
맞는 이미지를 붙인다. 기본 순서는 다음과 같다.

1. H2: 그 섹션의 개념을 짚는 짧은 제목
2. H3: 행동이나 차이와 결과를 설명하는 문장형 부제
3. 주 시각물: 바로 그 개념의 실제 화면, 이미지, 영상 또는 시뮬레이션
4. 서술형 설명: 시각물에서 보이는 대상과 관계를 이어서 설명하는 문단
5. 필요한 보조 자료: 표, 예시, 코드, 실행 칸, 실습 순서

**표, 코드 블록, 실행 칸, 번호 목록을 주 시각물로 대신하지 않는다.** 이미지 없이 표나 실행 칸만
있는 섹션을 완료로 판단하지 않는다. 정확한 값과 관계를 도식으로 보여 줘야 한다면 실측 자료를 확인한 뒤 ImageGen으로 만든다.
생성형 그림이 모든 섹션에 필요한 것은 아니지만 개념에 맞는 주 시각물은 각 섹션에 필요하다.
주 시각물의 기본은 내용을 직관적으로 보여 주는 장면형 이미지다. 모든 개념을 상자, 화살표,
라벨로 바꾼 도식을 기본값으로 삼지 않는다. 정확한 구조나 수치 비교를 장면만으로 설명하기
어려운 곳에서만 도식을 선택한다.
본문 뒤의 참고 링크 목록인 `더 해 볼 것`은 개념을 가르치는 섹션이 아니다.

섹션은 해당 개념의 설명과 확인으로 닫는다. 다음 섹션을 예고하려고 다른 개념을 끼워 넣지 않는다.
이는 이 블로그에 적용하는 교안 기준이며 전역 글쓰기 스킬의 일반 블로그 이음 방식보다 우선한다.

읽기 화면은 원문의 순서를 유지한다. 주 이미지는 16:9 프레임 안에서 원본을 자르거나 늘이지 않고
보여 주며 캡션은 이미지 밖에 둔다. 연결된 이미지의 링크와 캡션도 보존한다.
`site/src/components/Markdown.tsx`가 렌더링을, `site/scripts/visual-api.mjs`가 화면 점검을 맡는다.
섹션 구성의 누락은 교안처럼 편집 권고로 보고하고, 깨진 이미지와 화면 오류는 실패로 구분한다.
**서로 다른 H2가 같은 이미지를 돌려 쓰지 않는다.** 한 섹션에 필요한 보조 이미지는 추가할 수 있다.

### 공식 원본도 본문 배치 기준을 따른다

**출처가 정확한 것과 설명이 읽히는 것은 별개의 조건이며 둘 다 충족해야 한다.** 공식 이미지,
직접 캡처, 생성 이미지에 같은 본문 배치와 가독성 기준을 적용한다. `source-original-v1`은 원본의
내용과 색을 보존하는 프로필이지 크기, 비율, 구도와 화면 검수를 면제하는 프로필이 아니다.

제작 규격은 비공개 형제 저장소 `../eddmpython-course/scripts/course-scene.mjs`의
`visualPlanning.generationGuide.canvas`와 `visualPlanning.lectureProfiles`를 준용한다.
작업 시작 때 그 저장소에서 `npm run scene:catalog`로 현재 값을 확인하고, 장면에 맞는 프로필을
선택한다. 허용 크기, 최소 원본 크기, 안전 영역과 대상 점유 기준의 수치를 이 문서나 글별 계획에
따로 복제하지 않는다. 교안의 문장, 자산과 구현은 가져오지 않는다.

| 구분 | 적용 원칙 |
|---|---|
| 출처 원본 | 원래 비율, 색, 글자와 제품 형태를 보존한다. 원본 주소와 출처를 기록한다 |
| 본문용 제작본 | 선택한 프로필의 `ratio`, `minimumSource`, `safeArea`, `stageFit`을 함께 적용한다. 프레임 비율만 맞췄다고 제작을 끝내지 않는다 |
| 화면 배치 | 위 렌더링 규칙대로 제작본 전체를 보여 준다. 자동 잘림이나 가로·세로를 다르게 늘리는 방식으로 틀을 채우지 않는다 |
| 읽힘 | 그 절에서 설명하는 버튼, 값, 코드와 관계를 본문 크기에서 구별할 수 있어야 한다. 빈 배경이나 메뉴까지 포함한 이미지 면적으로 대상 점유를 계산하지 않는다 |

원본 파일 자체가 제작 캔버스와 다른 비율일 수 있다. 이때 원본을 찌그러뜨려 규격을 맞추지 않고,
본문용 구도 안에 원래 비율로 배치한다. 안전 영역은 잘림을 막는 공간이며 장식용 여백의 목표가
아니다. 작은 그림에 큰 빈 배경을 붙이거나 픽셀 수만 늘린 파일은 해상도와 점유 기준을 충족한
것으로 취급하지 않는다.

화면 설명은 그 절에 필요한 영역과 상태부터 정한다. 전체 페이지를 축소했을 때 글자가 읽히지
않으면 필요한 부분을 충분한 해상도로 다시 캡처한다. 제작 단계의 부분 캡처는 허용하지만,
설명에 필요한 버튼, 열 이름, 값이나 결과를 잘라서는 안 된다. 캡션에는 부분 화면임을 밝히고
전체 문서나 원본으로 가는 링크를 보존한다. 저작권 표기는 사용 조건에 맞게 유지한다.

치트시트와 긴 문서는 설명할 구역을 크게 보여 주고 전체 자료는 링크로 제공한다. 작은 공식
이미지는 더 큰 공식 원본이나 실제 화면 캡처를 먼저 찾는다. 흐린 글자를 생성 도구로 추측해서
복원하거나, 원본 링크를 눌러 확대할 수 있다는 이유로 본문 가독성 검사를 생략하지 않는다.

### 제작과 검수의 완료 조건

1. `media.json`의 `visualSubject`와 `contentAnchor`로 독자가 그림에서 확인할 대상을 정한다
2. 원본의 실제 픽셀 크기와 비율을 확인하고 course의 해당 프로필에 맞는 구도를 선택한다
3. `narrativeUse`에 선택한 프로필과 크게 보여 줄 대상을 기록한다. 캡처라면 `captureState`에 실제 화면 상태와 부분 캡처 범위를 남긴다
4. 제작본의 픽셀 크기를 읽고, 핵심 대상의 점유와 안전 영역을 확인한다. 원본과 대조해 글자, 값과 형태가 유지됐는지도 본다
5. 데스크톱과 모바일 본문에서 직접 확인한다. 별도 확대 없이 그 절이 짚는 대상과 관계를 읽을 수 있어야 한다
6. 위 조건을 충족한 바이트만 발행한다. 이미지 변경 뒤에는 같은 화면에서 다시 확인한다

**자동 검사 통과, 공식 출처 확인, 이미지 업로드 성공은 각각의 확인 결과일 뿐 시각 검수 완료가
아니다.** 검수에서는 실제로 확인한 화면과 판단을 남긴다. 작은 리본을 흐리게 확대하거나, 문서
전체를 읽을 수 없게 축소하거나, 핵심 대상보다 빈 공간이 크게 남은 제작본은 다시 구성한다.
화면 증거의 생성과 승인 절차는 [visualVerification.md](visualVerification.md)를 따른다.

### 혼자 따라 할 수 있는 섹션 배선

섹션의 설명 방식도 위 교안을 기준으로 삼는다. 독자가 필요한 것을 따로 검색하거나 생략된 단계를
추측하지 않아도, 그 섹션 안의 자료로 행동하고 결과를 확인할 수 있어야 한다. 쉬운 말과 교정 기준은
전역 `$blog-writing`이 소유하고, 이 절은 공개 블로그에서 자료와 실행 화면을 연결하는 계약을 맡는다.

- 시작 위치를 밝힌다. 열 주소, 프로그램, 폴더와 파일, 선택할 화면 상태를 그 행동 앞에 적는다
- 필요한 것은 쓰는 섹션에서 제공한다. 공식 페이지는 직접 링크하고, 예제 파일은 다운로드 또는
  그대로 실행하면 만드는 완결 코드를 제공한다. 글 끝의 링크 목록만으로 준비 단계를 대신하지 않는다
- 입력할 문장, 값과 명령을 복사할 수 있게 준다. 이미지 속 글자를 독자가 다시 타이핑해야만
  진행되는 구성은 쓰지 않는다. 버튼과 메뉴는 실제 화면에 적힌 이름으로 부른다
- 앞에서 만든 파일이나 결과가 필요하면 이름과 해당 섹션 링크를 붙인다. 다른 글을 읽었다고
  전제하지 않으며, 이 글에 없는 준비물을 이미 가지고 있다고 가정하지 않는다
- 실습은 입력, 실행, 확인할 결과를 한곳에 둔다. `실행하세요`, `결과를 확인하세요`만 쓰지 않고
  어디에서 어떤 명령이나 버튼을 쓰며 어떤 파일명, 값, 화면이 보여야 하는지 적는다
- 개념 설명은 억지 설치 절차를 만들지 않는다. 실제 화면, 데이터나 전후 문장을 제공하고 어디를
  비교하면 그 개념을 구분할 수 있는지 짚는다. 답을 확인할 근거도 같은 섹션에 둔다
- 계정, 설치, 비용 또는 접근 권한이 필수라면 행동 전에 알린다. 브라우저 실습과 내 컴퓨터에서의
  실행은 구분하고, 브라우저 결과를 로컬에 저장된 파일처럼 설명하지 않는다
- 한 섹션이 맡은 개념의 확인으로 닫는다. 필요한 준비를 생략해 섹션을 짧게 만들지 않으며,
  별개 개념의 설명이 필요하면 새 섹션으로 나눈다

검수 때는 각 섹션의 링크와 파일을 실제로 열고, 제공한 입력으로 같은 동작을 해 본다. 없는 파일,
접근 불가 링크, 본문과 다른 버튼 이름, 빠진 실행 단계와 결과 불일치는 고친 뒤 다시 확인한다.
이미지의 개수나 문장의 짧음만으로 따라 할 수 있다고 판단하지 않는다.

## 미디어 정보의 소유

| 무엇 | 어디 | 추적 |
|---|---|---|
| 의미와 출처 계획 | 각 글 폴더의 `blog/posts/<글>/media.json` | Git |
| 생성 이미지의 공통 지시문과 색 토큰 대응 | `blog/media/imageStyle.json` | Git |
| 교안의 의미와 출처 계획 | `../eddmpython-course/curriculum/<카테고리>/plan.json` | 형제 비공개 저장소 |
| 글과 원격 객체의 대응 | `blog/media/catalog.json` | Git |
| 실제 바이트 | Hugging Face `eddmpython/eddmpython-media` | 원격만 |

### plan 을 둘로 나눈 이유

`plan.json` 은 자산마다 `sectionHeading` 과 `contentAnchor` 를 들고 있고 그 둘은 본문 문장
그대로다. `contentAnchor` 는 `check:post` 가 본문에 실제로 있는 문장인지 대조하는 필드라서
정의상 본문에서 복사한 것이다.

교안은 유료 자료이므로 그 문장이 공개 저장소에 올라가면 안 된다. 그래서 **plan 만 갈랐다.**
이미지 바이트와 `catalog.json` 은 블로그와 그대로 공유한다. catalog 에는 `alt` 와
`visualSubject` 와 `sourcePost` 만 들어가고 그것은 이미지 설명이다.

```bash
python -X utf8 blog/scripts/generate_flux.py <post-id> --plan ../eddmpython-course/curriculum/01-automation-start/plan.json
python -X utf8 blog/scripts/publish_media.py --asset <post-id>/<key> --plan ../eddmpython-course/curriculum/01-automation-start/plan.json --reviewed
```

**`--plan` 을 주면 글 파일을 그 plan 이 있는 폴더 아래에서 찾는다.** 교안 글이 plan 옆에
있기 때문이다. 블로그는 글 폴더 안에 본문과 계획이 함께 있으므로
블로그 자산에는 `--plan` 을 주지 않는다. 주면 글을 못 찾는다.

**바이트는 저장소에 커밋하지 않는다.** SVG 를 포함해 `blog/` 아래에 이미지 파일을 두지 않는다.
`check:blog` 가 막는다. 작업본은 저장소 밖에 둔다.

```text
<EDDMPYTHON_RUN_DIR>/blog-media/<post id>/<assetKey>.webp
```

PNG, JPG, GIF도 지원한다. ImageGen 결과는 원본 PNG를 우선 보존하고, 용량 변환이 필요하면 색과 세부 내용이 유지되는지 확인한다.

## plan.json 계약

### Codaro 학습 이미지 연결

블로그와 Codaro 수업이 같은 개념을 설명하면 검수한 공개 이미지의 같은 원본을 사용할 수 있다.
서로 다른 개념의 섹션에 같은 그림을 반복하는 것과는 다르다. 캡처가 블로그 도구 화면이면 Codaro
실행 화면이라고 부르지 않고, 학습할 입력·출력 또는 검토 대상을 보여 주는 참고 화면으로 표시한다.

원본 바이트와 출처의 정본은 이 문서의 미디어 소유 표를 유지한다. Codaro는 공개된 콘텐츠 주소
객체를 해시로 고정해 자체 자산으로 받아 배포한다. 실행 중 외부 이미지 서버에 의존하거나 형제
저장소 경로를 읽지 않는다. Codaro의 등록과 로컬 배포 절차는 해당 저장소의
`docs/skills/ops/product/branding.md`가 소유한다.

등록할 때 블로그 자산 ID, 공개 원본 주소, 해시와 출처를 보존하고 Codaro 섹션은 등록된 자산 ID를
참조한다. 그림의 색·질감을 수업마다 다시 만들지 않으며, 학습 문맥에 맞는 설명은 이미지 밖에 둔다.
원본이 바뀌면 자동으로 최신 그림을 덮어쓰지 않고 내용과 가독성을 다시 검수한 뒤 참조를 갱신한다.
유료 교안 이미지나 비공개 화면은 이 공유 대상에 포함하지 않는다.

**최상위에 `version` 과 `promptContract` 가 있고 자산은 `assets` 아래에 들어간다.**
`check-blog.mjs` 와 `publish_media.py` 가 둘 다 이 래퍼를 요구한다.

발행할 asset id는 `<post id>/<영문 kebab 키>`다. 블로그의 post id는 세 자리 순번으로 시작하고
공유 업로더는 교안의 두 자리 순번도 받는다. 허용 형식의 정본은 `publish_media.py`의 `ASSET_ID_RE`다.
아래는 블로그 글 폴더 안의 `media.json` 형식이다. `assets`의 키에는 해당 글 안의 자산 키만 쓴다.

```json
{
  "version": 1,
  "promptContract": "section-grounded-v2",
  "assets": {
    "example-scene": {
      "role": "section",
      "sectionHeading": "이 이미지가 바로 뒤따르는 H2 원문",
      "sectionSubtitle": "본문 H3와 같은 한 줄 부제",
      "contentAnchor": "이미지가 설명할 본문의 실제 문장",
      "visualSubject": "화면, 파일, 코드, 명령, 결과처럼 눈으로 확인할 대상",
      "visualRelationship": "대상의 전후, 원인과 결과, 순서",
      "visualProfile": "eddmpython-direct-v1",
      "palettePolicy": "eddmpython-source-aware-v1",
      "visualMode": "scene",
      "alt": "이미지를 보지 못해도 내용을 이해할 수 있는 설명",
      "placement": "H3 부제 바로 뒤",
      "narrativeUse": "독자가 글의 문제 장면을 한눈에 이해한다",
      "sourcePolicy": "auto",
      "sourceKind": "imagegen",
      "prompt": "본문의 구체적인 대상과 행동을 어떻게 보여 줄지 적는다"
    }
  }
}
```

`role` 은 공유 대표 이미지 `hero`, 각 H2 의 첫 이미지 `section`, 추가 설명 이미지 `support`
중 하나다. 대표 이미지가 특정 H2 의 의미 장면과 맞으면 `section` 이미지 하나를 og 에도 함께
써도 된다.

`check:post` 가 대조하는 것이 셋이다.

- `sectionHeading` 이 본문 H2 원문과 **정확히** 같은가
- 부제를 쓴 절이면 `sectionSubtitle` 이 H3 원문과 같은가
- `contentAnchor` 가 그 절의 설명에 **실제로 있는 문장**인가

### 이미지는 부제 바로 아래에 붙는다

새로 쓰거나 고치는 섹션은 위 구성대로 H3를 두고 그 바로 뒤에 `role: section` 이미지를 붙인다.
기존 자산을 깨뜨리지 않기 위해 업로더와 파서는 아래 두 배치를 계속 읽는다.

| 그 절의 모양 | `sectionSubtitle` | `placement` |
|---|---|---|
| H2 아래 H3 부제가 있다 | 그 H3 원문과 같아야 한다 | `H3 부제 바로 뒤` |
| H2 아래 부제가 없다 | 비운다 | `H2 제목 바로 뒤` |

어느 쪽이든 **이미지는 제목과 부제 다음에 가장 먼저 오는 것**이어야 하고
`contentAnchor` 는 이미지 **아래**의 문장이어야 한다. `check-blog.mjs` 가 그 절의 본문에서
찾는다.

**본문을 먼저 쓰고 그 뒤에 plan 을 적는다.** 그 절의 서술 문단이 없으면 `contentAnchor` 를
지어내게 된다. 신규 이미지는 `site/scripts/imagePrompt.mjs`가 이 근거와 공통 스타일을 묶는다.

## 내용에서 이미지 선택

이미지는 분위기를 채우는 장식이 아니다. **본문이 말하는 실제 제품, 화면, 파일, 입력과 결과를
직접 보여 준다.** 이미지와 설명을 읽기 위해 독자가 비유를 해석해야 한다면 대상 선택부터 고친다.

| 본문이 다루는 것 | 선택할 이미지 | 지킬 것 |
|---|---|---|
| 실제 제품과 서비스 | 공식 제품 이미지, 공식 배포 로고, 사용 허락을 확인한 이미지, 직접 캡처한 제품 화면 | 제품의 형태, 비율, 상표와 고유 색을 유지 |
| 화면 사용법과 동작 | 실제 화면을 먼저 확인하고 그 화면의 해당 상태를 캡처하거나 ImageGen으로 묘사 | 실제 버튼, 입력값, 파일명과 결과의 관계를 보존 |
| 개념과 변화 | 본문에 나온 구체적인 파일, 데이터, 코드와 실제 결과를 ImageGen으로 표현 | 다른 사물로 치환하지 않고 설명 대상 자체를 보여 줌 |
| 꼭 필요한 구조와 수치 비교 | 확인한 관계와 실측 자료를 입력한 ImageGen 도식 | 연결 방향, 수치, 단위와 크기 관계를 원자료와 대조 |

제품 이미지를 차용할 때는 공식 사이트나 공식 미디어 자료를 먼저 찾고, 사용 조건과 출처를 확인한다.
검색 결과 썸네일만 보고 가져오거나 생성한 로고를 공식 로고처럼 쓰지 않는다. 원본 URL, 제공자,
사용 조건은 해당 글의 `media.json`에 기록하고 필요한 출처 표기는 이미지 밖에 둔다.

화면 설명은 실제 화면을 먼저 열어 확인한다. 파일 선택 설명이면 파일 선택 화면을, CSV의 앞자리 0
설명이면 실제 파일 내용과 읽은 값을 보여 준다. 디지털 원고 교정을 종이 원고와 연필로 바꾸거나,
데이터 처리를 창고와 컨베이어로 바꾸는 식의 추상적 대체 이미지를 쓰지 않는다.

화면을 ImageGen으로 묘사할 때는 확인한 캡처를 내용 참조로 제공한다. URL을 프롬프트에 적은 것만으로
참조 이미지를 제공했다고 취급하지 않는다. 실제 캡처와 생성한 설명 이미지는 출처와 캡션에서 구분하며,
생성한 화면을 실행 성공의 증거로 쓰지 않는다. 정확한 글자나 제품 모습이 훼손되면 원본과 대조하여
ImageGen으로 수정한다. 원본 캡처만으로 설명이 충분하면 생성 이미지로 바꿀 필요가 없다.

## 공통 색감과 표현

규칙의 의미와 선택 기준은 이 문서가 소유한다. 생성에 쓰는 공통 지시문, 프로필 이름, 화면 비율과
색 토큰 대응은 `blog/media/imageStyle.json`이 소유한다. 색상 값 자체는
`site/src/design.ts`의 `DESIGN.palette` 한 곳에서 읽는다. 글마다 색상 값을 복사하지 않는다.

| 요소 | 공통 기준 |
|---|---|
| 기본 바탕 | 차콜 계열의 어두운 중성색. 추가 배경은 `carbon` 토큰 사용 |
| 주요 면과 글자 | 아이보리 계열의 밝은 중성색. `ivory` 토큰 사용. 화면 내용은 읽을 수 있는 대비 유지 |
| 강조색 | `brand` 토큰의 코랄. 지금 눌러야 할 곳, 달라진 값, 확인할 결과 중 한 초점에만 사용 |
| 보조색 | 중성 회색과 명도 차이. 항목을 구분하려고 무지개색을 늘리지 않음 |
| 실제 제품과 화면 | 원본의 고유 색이 공통 팔레트보다 우선. 로고, UI 상태색, 사진을 일괄 흑백화하거나 코랄로 칠하지 않음 |
| 질감 | 절제된 사실적 디지털 편집 이미지. 무광, 또렷한 윤곽, 대상이 실제로 가진 미세 질감 |
| 조명 | 부드러운 중성 방향광과 얕은 자연 그림자. 과장된 역광과 영화 같은 광원 효과는 쓰지 않음 |
| 화면 표현 | 글자, 아이콘과 데이터는 선명하게. 화면 위에 종이 결, 붓 터치, 거친 필름 입자를 덧씌우지 않음 |
| 피할 느낌 | 금색·세피아 색조, 네온, 플라스틱 장난감, 과도한 광택, 장식용 그라데이션, 의미 없는 빛 효과 |

강조색은 장식이 아니라 **설명에서 보라는 곳**에 놓는다. 가장 밝은 픽셀을 자동으로 코랄로 칠하는
방식은 신규 이미지에 쓰지 않는다. 실제 제품 원본에 들어 있는 색은 금지 팔레트에 맞추려고 변조하지
않는다. 팔레트 제한은 새로 추가하는 배경, 장식과 강조를 대상으로 한다.

큰 제목, 부제, 본문과 캡션은 HTML과 마크다운에 남긴다. 이미지에는 대상과 관계를 식별하는 데 필요한
짧은 라벨만 넣는다. 실제 화면의 글자는 그대로 유지하고 새로 필요한 라벨은 본문과 같은 이름을 쓴다.
장면, 화면, 도식 모두 같은 공통 느낌을 사용하지만 구도를 획일적인 카드나 상자로 고정하지 않는다.

같은 작업에서 만드는 이미지에는 공통 지시문을 그대로 사용한다. 기준 이미지가 있으면 모든 생성에
동일한 스타일 참조로 연결한다. 내용 참조와 스타일 참조를 구분하며, 스타일 참조의 사물이나 내용을
다른 글에 복제하지 않는다. 내용의 정확성과 화면의 가독성이 스타일보다 우선한다.

## ImageGen 제작

신규 설명 이미지와 필요한 도식은 전역 `imagegen` 스킬을 읽고 **내장 ImageGen**으로 만든다.
도식이 정확해야 한다는 이유로 SVG, HTML, Canvas, Mermaid를 렌더한 이미지를 대신 납품하지 않는다.
계산과 데이터 검증에 코드를 쓰는 것은 허용하지만 최종 설명용 도식 이미지는 ImageGen이 만든다.

기존 `generate_flux.py`는 이전 회색 원본과 교안 작업을 위한 별도 API 경로다. 신규 블로그 이미지의
기본 생성 명령이 아니다. 모델이나 CLI 경로를 바꾸는 것은 `imagegen` 스킬의 명시 선택 절차를 따른다.
기존 `authored` 자산도 호환과 이력 재현을 위해 읽을 뿐 신규 제작의 기본값으로 고르지 않는다.

### 프롬프트 구성

`site/scripts/imagePrompt.mjs`는 해당 절의 주장과 대상, 관계에 공통 지시문과 현재 디자인 색을 붙인다.
색이나 질감 지시를 각 글의 자유 프롬프트에 다시 쓰지 않는다. 이 명령은 프롬프트만 출력하며 이미지를
생성하거나 외부 서비스에 전송하지 않는다.

```powershell
cd site
node --experimental-strip-types scripts/imagePrompt.mjs
node --experimental-strip-types scripts/imagePrompt.mjs <post-id> <asset-key>
```

첫 명령은 현재 공통 기준을 확인한다. 두 번째 명령의 대상은 신규 프로필로 작성한 이미지 계획이어야
한다. 출력한 프롬프트와 직접 확인한 참조 이미지를 ImageGen에 제공한다. 결과를 보기 전에 자동으로
본문 URL을 바꾸거나 `--reviewed`로 발행하지 않는다.

### 계획에 남길 근거

신규 ImageGen 계획은 공통 파일의 `visualProfile`과 `palettePolicy`를 사용하고
`visualMode`를 `scene`, `screen`, `diagram` 중에서 정한다.

- 공통 의미: `contentAnchor`, `visualSubject`, `visualRelationship`은 본문 실제 내용을 가리킨다
- 화면 묘사: `sourceUrl`과 `captureState`에 확인한 화면 주소와 입력·선택·결과 상태를 남긴다
- 도식: `diagramEvidence`에 필요 이유와 관계·수치를 확인한 자료 또는 실행 결과를 남긴다
- 차용 자료: `credit`, `license`에 제공자와 확인한 사용 조건을 남긴다. 공식 이미지도 사용 조건을 확인한다
- 내용 참조와 스타일 참조: `referenceImages`에 역할, 출처 URL 또는 발행 객체 주소와 보존할 요소를 남긴다
- 실제 생성에 쓴 요청: `prompt`에는 구체적인 장면 지시를, 공통 스타일은 프로필로 연결한다

| 자산 | `sourceKind` | 프로필 |
|---|---|---|
| 실제 제품 캡처 | `screenshot` | `product-screen-v1` |
| 공식 또는 사용 허락을 받은 원본 | `official` 또는 `licensed` | `source-original-v1` |
| 화면 묘사, 내용 직접 이미지, 필요한 도식 | `imagegen` | `imageStyle.json`의 신규 프로필 |
| 실제 화면 녹화 | `recording` | `source-original-v1` |
| 기존 코드 렌더 도식 | `authored` | `design-token-svg-v1`, 이전 자산의 재현 전용 |

### 검수와 보관

1. 원본 자료와 결과 이미지의 제품, 화면, 파일, 값과 관계가 같은지 직접 본다
2. 다른 섹션의 그림과 바꿔도 자연스러우면 본문과 직접 연결됐는지 다시 판단한다
3. 화면의 글자와 도식의 수치·단위·연결을 하나씩 대조한다. 그럴듯한 그림을 정확한 그림으로 취급하지 않는다
4. 기본색, 강조 위치, 질감과 조명이 공통 기준을 따르는지 여러 이미지를 함께 놓고 확인한다
5. 데스크톱과 모바일 본문에서 자르지 않고 읽히는지 확인한다. 제목과 캡션, 출처는 이미지 밖에 둔다
6. 통과한 파일만 기존 staging과 Hugging Face 발행 절차로 연결한다

생성된 원본은 색을 다시 칠하지 않고 그대로 보존한다. `imagegen` 스킬의 기본 저장 위치는 작업
입구일 뿐이며, 글에 연결할 이미지의 최종 바이트는 아래 콘텐츠 주소 객체로 발행한다. 수정본은 새 객체로
남기고 이전 객체를 자동 삭제하지 않는다. 필요한 변환에서도 내용과 색을 바꾸지 않으며, 색·장면·강조를
수정할 때는 ImageGen에 원본을 참조로 제공한다.

### 이전 회색 원본의 유지

`eddmpython-dark-v2`와 `eddmpython-gray-master-v1`은 기존 자산과 해당 계약을 쓰는 교안의
유지 경로다. `paint_media.py`는 이 회색 원본 전용이며 신규 이미지와 제품 원본을 넣지 않는다.
기존 원본의 `masterSha256`과 `masterPath`는 지우지 않는다. 원본을 다시 받을 때는 해시를 대조하고,
기존 강조색을 다시 칠해 발행하면 원본과 발행본을 함께 업로드한다.

`publish_media.py --verify`는 HF 트리 API의 페이지를 끝까지 읽어 객체의 존재, SHA-256과 바이트 수를
확인한다. `.github/workflows/media.yml`이 원본과 발행본을 함께 감시한다. 원본 접미사와 staging
경로의 정본은 `blog/scripts/media_paths.py`다.

### 본문 보조 자료

`flow` 코드 블록은 번호와 화살표를 가진 본문 보조 카드다. 주 이미지나 ImageGen 도식의 대체물이
아니다. 실행 칸과 비교 도구 역시 실제 동작을 보여 주는 보조 자료로 유지한다. 녹화는 원본을 보존하며
개인정보나 자격증명이 보이는 화면은 발행하지 않는다. 공유 catalog의 교안 자산 검증은 비공개 저장소가
소유하며, 공개 블로그의 새 스타일 규칙 때문에 교안의 기존 계획을 일괄 변환하지 않는다.

## Hugging Face 발행

본문에는 먼저 자리표시자를 둔다. 같은 이미지를 공유 카드에도 쓰려면 frontmatter 에
`ogImage: media://hero` 를 추가한다. 업로더가 plan 의 대체 텍스트와 실제 너비, 높이, MIME 을
frontmatter 에 함께 기록한다.

```markdown
![대체 텍스트](media://hero "독자에게 보이는 선택 캡션")
```

발행 전 준비는 한 번만 한다.

```bash
uv venv .venv
uv pip install --python .venv/Scripts/python.exe -r blog/requirements.txt
```

데이터셋을 처음 만들 때만 `--create-repo` 를 붙이고 이후에는 뺀다.

```bash
python -X utf8 blog/scripts/publish_media.py --asset 20260808-example/hero --reviewed
```

스크립트는 이 순서를 바꾸지 않는다.

1. plan 과 저장소 밖 작업본을 검증한다
2. 파일 바이트의 SHA-256 을 계산한다
3. `objects/sha256/<앞 두 글자>/<전체 해시>.<확장자>` 에 올린다
4. 원격 객체가 실제로 존재하는지 다시 확인한다
5. **회색 원본이 옆에 있으면 같은 방식으로 올리고 다시 확인한다**
6. catalog 에 바이트 수, MIME, 너비, 높이를 기록하고, 원본이 있으면 `masterSha256` 과
   `masterPath` 를 자산에 적는다. 본문의 `media://` 를 Hugging Face URL 로 바꾼다
7. 성공한 로컬 작업본과 원본과 빈 staging 폴더를 삭제한다

**참조가 끊긴 객체를 자동으로 지우지 않는다.** 글을 갈아엎어도 이미지는 남는다.

**업로드나 원격 확인이 실패하면 본문과 catalog 를 바꾸지 않는다.** 원격 검증 전에 공개 참조를
바꾸지 않고, catalog 갱신 전에 로컬 원본을 지우지 않는다.

## 보존하고 찾아 쓰고 나중에 지운다

**`catalog.objects` 는 지금 글이 안 쓰는 이미지도 그대로 들고 있는다.** 2026-08-19 까지는
`publish_media.py` 가 발행할 때마다 참조 없는 객체를 조건 없이 지웠다. 그 시점에 참조 없는
객체가 260개였고 한 번만 발행하면 전부 사라질 참이었다. 004 가 옛 글 이미지 여덟 장을 다시 쓸
수 있었던 것이 이 색인 덕분이라 자동 삭제를 없앴다.

객체 레코드는 자기 설명을 함께 가진다. `alt`, `visualSubject`, `sourcePost` 다. 글이 사라져도
무엇이 그려진 이미지인지 남는다.

```bash
python -X utf8 blog/scripts/publish_media.py --find 전표      다시 쓸 이미지를 설명으로 찾는다
python -X utf8 blog/scripts/publish_media.py --prune-objects  참조 없는 것을 보여만 준다
python -X utf8 blog/scripts/publish_media.py --prune-objects --apply   실제로 정리한다
```

`--find` 는 지금 쓰는 것과 안 쓰는 것을 함께 보여 준다. 찾은 객체를 다시 쓰려면 새 글의
`plan.json` 에 항목을 만들고 같은 `sha256` 을 catalog 에 이어 준다.

**`--prune-objects` 는 교안 참조를 함께 센다.** 교안 plan 은 공개 catalog 의 `assets` 에
등록되지 않으므로 catalog 만 보면 교안이 쓰는 객체가 전부 참조 없음으로 보인다.
2026-08-19 에 실제로 279개 전부가 삭제 대상으로 잡혔다. `course_referenced_sha()` 가
교안 plan 의 `inventory` 와 `assets`, 그리고 교안 본문의 sha 를 모아 그것을 막는다.

`--prune-objects` 는 **catalog 레코드만** 지운다. Hugging Face 의 실제 바이트는 그대로 남으므로
이미 배포된 글의 이미지가 깨지지 않는다. 원격까지 지우는 것은 되돌릴 수 없으니 따로 한다.

발행 스크립트는 이미 설정된 셸 환경변수를 먼저 쓰고, 없으면 eddmpython 루트 `.env`,
형제 DartLab `.env` 순서로 읽는다. **`HF_TOKEN` 은 이 로컬 저장소에만 두고 Git, 문서, 로그에
값을 남기지 않는다.** 경계는 [secrets.md](secrets.md) 다.

## 확인과 롤백

```bash
cd site && npm run verify:media
```

원격에 실제로 있는지 본다. 배포 뒤에는 캐시버스터를 붙인 글 URL 에서 H2별 이미지와
`og:image`, `twitter:image` 가 plan 과 catalog 의 기대값과 같은지 대조한다.

롤백은 본문의 이미지 주소와 `catalog.json` 을 이전 커밋으로 되돌린 뒤 다시 배포한다.
Hugging Face 객체는 콘텐츠 주소라 지우지 않아도 되고, 지우면 옛 배포가 깨진다.
